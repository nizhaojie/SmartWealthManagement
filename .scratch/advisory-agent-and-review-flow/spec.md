# 投顾助手 Agent 与审核流

Status: ready-for-agent

前置：`customer-profiling-and-suitability`（画像与候选池）、`product-screening-and-customer-assets`（持仓聚合与穿透）

## Problem Statement

理财顾问为一位客户出一份方案，现在要手工做完整条链路：翻画像、回忆适当性规则、逐页翻产品手册筛出合规产品、比较收益与期限、写推荐理由、排版成一份能给客户看的文档。一位客户一两个小时，一天做不了几个。

而客户那边，`product-screening-and-customer-assets` 里的「请顾问出具方案」入口已经在源源不断地产生请求——现在这些请求落地之后没有任何东西接住。

这里有一条不能碰的红线：**投顾内容送达客户前必须经理财顾问审核**。让 AI 直接把方案发给客户是违规的；但让 AI 生成初稿、顾问审核后发出是合规的。两者的差别全在于审核是否真实发生过——而「真实发生过」需要能被举证，光有一个「已审核」的状态标记不够。

## Solution

投顾助手 Agent 面向理财顾问，读取客户画像与持仓，在**候选池**范围内（已完成适当性硬过滤）做排序与阐述，产出产品推荐、资产配置建议与推荐理由。这些输出默认是**投顾内容**，不会自动送达客户。

生成的版本叫 **AI 原稿**，永久留存。顾问在审核界面看到原稿、可编辑、可放行或驳回；放行后产生 **顾问定稿**，这是唯一允许送达客户的版本。原稿与定稿都在库中，两者的差异即是审核留下的痕迹——能用来举证审核是实质性的而非橡皮图章。

顾问的画像面板里增加一张**目标配置与实际配置的对比图**（ADR-0006）——两者的差额正是方案要解决的问题。

## User Stories

### 理财顾问 · 生成

1. As a 理财顾问, I want to 对一位客户发起方案生成, so that 我不必从零开始写
2. As a 理财顾问, I want to 系统只在候选池里选产品, so that 我不必再自己核对适当性
3. As a 理财顾问, I want to 看到推荐理由并且理由引用了客户画像的具体信息, so that 我能判断它是不是针对这位客户的
4. As a 理财顾问, I want to 看到每款推荐产品的排序依据（收益、风险、期限匹配度各自的贡献）, so that 我能判断排序是否合理
5. As a 理财顾问, I want to 拿到一份资产配置比例建议, so that 我有一个可以讨论的起点
6. As a 理财顾问, I want to 系统提示客户持仓的行业集中度风险, so that 我不会推出一个让集中度更糟的方案
7. As a 理财顾问, I want to 指定生成时的侧重（例如更看重流动性或更看重收益）, so that 方案贴近这位客户当下的诉求
8. As a 理财顾问, I want to 在客户画像置信度低或已过期时收到警示, so that 我不会基于过时信息出方案
9. As a 理财顾问, I want to 看到客户提交的方案请求队列, so that 我知道谁在等我

### 理财顾问 · 审核

10. As a 理财顾问, I want to 在审核队列看到所有待审内容及其等待时长, so that 我能安排处理顺序
11. As a 理财顾问, I want to 审核页有独立 URL, so that 我能把一条待审内容的链接存下来或发给别人
12. As a 理财顾问, I want to 浏览器后退键能从审核页回到队列, so that 我不必去找返回按钮
13. As a 理财顾问, I want to 并排看到 AI 原稿与我的编辑版本, so that 我清楚自己改了什么
14. As a 理财顾问, I want to 编辑内容后放行, so that 送达客户的是我认可的版本
15. As a 理财顾问, I want to 驳回一份内容并填写理由, so that 生成方知道问题在哪
16. As a 理财顾问, I want to 放行时系统校验推荐产品仍在候选池内, so that 我不会因为手工编辑意外引入越级产品
17. As a 理财顾问, I want to 看到我审核过的历史记录, so that 我能回溯自己的判断
18. As a 理财顾问, I want to 一份内容在我审核期间不被他人同时编辑, so that 不会出现互相覆盖

### 客户经理

19. As a 客户经理, I want to 看到我名下客户的方案进度, so that 我能回答客户的询问
20. As a 客户经理, I want to 我无法审核投顾内容, so that 资质要求在系统里是硬的

### 客户

21. As a 客户, I want to 收到的方案是顾问定稿而不是 AI 原稿, so that 我看到的是经过专业人员把关的内容
22. As a 客户, I want to 方案附带免责声明, so that 我理解它的性质
23. As a 客户, I want to 看到方案由哪位顾问出具, so that 我知道该找谁

### 合规

24. As a 合规负责人, I want to 未经审核的投顾内容在任何路径下都无法送达客户, so that 红线不依赖流程自觉
25. As a 合规负责人, I want to AI 原稿永久留存且不可修改, so that 能举证审核是实质性的
26. As a 合规负责人, I want to 只有持有投顾资质的角色能放行, so that 资质约束在服务端生效
27. As a 合规负责人, I want to 每次审核记录审核人、时间与操作, so that 责任可追溯

### 开发者

28. As a 开发者, I want to 审核的暂停与恢复由运行时的中断机制承担, so that 我不必自己实现状态持久化
29. As a 开发者, I want to 对比图与配置饼图共用同一套图表封装, so that 主题与响应式只处理一次

## Implementation Decisions

遵循 `docs/adr/`，核心是 ADR-0005（筛选与推荐之分）、ADR-0006（目标与实际配置）、ADR-0007（LangGraph interrupt）、ADR-0009（护栏测试）。

### 候选池是唯一输入范围

Agent 的排序与阐述只在候选池内进行。候选池已由 `customer-profiling-and-suitability` 完成适当性硬过滤，**Agent 不重新做适当性判断**——它拿到的集合本身就是合规的。

这意味着 Agent 的提示词里不需要也不应该出现适当性规则：让模型去判断一件已经由结构保证的事，只会引入它判断错的可能。

### 内容分类

投顾助手的输出**默认是投顾内容**，必须经审核。这是 Agent 配置里的内容分类默认值（ADR-0007）。

例外：纯事实性的查询（例如「客户张三持有哪些产品」）仍是事实性内容。分类由工具决定——调用了推荐类工具即产出投顾内容，只调用查询类工具则是事实性内容。

### 原稿与定稿

AI 原稿在生成时落库，**此后不可修改**。顾问的编辑产生新的版本记录，放行后的版本即顾问定稿。两者并存，差异可计算——这是举证审核实质性的依据。

顾问定稿是唯一允许送达客户的版本。客户侧接口只能读到定稿，读不到原稿。

### 审核流

用运行时的中断机制实现（ADR-0007）：生成流程在产出原稿后中断，等待人工操作，放行或驳回后恢复。状态持久化由运行时的检查点承担，不自己实现。

放行时**重新校验推荐产品仍在候选池内**——顾问手工编辑可能引入越级产品，这道校验是最后一关。

同一份内容在审核期间加锁，防止并发编辑互相覆盖。

资质校验在服务端：只有理财顾问角色能放行。客户经理能看能评论，不能放行。

### 排序

在候选池内按收益、风险、期限匹配度加权打分排序。**每项的贡献要能被单独读出并展示**——顾问需要判断排序是否合理，一个不可拆解的总分做不到。

注意这与 ADR-0005 不冲突：ADR-0005 约束的是**客户侧**的产品筛选不得排序；此处是**顾问侧**的投顾内容，排序正是它的价值所在。两者的分野即在于送达对象与是否经过审核。

### 集中度风险

基于持仓穿透的结果，识别底层资产在行业维度的集中度，超过阈值时在方案生成时提示。穿透能力在 `product-screening-and-customer-assets` 已实现，此处消费它。

### 对比图

顾问画像面板增加一张**目标配置与实际配置的对比图**，用**成对横向条形**，不用双饼图（ADR-0006）：两个饼图之间人眼无法比较扇区大小，条形可以沿同一基线对齐直读差值——而差值正是这张图存在的理由。

类别顺序在两组之间保持一致，否则对比无从读起。

### 免责声明

一切投顾内容的输出末尾附免责声明。声明是结构的一部分而非模型生成的文本——由模板附加，不依赖模型记得写。

## Testing Decisions

沿用两个 seam。

### Seam 1 — 后端 HTTP 层

核心是护栏测试 5：

- **未经审核的投顾内容无法通过任何客户侧接口读取**（护栏测试 5）
- 客户侧接口读取方案时拿到的是定稿，不是原稿
- 客户经理角色调用放行接口被拒绝
- 顾问编辑时引入越级产品，放行被拒绝
- AI 原稿在顾问编辑后仍可读取且内容未变
- 驳回时理由为空被拒绝
- 同一份内容并发编辑时第二个请求被拒绝或排队
- 推荐结果中的产品全部来自候选池（护栏测试 1 的延续）
- 投顾内容输出末尾含免责声明

审核流的中断与恢复在这个 seam 上测：发起生成 → 断言进入待审状态 → 放行 → 断言产出定稿。不测运行时内部的节点状态。

### Seam 2 — Vue 组件挂载

- 审核页并排渲染原稿与编辑版本
- 放行与驳回入口存在；驳回时理由必填
- 排序依据可展开查看各项贡献
- 对比图的两组类别顺序一致
- 画像置信度低或过期时渲染警示
- 审核页有独立路由，后退可回队列

## Out of Scope

- 方案的 PDF 导出与排版
- 方案发送给客户的通知渠道（站内、短信、邮件）
- 客户对方案的反馈与二次沟通
- 多位顾问的协同审核与会签
- 审核的 SLA 与超时升级
- 图谱增强的推荐（在 `knowledge-graph-and-graphrag`，本 slice 的排序不依赖图谱）
- 净值预测与收益回测

## Further Notes

这份 spec 与 `product-screening-and-customer-assets` 构成一对：同样是「给客户看产品」，客户侧强制不排序、不评价（ADR-0005），顾问侧允许排序、必须阐述。两者看起来矛盾，实则是同一条合规线的两侧——差别在于送达对象是否经过持证人员。实现时如果发现两边在共用同一个排序函数，那说明边界已经破了。

审核流最容易做成橡皮图章：加一个「已审核」布尔字段、顾问点一下就置真。那样系统上合规、举证时站不住。原稿与定稿并存、差异可计算，才是这条红线真正的实现方式。
