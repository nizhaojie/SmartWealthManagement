# 客户充值：资金账户的第一个入口

Status: ready-for-agent

前置：`operation-advice-and-customer-trading`（资金账户与可用余额 `#01`、客户侧受理 `#02`/`#03`、交易成为风控输入 `#04`）、`onboarding-funding-account-and-target-allocation`（开户即建资金账户、余额 0）

**本 slice 新增一条 ADR（0023），并推翻两处已实现的既有决定**（清单见下表与 `Further Notes`）：

| 被改的既有决定 | 出处 | 改动内容 |
|---|---|---|
| 「种子**给足余额**，**不做入金**」（Q20） | `operation-advice-and-customer-trading` 的 Q20、Implementation Decisions 的「资金账户与余额」、Out of Scope 第一条、`docs/demo-script.md:43` 与 `:124-125` | 入金成为客户自助的一条资金操作，余额因此第一次有了入口。种子仍是余额的初始值，但「余额只能减少」不再成立；演示脚本、注释与断言里那一批「不做入金」的话都要跟着改。 |

## Problem Statement

**资金账户只有出口，没有入口。** `available_balance` 的四个写入点全部是「减少」或者「不是客户能发起的」：申购扣减（`backend/app/order_acceptance/service.py:305`）、转账扣减（`:422`）、赎回增加（`:356`，前提是先有持仓）、种子对齐（`backend/app/db/seed.py:576`，只在装库时跑）。客户在应用里没有任何动作能让余额变大。

两个后果都能在今天的代码里指出来：

1. **新开户的客户永久不能动钱。** `onboarding-funding-account-and-target-allocation` 让开户建出余额为 0 的资金账户，而申购与转账都要求余额大于 0、他也没有持仓可赎。他能登录、能看资产页、能做完风评、能看到产品清单，然后被「可用余额不足」永久挡住——**这是一条死路，不是一次拒绝**。演示与测试绕过它的是直接写库的助手（`backend/tests/test_end_to_end_customer_journey.py:200-206` 的 `_fund_customer_account`、`test_operation_advice_decision.py:140-146` 的 `_fund_account`、`test_operation_advice_draft.py:75` 的 `SEEDED_BALANCE`），产品里没有对应路径。
2. **演示里的余额是一次性的。** Q20 用「种子给足」把这个问题挡在演示之外，代价是余额花完就要换一位客户重来（`docs/demo-script.md:44`），而「这位客户的钱是怎么多起来的」在应用里没有答案。

根因不是校验太严（那些校验都是对的），而是**资金账户缺一个入口**。

## Solution

**客户在「交易」页自助充值**：钱从机构之外进入自己的资金账户。它是最小形态的入金——受理通过即入账、不记钱的来源、由客户自助发起、不经审核。

**它和转账一样是一笔既成事实。** 充值没有产品，因此落在自己的表 `fin_deposit` 里（延续 ADR-0019 的分表理由），客户却在同一张合并的「交易流水」里看到它——合并读从两表升为**三表扇入**。它也照常是一笔交易事件：受理侧落库后调用既有的 `submit_transaction_event`，风控因此**第一次看得见入金**。

**受理侧只拦两条：金额必须为正、资金账户必须存在。** 不设限额、不要风评。大额入金不在受理侧拒收——反洗钱的规范动作是**申报与预警**，5 万申报阈值本来就在规则引擎里（`backend/app/risk_monitoring/fields.py:29`）。收下它的是 13 条只建在金额、笔数与时段上的规则，其中 R009（七日频繁小额）与 R015（疑似拆分规避申报阈值）恰恰是入金最典型的形态。

**新开户的客户因此从「永久冻结」变成「充值即可交易」。** 这是本 slice 真正的验收标准：客户端充值一笔 → 余额涨 → 风控侧出现对应预警。

## User Stories

### 客户

1. As a 客户, I want to 把钱从机构外转入我的资金账户, so that 我不必等一笔赎回才有钱可用
2. As a 开户后余额为 0 的客户, I want to 靠自己把余额变成能交易的钱, so that 我不必等谁给我打款
3. As a 客户, I want to 充值后立刻看到余额变大, so that 我知道现在买得起多少
4. As a 客户, I want to 在我自己的交易流水里看到充值, so that 核对资金流入时不必去别处找
5. As a 客户, I want to 充值失败时知道是哪一种原因, so that 我知道是金额不对还是我没有资金账户

### 风控专员

6. As a 风控专员, I want to 客户的每一笔入金也过规则引擎, so that 大额与分散入金不会成为监测盲区

### 合规负责人

7. As a 合规负责人, I want to 大额入金被记录与分级而不是被拒收, so that 申报口径不靠拒绝客户来实现
8. As a 合规负责人, I want to 充值的校验只落在受理侧、入海口保持窄口, so that 内部补录仍然能修复数据

### 开发者

9. As a 开发者, I want to 充值复用既有的交易事件管线与无产品分支, so that 风控不出现第三条输入路径
10. As a 开发者, I want to 客户侧流水的合并读被写成一个可照做的模式, so that 加第四类记录时不会再有人漏掉一张表

## Implementation Decisions

### 领域语言

`CONTEXT.md` 已就地更新：新增 **充值** 词条，并连带修订三条既有定义——**可用余额**（「赎回与充值增加它」）、**交易流水**（四类）、**转账**（「是交易流水里没有产品的两类之一」）。

充值**不是**投顾内容（不经审核），也**不是**「转账的反向别名」：转账有对手方，充值不记来源（Q2）。

### 充值的事实

新表 `fin_deposit`，与 `fin_transfer`（迁移 `0025`）同形：`deposit_no`、`customer_id`、`amount Numeric(18,2)`、`create_time`；`CHECK amount > 0`；索引 `ix_fin_deposit_customer_id`。**没有 status 列**——受理通过即入账（Q5）。

流水号前缀 `DP`，与 `TR` 同一形状：两类记录会并排出现在客户的同一个列表里，形状不同会让人以为它们不是一种东西。

### 受理

校验两条：金额 > 0、资金账户存在。校验、落库与余额变动在同一个会话里，且全部在落库之前（ADR-0018）。余额只增：`available_balance += _money(amount)`，因此 `CHECK available_balance >= 0` 恒成立。

入口 `POST /api/customer/transactions/deposit`，请求体 `{amount}`，客户标识由凭证推导（既有约定，请求体里没有这个字段）。返回形状与申赎一致：`{transaction, available_balance}`。

随后调用 `submit_transaction_event` 的**无产品分支**（`alerting._submit_recorded_fact`），传 `transaction_id` 与 `transaction_no`——「先事务性落库」这一步仍然发生，只是那一行在 `fin_deposit` 里。

### 客户侧流水

合并读从两张表升为三张（Q3）：新增 `_deposit_rows()`，排序键的来源序号加 `_FLOW_DEPOSIT=2`（既有 `_FLOW_TRANSACTION=0` / `_FLOW_TRANSFER=1`），`_serialize_flow` 对充值行给出全为 `None` 的产品位与对手方位，类型筛选 `transaction_type=充值` 只读这一张表。**仍然不分页**（既有口径）。

界面侧因此**表格零改动**：`TransactionHistory.vue:14-23` 已经定了规矩——「缺失的一项显示为「—」，不编造、也不留空单元格」。要改的只有 `:11-12` 那句「转账是唯一的没有产品、有收款人的那一类」。

### 风控接入

- `alerting.TRANSACTION_TYPES` 加「充值」，并**重写 `alerting.py:93-95` 的注释**。那段注释现在是「转账是点名场景，但规则只建在金额上，因此可以收；其他类型收进来只会让一批规则永不命中——静默漏报」，加了充值它就会变成第三句不成立的话。准确的口径是：**类型分支只活在 7 条规则里**（R011–R014 按方向取值或配对、R016 产品维、R019 越级、R020 大额赎回），其余 **13 条**只建在金额、笔数与时段上（R001–R010、R015、R017、R018），因此转账与充值都收得下。
- **不新增字段、不新增规则**（Q9）。`OPPOSITE_TRANSACTION_TYPES` 不动：把「充值↔转账」配对会把「把买进来的钱转出去」误判成对倒；「入金后短期内转出」是一条新的复合字段，属于另一件事。
- **`_history_events` 必须读第三张表**（`alerting.py:166-203`）：它现在读 `fin_transaction` 与 `fin_transfer`，漏掉 `fin_deposit` 不会报错，只会让窗口与累计类规则**一起少算**入金，而且从结果上完全看不出来。要加 `_deposit_event()`（与 `_transfer_event()` 同形），并把自身那一行按「事件来自哪张表」排除——三张表的 id 各自从 1 开始。
- 充值的预警**不填** `RiskAlert.transaction_ids`（`_fin_transaction_id` 已按 `product_id is None` 返回 `None`），因此预警详情的「关联交易」为空、金额与类型仍在命中依据里。**`AlertDetailPage.vue` 零改动**。
- **不新增护栏条目**：充值同样只走受理侧、不碰入海口，ADR-0009 的护栏 7（交易受理校验不可绕过）的 seam 已覆盖它，新断言挂在既有文件里。

### 界面

「交易」页加第四个同构卡片：`data-testid="deposit-form"`、字段「金额（元）」、按钮 `name="submit-deposit"`，**追加在既有三张之后**——「买 → 卖 → 出」的顺序不动，新类型追加对既有测试选择器扰动最小。流水筛选的 `TRANSACTION_TYPES` 加「充值」。

内部端无改动：客户经理没有客户流水页，预警详情见上一条。

### 种子与演示

种子不动（Q11）。`docs/demo-script.md` 第四幕改成「余额不足被拒 → 充值 → 同一笔转账成功」，§二「上台前必须知道的三件事」的第 2 条与那一幕的台词一起改。

## Out of Scope

- 钱的来源建模（Q2）：没有付款人、没有绑定银行卡、没有渠道
- 受理侧限额：单笔上限、单日累计、冷静期（Q7：大额交给风控）
- 内部代客入金（Q6：只有客户自助；人工场景由内部补录覆盖）
- 到账的中间态（Q5：受理通过即入账，不做「待入账 / 处理中」）
- 充值的风控规则扩展（如「入金后短期内转出」「多笔小额入金凑整」）
- 多币种、冻结、对账、利息、资金收益
- 充值的手续费与费率
- 语义视图 `va_transaction_stat` 纳入充值（转账也不在，口径一致）
- 与外部银行的真实对接
- 充值记录出现在内部端（客户经理没有流水页；预警详情按上面）

## Further Notes

- **本 slice 补的是资金账户的入口。** 出口一直有（申购、转账），入口没有——所以「余额不足」第一次变成可自救的状态，而不是换一位客户重来。
- **三处静默失败面要一起看**，它们的共同点是**都不会报错**：客户侧流水的合并读（漏一张表就是整行消失）、`_history_events` 的三表读法（漏一张表就是所有算子一起少算）、`alerting.py:93-95` 的注释（不改就是一句已经失效的话）。
- **`transaction_id` 这个名字在三张表之间复用**：无产品事件的它是 `fin_transfer.id` / `fin_deposit.id`，有产品时是 `fin_transaction.id`。既有设计如此，本 slice 沿用；不要在 `transaction_ids` 里混填——`_fin_transaction_id` 已经用 `product_id is None` 挡着，别把这个判据挪走。
- **「不做入金」是一句话，但它写在七个地方**（两份 spec 的结论与 Out of Scope、演示脚本两处、四个源码/测试文件的注释）。Q20 的推翻必须逐处交代，否则下一个人会拿旧注释当准。清单在 `#04`。
- **新开户客户从「永久冻结」变成「充值即可交易」。** `test_a_newly_opened_customer_has_a_funding_account_with_no_money` 的语义不变（余额仍是 0），但它不再是终态——那条断言现在证明的是「没钱」而不是「没救」。
- **充值之后的余额增长会让几处既有文案松动**：`CustomerAdviceSection.vue` 的「可用余额不足以申购候选池内的任何产品」不再必然持续成立（客户可以先充值）。这不是缺陷，但讲解时要知道这条路径已经存在。
