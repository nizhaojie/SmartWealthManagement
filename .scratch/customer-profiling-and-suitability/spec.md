# 客户画像、风险评测与适当性匹配

Status: ready-for-agent

前置：`internal-workbench-shell`（内部工作台外壳）

## Problem Statement

理财顾问要判断一位客户能买什么、适合什么，现在靠翻资料和凭经验。他需要知道客户的风险承受等级、投资经验、资产规模、配置意愿——这些信息散在风评问卷、持仓记录和历次对话里，没有一个地方能一次看全。

更要命的是适当性：监管要求客户的风险承受等级必须与产品风险等级匹配，越级销售是硬违规。现在这道校验靠人记住规则并在每次推荐时自觉执行——只要有一次疏忽，就是一起适当性违规。

还有一类隐性风险：一份两年前做的风险评测，客户的情况早就变了，但系统仍在拿它当依据。或者一个 17 岁的申请人、一个无收入且资产不足万元的客户，按规则本该走特批却被正常放行。

## Solution

系统为每位客户维护一份**客户画像**：风险承受等级、投资经验、收入区间、资产规模、目标配置、产品偏好，每个标签都带**置信度**与来源，读取方能知道这份画像有多可信、有多新鲜。

风险承受等级由 16 道评测题计算得出，落在 C1 到 C5。画像研判引擎另有一套四维度加权打分，把基础属性、投资经验、风险偏好、行为异常综合成等级——两者互为印证。

**适当性匹配实现为检索层的硬过滤**（ADR-0005 已确立的同一原则）：Cn 客户的候选池里根本不出现 Rn 以上的产品，而不是先列出来再置灰，也不是交给模型去判断。越级产品不进入候选池，因此不存在「模型这次没听话」的可能。

几条硬性门槛直接熔断：年龄不足 18 或超过 80 需人工审核；无收入且资产不足万元只允许最低两档产品；风评过期则冻结画像权限并提示重新评估。

## User Stories

### 客户

1. As a 客户, I want to 在客户端作答风险评测问卷, so that 我能知道自己的风险承受等级
2. As a 客户, I want to 问卷能中途保存, so that 我不必一口气答完 16 道题
3. As a 客户, I want to 提交后立刻看到我的等级与它的含义, so that 我理解这个结果意味着什么
4. As a 客户, I want to 看到我的评测结果有效期, so that 我知道什么时候需要重做
5. As a 客户, I want to 在评测过期前收到提示, so that 我不会在想买产品时才发现权限被冻结
6. As a 客户, I want to 看到我自己的风险承受等级结论, so that 我理解为什么某些产品我看不到
7. As a 客户, I want to 看不到我的画像内部细节（置信度、研判过程、服务记录）, so that 这些内部信息不越过客户可见视图的边界

### 理财顾问

8. As a 理财顾问, I want to 查看一位客户的完整画像, so that 我在沟通前就掌握他的情况
9. As a 理财顾问, I want to 看到画像每个标签的置信度与来源, so that 我知道哪些信息可靠、哪些只是客户随口一说
10. As a 理财顾问, I want to 看到画像的计算时间, so that 我知道自己看的是不是过时的数据
11. As a 理财顾问, I want to 看到客户的风险承受等级是怎么算出来的（四个维度各自得分）, so that 我能向客户解释这个结论
12. As a 理财顾问, I want to 看到客户的历次风险评测记录, so that 我能看出他的风险偏好是否在变化
13. As a 理财顾问, I want to 手工修正某个画像标签并填写理由, so that 我在访谈中获得的信息能进入系统
14. As a 理财顾问, I want to 我的修正被记为高置信来源, so that 它不会被一次 AI 对话提取轻易覆盖
15. As a 理财顾问, I want to 看到标签冲突的历史记录, so that 我知道这个标签曾经被改过、改前是什么
16. As a 理财顾问, I want to 看到某位客户因硬性门槛被熔断的提示与原因, so that 我不会白忙一场

### 风控与合规

17. As a 合规负责人, I want to 越级产品根本不进入候选池, so that 适当性违规在结构上就不可能发生
18. As a 合规负责人, I want to 适当性校验发生在服务端且无法被前端参数绕过, so that 它是真的硬约束
19. As a 合规负责人, I want to 每次适当性判定都留下记录, so that 事后能举证当时依据的是哪一份评测
20. As a 合规负责人, I want to 风评过期的客户被冻结画像权限, so that 系统不会拿两年前的结论做今天的判断
21. As a 合规负责人, I want to 年龄与资产的硬性门槛强制人工介入, so that 边界客户不被自动放行

### 开发者

22. As a 开发者, I want to 画像读取先查缓存未命中再回源并回填, so that 高频读取不每次都打数据库
23. As a 开发者, I want to 缓存不可用时系统降级为直连数据库而不是报错, so that 缓存是优化不是依赖
24. As a 开发者, I want to 置信度计算是一个纯函数, so that 它易于测试且结果可复现
25. As a 开发者, I want to 适当性规则是一处定义、多处引用, so that 不会出现两个地方各写一遍规则然后逐渐漂移

## Implementation Decisions

遵循 `docs/adr/`，特别是 ADR-0004（身份域）、ADR-0005（硬过滤原则）、ADR-0006（目标配置与实际配置）、ADR-0009（护栏测试）。

### 等级表示

风险承受等级在库中、接口中、逻辑中一律是 `C1`–`C5`；产品风险等级一律是 `R1`–`R5`。中文名称只在展示层由映射表生成（见 `CONTEXT.md`）。适当性比较是序数比较：Cn 客户可持有 R1 至 Rn。

### 风险评测

16 道题，每题四个选项对应不同分值，总分映射到 C1–C5 五档。题目内容需自行构造，覆盖收入、投资经验、风险承受力、投资目标四个维度。

每次评测写入评估记录表并更新画像的等级与分值。**历次记录全部保留**，不覆盖——顾问要能看出客户风险偏好随时间的变化。

评测有有效期，过期即冻结画像权限。

### 画像研判引擎

四维度加权：基础属性 25%、投资经验 25%、风险偏好 30%、行为异常 20%，加权总分映射到 C1–C5。

四个维度各自的得分要能被单独读出并展示——顾问需要向客户解释结论是怎么来的，一个不可拆解的总分做不到这件事。

### 硬性门槛

门槛判断**先于**加权打分，命中即熔断，不再计算等级：

- 年龄 < 18 或 > 80 → 标记需人工审核
- 无收入且资产 < 1 万 → 仅允许 R1–R2
- 评测过期 → 冻结画像权限，提示重新评估

熔断结果与原因要能传到界面，顾问看得见为什么这位客户走不通正常流程。

### 置信度

每个标签带一个 0 到 1 的置信分。来源决定初始值（风评问卷最高、AI 对话提取次之、客户自述再次、默认值最低），证据累积带来增益且有上限，冲突带来惩罚，时间带来衰减。计算是纯函数，边界钳制在 0 到 1。

理财顾问的手工修正记为高置信来源，不会被一次 AI 对话提取覆盖。

### 标签冲突

新旧标签冲突时：来源置信度高的覆盖低的；来源相同则新数据覆盖旧数据。**冲突记录必须保留**用于审计——顾问要能看到这个标签曾经是什么、什么时候被什么来源改掉的。

### 适当性硬过滤与候选池

适当性是检索层的过滤条件，不是结果的后置校验。产品查询在数据访问层就带上等级约束，越级产品不进入结果集——因此不存在「查出来了但没展示」的中间状态，也就不存在被参数绕过的可能。

过滤后剩下的集合即**候选池**，是后续投顾推荐的唯一输入范围。

### 缓存

画像读取走 Cache-Aside：先查缓存，未命中查库并回填。缓存不可用时直连数据库，恢复后自动回填——缓存是优化，不是依赖。

### 客户可见边界

客户能看到的只有自己的风险承受等级结论与评测有效期。置信度、四维度得分、研判过程、冲突记录、服务记录都在客户可见视图之外，客户侧接口不返回这些字段。

## Testing Decisions

沿用两个 seam。

### Seam 1 — 后端 HTTP 层

核心是护栏测试 1：

- **C1 客户的候选池里不出现 R2 及以上产品**（护栏测试 1）
- C3 客户能拿到 R1–R3，拿不到 R4、R5
- 构造请求参数试图绕过等级约束时，服务端仍不返回越级产品
- 16 题全部作答后返回正确的等级
- 年龄 17、年龄 81、无收入且资产不足、评测过期四个边界各自触发对应熔断
- 画像标签冲突后，冲突记录可查且旧值仍在
- 顾问修正的标签不被后续 AI 对话提取覆盖
- 客户侧画像接口不返回置信度、四维度得分与冲突记录
- 缓存不可用时画像仍可读取

置信度计算作为纯函数单独测试——它没有外部依赖，直接测输入输出，不经过 HTTP。这是这份 spec 里唯一一处低于 HTTP 层的断言，因为它本身就是一个无依赖的纯计算。

### Seam 2 — Vue 组件挂载

- 画像面板渲染出每个标签的置信度与来源
- 画像的计算时间可见
- 四维度得分可展开查看
- 熔断状态渲染出原因而不是空白
- 问卷中途保存后重新进入，已答题目仍在

## Out of Scope

- 产品推荐与排序（候选池的消费方在 `advisory-agent-and-review-flow`）
- 产品筛选与产品列表页（在 `product-screening-and-customer-assets`）
- 实际配置的计算与展示（需要持仓聚合，在 `product-screening-and-customer-assets`）
- 从对话中自动提取画像标签的 LLM 抽取链路（本 slice 只实现标签的写入、冲突与置信度机制，自动抽取在 `memory-confidence-and-integration`）
- 置信度的综合重排与周期校准（在 `memory-confidence-and-integration`）
- 行为异常维度所依赖的交易频率与集中度计算的完整实现（本 slice 用持仓与交易的简单聚合）

## Further Notes

这份 spec 里最容易做错的是把适当性写成「查出来再过滤」——那样在代码上更自然，但它留下了一个中间状态：越级产品曾经出现在某个变量里。一旦后续某处忘记过滤，或者某个接口直接返回了那个中间结果，就是一次适当性违规。写成检索层的约束，这个中间状态从不存在。

评分表里「适当性违规 -10」是仅次于「项目无法启动」的扣分项，而它恰好是最容易被一次「优化」无意破掉的那类约束——所以护栏测试 1 在这份 spec 里不是可选项。
