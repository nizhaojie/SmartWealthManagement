# 地基与客服链路端到端

Status: ready-for-agent

## Problem Statement

客户想了解一款产品的要素、一条政策的含义，或者一个常见问题的答案，目前只能打客服热线排队。等到了坐席，不同的人给出的口径还未必一致。而这类问题绝大多数本来就有标准答案——答案写在产品手册、政策文件和 FAQ 里，只是没有人能在几秒钟内把它找出来、说清楚，并指明出处。

更麻烦的是相反的情形：一个听起来很流畅、实际上没有任何依据的回答。在金融场景里，客户无法分辨「系统查到了」和「系统编了一个」，而这两者的后果差别极大。

与此同时，本仓库目前是空的——没有工程骨架、没有数据库、没有任何可运行的东西。在任何业务功能能被演示之前，需要先有一条真正跑通的链路，来验证后续所有功能都要依赖的那几条基础契约。

## Solution

客户在客户端登录后向智能客服 Agent 提问，回答逐字流式呈现。回答中的每个论断都挂着可点击的引用角标，点开能看到来源文档标识与段落位置。检索不到依据时 Agent 不作答，而是明确说明并给出人工渠道——**宁可不答，不可编造**。

Agent 只产出事实性内容：已披露的产品要素、公开政策条款、FAQ 答案。它的工具集里不存在推荐类能力，因此不需要审核即可送达客户。

这一刀同时把地基铺好：monorepo 骨架、六个容器、11 张表、统一响应格式、两个身份域的凭证签发与校验、分级日志与链路追踪。这些不是为本 feature 服务的附属品，而是后续每个 Agent 都要落在上面的东西——先用一条最薄的真实链路把它们验证一遍，比先写四份接口文档再联调要可靠。

## User Stories

### 客户

1. As a 客户, I want to 用账号和密码登录客户端, so that 我能看到属于我自己的内容
2. As a 客户, I want to 登录失败时看到明确但不泄露信息的提示, so that 我知道是账号错了还是系统故障，而攻击者无法靠提示区分账号是否存在
3. As a 客户, I want to 向智能客服 Agent 用日常语言提问, so that 我不必学会某种检索语法
4. As a 客户, I want to 回答逐字出现而不是等几秒钟后整段弹出, so that 我知道系统在工作而不是卡住了
5. As a 客户, I want to 回答里每个论断都带一个引用角标, so that 我能判断这个说法是否有依据
6. As a 客户, I want to 点开角标看到来源文档与段落位置, so that 我能自己去核对原文
7. As a 客户, I want to 系统在检索不到依据时明确说它不知道, so that 我不会被一个听起来可信但其实是编造的答案误导
8. As a 客户, I want to 在系统答不上来时拿到人工客服渠道, so that 我的问题仍有出路
9. As a 客户, I want to 连续追问时系统记得刚才聊过什么, so that 我不必每句话都把前提重复一遍
10. As a 客户, I want to 问一个与理财无关的闲聊问题时被友好地引导回业务, so that 我不会以为系统坏了
11. As a 客户, I want to 主动登出, so that 在共用设备上我的会话不会留给下一个人
12. As a 客户, I want to 重新登录后是一段全新的对话, so that 昨天的上下文不会莫名其妙地影响今天的回答
13. As a 客户, I want to 我的会话在长时间不操作后失效, so that 忘记登出不至于让别人接着用

### 知识库维护者

14. As a 知识库维护者, I want to 上传 txt / md / docx 文档入库, so that Agent 能基于最新资料回答
15. As a 知识库维护者, I want to 上传时指定知识类型（FAQ / 产品 / 政策）, so that 检索能落在正确的范围里
16. As a 知识库维护者, I want to 查看已入库文档的列表与状态, so that 我知道知识库里现在有什么
17. As a 知识库维护者, I want to 删除一份文档时向量、元数据与原始文件被一并处理, so that 不会出现「文档删了但 Agent 还在引用它」
18. As a 知识库维护者, I want to 直接检索知识库看命中了什么, so that 我能在不走对话的情况下判断检索质量
19. As a 知识库维护者, I want to 40 组现有 FAQ 被导入作为初始知识库, so that 系统第一次启动就能回答常见问题

### 安全与合规

20. As a 合规负责人, I want to 客户凭证打到任何内部接口一律无效, so that 身份域的隔离不只是前端路由上的约定
21. As a 合规负责人, I want to 未携带凭证的请求无法访问任何业务数据, so that 不存在忘记加守卫的裸奔接口
22. As a 合规负责人, I want to 密码以不可逆方式存储, so that 数据库泄露不等于账号泄露
23. As a 合规负责人, I want to 每次 Agent 调用都留下永久记录（使用者、问题、最终答案、引用文档、内容分类）, so that 事后能举证系统当时说了什么、依据是什么
24. As a 合规负责人, I want to 日志与归档中的身份证号、手机号、姓名、银行卡号被脱敏, so that 留痕本身不成为新的泄露源

### 开发者

25. As a 开发者, I want to 一条命令起全部依赖容器, so that 我不必手工装六个服务
26. As a 开发者, I want to 所有容器端口避开默认值, so that 它们不与我机器上其他项目冲突
27. As a 开发者, I want to 一份环境配置模板说明每个变量的含义与取值, so that 我不必读代码才知道该填什么
28. As a 开发者, I want to 在没有 LLM API key 的情况下也能把项目跑起来并跑通测试, so that 我不会被一个外部依赖堵死
29. As a 开发者, I want to 数据库结构由可重复执行的迁移脚本管理, so that 我不必手工同步建表语句
30. As a 开发者, I want to 一份测试数据集（测试客户、产品、持仓、交易）随迁移一起灌入, so that 我不必为了看一眼界面先手工造数据
31. As a 开发者, I want to 所有接口返回同一种外层结构, so that 前端只写一次拆包与错误处理
32. As a 开发者, I want to 每个响应带链路追踪标识, so that 我能把前端看到的一次失败对应到后端日志的某一行
33. As a 开发者, I want to 日志按级别分文件, so that 排查错误时不必在正常流水里翻找
34. As a 开发者, I want to 两个前端共享的 HTTP 客户端与格式化逻辑只写一份, so that 改一处不必同步两遍
35. As a 开发者, I want to 有东西阻止我把业务语义放进共享包, so that 客户端的产物里不会混入内部逻辑

## Implementation Decisions

遵循 `docs/adr/` 中已确立的决定。本 slice 直接受 ADR-0003（monorepo 与 shared 边界）、ADR-0004（身份域拆表）、ADR-0007（LangGraph 运行时）、ADR-0008（fake provider 与回放模式）、ADR-0009（护栏测试）约束。

### 工程骨架

pnpm workspace，四个包：后端（Python，不在 workspace 内但同处仓库）、客户端应用、内部工作台应用、共享包。内部工作台在本 slice 中只需要存在到「能验证客户凭证被拒绝」的程度，不实现任何业务页面。

共享包只允许放与业务语义无关的东西：HTTP 客户端、响应拆包、错误码映射、日期与金额格式化、主题令牌。风控规则字段、预警分级、审核流状态、画像权重一律不许进（ADR-0003）。

### 依赖与环境

六个容器：MySQL、Redis、Milvus 及其依赖 etcd 与 MinIO、Neo4j。端口全部避开默认值。Neo4j 在本 slice 中只需起得来，不写入数据。

环境变量已在 `backend/.env.example` 中定稿，Chat 与 Embedding 分开配置，两者的 provider 取值只有 `fake` 与 `openai_compatible`（后者指协议而非厂商）。未配置 key 时默认 `fake`，此时全部功能仍可运行，只是回答内容是确定性假数据。

`EMBEDDING_DIMENSION` 写入 Milvus 集合后不可更改，建集合前必须确认。

### 数据模型

11 张表。用户表按身份域拆成客户表与员工表（ADR-0004），两者没有共同父表，也不存在同一人既是客户又是员工的情况。

其余表沿用需求文档的设计：客户画像、产品、交易流水、持仓、风险评估记录、预警、工单、会话归档、知识元数据。本 slice 只实际读写其中的客户表、员工表、知识元数据表与会话归档表，其余建表但不使用。

风险承受等级字段存 `C1`–`C5`，产品风险等级存 `R1`–`R5`。中文名称（保守型等）只在展示层由映射表生成，不入库（见 `CONTEXT.md`）。

### 认证

JWT，access token 短时效配合 refresh token。客户与员工使用不同的 token 受众，校验时受众不匹配一律拒绝——这是身份域隔离的实现点，不依赖任何路由层判断。密码以自适应哈希算法存储。

### 知识入库

文档解析支持 txt、md、docx。分块 512 token、overlap 64 token，保留标题层级作为元数据。每份文档先在知识元数据表建记录，再生成向量入 Milvus，向量的元数据关联该记录标识，原始文件存 MinIO。

删除是三处联动：元数据标记过期、Milvus 向量删除、MinIO 文件标记归档。这保证不会出现「文档已删但 Agent 仍在引用」。

### 检索与生成

检索返回 TopK 片段及相似度分数。**最高分低于阈值时不进入生成环节**，直接返回兜底话术与人工渠道——这条先于 LLM 调用发生，因此不依赖模型是否听话。

生成时把检索片段注入系统提示词，要求每个论断挂引用。引用是结构化数据，不是回答文本里的字符串：它至少包含文档标识与段落位置，前端据此渲染角标并支持点开查看。模型输出的引用标识必须能在本次检索结果中找到，找不到的引用在返回前剔除。

### Agent 运行时

LangGraph 单运行时（ADR-0007），本 slice 只装配智能客服 Agent 一份配置：提示词、工具集（只含检索类工具，不含任何推荐能力）、短期记忆策略、内容分类默认值为事实性内容。

意图分为产品咨询、政策解读、FAQ、闲聊、转人工五类。前三类走检索，闲聊走直接生成并引导回业务，转人工返回固定话术。

### 会话与记忆

短期记忆存 Redis，键按会话标识组织，列表结构，滑动过期，总 token 超预算时截断最旧的消息。会话不跨登录延续：重新登录即新会话。

会话结束后完整对话流水写入归档表，写入前脱敏。工具调用记录一并留存。

### 流式输出

SSE，`text/event-stream`。**流式只是传输方式，不是决策环节**：兜底判断、引用剔除、内容分类都在开始推流之前完成，推流过程中不再改变回答的性质。

### 前端

两个应用各自独立登录、独立构建。Element Plus 默认主题，不做视觉定制——视觉留到 roadmap 收尾阶段统一重构。

受合规约束的组件只吃样式、不吃语义（ADR-0009）：引用角标与面板保留自有 DOM 结构与全部 ARIA 属性，Element Plus 只提供外层容器。

### 统一契约

所有接口返回同一外层结构，含业务状态码、描述、数据体与链路追踪标识。错误码沿用需求文档的定义（参数、认证、权限、资源、服务内部，以及 LLM 调用失败、检索无结果等业务码）。

## Testing Decisions

好测试只断言外部可观察的行为——请求进去、响应出来、界面上看得见的东西。不断言某个函数被调用了几次、某个中间结构长什么样。检索用了哪种索引、提示词怎么拼、LangGraph 有几个节点，都可以随时重写而不应该弄红任何测试。

测试落在两个 seam，不新增第三个。

### Seam 1 — 后端 HTTP 层

测试通过 ASGI 应用打真实端点，走真实路由、中间件与凭证校验。

存储用真实容器的独立测试库与测试集合（环境变量中已预留），**不打桩**——因此这个 seam 覆盖真实的 SQL 行为与真实的向量检索行为。LLM 与 Embedding 用 `fake` provider，它是 ADR-0008 已决定存在的产品能力，不是为测试新造的接缝，于是模型输出是确定性的。

这个 seam 上要断言的行为：

- 登录成功返回凭证；登录失败不泄露账号是否存在
- **客户凭证打到内部接口返回 401 或 403**（护栏测试 2）
- 无凭证请求任何业务接口被拒
- 提问返回的回答带结构化引用，且每条引用能在检索结果中找到对应片段
- 检索最高分低于阈值时返回兜底话术而非生成内容，且不发生 LLM 调用
- 多轮提问时上下文被保留；重新登录后上下文不存在
- 文档上传后可被检索到；删除后不再被检索到
- 归档记录中的身份证号、手机号、姓名、银行卡号已脱敏
- SSE 端点返回正确的内容类型，且流的最后包含完整回答与引用

### Seam 2 — Vue 组件挂载

挂载页面组件，只在 HTTP 客户端处打桩。断言：

- 带引用的回答渲染出可点击角标，点击后来源信息可见
- 兜底回答渲染出人工渠道，且**不**渲染引用角标
- 未登录时访问受保护页面被导向登录页
- 引用面板保留其 ARIA 语义（未被 Element Plus 组件覆盖）

### 构建期检查

共享包的依赖图中不得出现业务语义标识（护栏测试 6）。这不是运行时测试，是构建流程的一步，失败即中断构建。

### Prior art

本仓库是新的，没有既有测试可参照。隔壁 `../SmartWealthManagementSystem/` 有同类型的前端不变量测试可作为写法参考，但它是 React + Testing Library，本项目是 Vue，只借鉴断言的粒度与选取角度，不借鉴具体实现。

## Out of Scope

- 投顾助手、风控监测、数据分析三个 Agent 及其全部能力
- 客户画像、风险评测问卷、适当性匹配、候选池
- 产品筛选与产品列表页
- Neo4j 图谱构建、GraphRAG 融合检索、图谱可视化（本 slice 只要求容器起得来）
- 风控规则引擎、预警、工单
- 投顾内容的审核流、AI 原稿与顾问定稿
- 中期与长期记忆的完整实现（本 slice 只做短期记忆）
- 置信度体系与周期校准
- 多 Agent 事件通信
- 内部工作台的任何业务页面
- 前端视觉重构（明确留到 roadmap 收尾阶段）
- 真实支付通道、真实统一身份认证、短信验证码
- 移动端原生应用、K8s 部署、CI/CD

## Further Notes

`EMBEDDING_DIMENSION` 是本 slice 中唯一一个改起来代价陡增的值：向量灌入 Milvus 集合后想改维度，必须删集合重灌全部内容。当前定为 1024，对应通义 text-embedding-v3 的默认维度。动手建集合之前确认一次。

`fake` provider 在本 slice 中承担双重角色：既是测试的确定性基础，也是答辩现场的兜底路径（ADR-0008）。因此它的输出质量不能敷衍——它至少要产出结构完整、带合法引用的回答，否则回放模式在演示时会露馅。

需求文档 Phase 1 的验收标准写着「数据库 10 张表全部创建成功」，本项目因身份域拆表是 11 张（ADR-0004），答辩时需要解释一句。
