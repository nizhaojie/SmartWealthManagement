# 知识图谱与 GraphRAG

Status: ready-for-agent

前置：`advisory-agent-and-review-flow`（投顾助手的排序与阐述）

## Problem Statement

有一类问题，纯向量检索答不好：「客户 A 和客户 B 有什么共同持仓」「张三的持仓集中在哪些行业」「这位基金经理还管着哪些产品，客户是不是在他身上押得太重」。这些问题的答案不在任何一段文本里——它藏在实体之间的关系中，要顺着「客户 → 持仓 → 产品 → 行业」这样的路径走几跳才能得到。

向量检索能找到语义相近的段落，但它不理解「持有」「属于」「管理」这些关系，也无法沿着关系多跳。结果是这类问题要么答不上来，要么答得含糊。

投顾场景尤其需要这个：识别行业集中度、发现基金经理层面的隐性集中、找到相似客户的配置参考——都要求沿关系遍历。

## Solution

用 Neo4j 承载客户、产品、风险等级、行业、基金经理之间的关系，支持多跳查询。图谱是 **MySQL 的投影读模型**（ADR-0002）：MySQL 仍是唯一写入源，图谱由 MySQL 单向同步生成，只读，脏了就全量重建。

**GraphRAG** 在既有的向量检索之上增加一条图谱路径：从问题中识别实体，用实体去图谱做多跳查询拿到关联实体与关系路径，再把图谱结果与向量结果融合排序后一起注入模型。模型于是同时拿到文本语义与结构关系。

投顾工作台增加一张**图谱关系图**，让顾问直观看到一位客户的持仓网络——哪些产品、属于哪些行业、由谁管理、在哪里形成了集中。

## User Stories

### 理财顾问

1. As a 理财顾问, I want to 问「客户 A 和客户 B 有什么共同持仓」并得到准确答案, so that 我能发现可参考的配置
2. As a 理财顾问, I want to 问「张三的持仓集中在哪些行业」, so that 我能评估他的行业集中度
3. As a 理财顾问, I want to 问「这位基金经理还管着哪些产品」, so that 我能发现管理人层面的隐性集中
4. As a 理财顾问, I want to 看到一位客户的持仓关系图, so that 我对他的配置结构有直观印象
5. As a 理财顾问, I want to 在关系图上点击一个节点看到它的要素, so that 我不必切换页面查详情
6. As a 理财顾问, I want to 关系图能按关系类型过滤, so that 节点多时我还能看清
7. As a 理财顾问, I want to 集中度超过阈值的部分在图上有视觉标记, so that 风险一眼可见
8. As a 理财顾问, I want to 知道图谱数据的同步时间, so that 我理解自己看的是什么时点的结构
9. As a 理财顾问, I want to 图谱查询超时时仍能拿到基于文本检索的回答, so that 我不会因为一个增强功能失败而完全得不到答案

### 系统管理员

10. As an 管理员, I want to 手工触发图谱重建, so that 数据修正后能立刻同步
11. As an 管理员, I want to 看到图谱的节点与关系统计, so that 我能确认导入是否完整
12. As an 管理员, I want to 重建失败时旧图谱仍可用, so that 一次失败不会让功能中断
13. As an 管理员, I want to 看到上次重建的时间与耗时, so that 我掌握同步的健康状况

### 开发者

14. As a 开发者, I want to 图谱同步是幂等的全量重建, so that 我不必处理增量同步的一致性问题
15. As a 开发者, I want to 常用的图谱查询封装成工具, so that Agent 不直接拼查询语句
16. As a 开发者, I want to 向量与图谱的融合权重可配置, so that 我能调试融合效果而不改代码
17. As a 开发者, I want to 图谱不可用时整条链路降级为纯向量检索, so that 图库是增强不是依赖

## Implementation Decisions

遵循 `docs/adr/`，核心是 ADR-0002（投影读模型）。

### 图谱是投影，不是第二个写入源

MySQL 是唯一写入源。图谱由 MySQL 单向同步生成，**只读**——任何业务写入都不经过 Neo4j。脏了就全量重建，不做双向同步，不做增量补偿（ADR-0002）。

这决定了同步的实现形态：一次幂等的全量重建，而不是一套变更捕获机制。重建期间旧图谱保持可用，新图谱构建完成后切换。

代价是图谱有同步延迟，界面上要显示同步时间——顾问需要知道自己看的是什么时点的结构。

### 图谱模型

节点：客户、产品、风险等级、行业、基金经理。
关系：客户持有产品、客户具有风险等级、产品属于行业、产品由基金经理管理、产品适合某风险等级。

客户与持仓数据来自 MySQL；行业与基金经理数据需自行构造，要求与产品数据在业务上自洽（同一基金经理的产品类型应当合理相关）。

节点上只放查询与展示需要的属性，不把 MySQL 的整行搬过来——投影模型的价值在于关系，不在于复制数据。

### 实体识别

从问题中提取产品名、风险等级、行业、客户姓名、基金经理姓名。识别失败时不阻断——退化为纯向量检索，而不是报错。

识别出的实体要能对应到图中的真实节点；对应不上的实体丢弃，不用它去查询。

### 融合排序

向量检索结果与图谱查询结果按加权综合分排序，权重可配置。去重后按综合分降序注入模型上下文。

融合发生在注入之前，**不是让模型自己去权衡两组结果**——模型拿到的是一组已排序的上下文。

### 降级

图谱是增强，不是依赖。以下情形一律降级为纯向量检索，且降级是静默的（回答照常给出，不向用户报错）：

- 图谱查询超时
- Neo4j 不可用
- 实体识别未命中任何节点
- 图谱正在重建且旧图谱不可用

降级要在留痕中记录，便于事后分析图谱的实际命中率。

### 查询工具

常用查询封装为工具供 Agent 调用：客户持仓产品、产品所属行业、某风险等级的适配产品、客户持仓的行业分布、客户间的共同持仓、基金经理管理的产品。

**Agent 不直接拼查询语句**——工具的参数是实体标识，查询语句在工具内部固定。这既避免了查询注入，也让图谱结构的变化只影响工具实现。

### 关系图

投顾工作台的一张图，用 ECharts 的关系图系列。

节点按类型区分（客户、产品、行业、基金经理各一种视觉编码），关系用连线。节点数量需要控制——一位客户的完整关系网络可能上百个节点，全画出来是一团乱麻。因此：默认只展开到产品与行业两跳，更深的层级按需展开；提供按关系类型过滤。

集中度超过阈值的行业节点有视觉标记。

图表封装复用 `packages/shared` 中的图表壳（ADR-0003），配色与其余图表同源并做对比度校验。

## Testing Decisions

沿用两个 seam。

### Seam 1 — 后端 HTTP 层

Neo4j 用真实容器（测试库与开发库分开），同步脚本在测试中真实执行。

- 全量重建两次，结果一致（幂等）
- 重建后节点与关系统计符合源数据
- 多跳查询返回正确结果：客户持仓行业分布、客户间共同持仓、基金经理管理的产品
- 图谱不可用时对话接口仍返回回答，且回答基于向量检索
- 实体识别未命中时静默降级，不返回错误
- 降级事件在留痕中有记录
- 图谱查询工具拒绝超出其参数契约的输入
- 融合权重改变时结果排序随之改变

「GraphRAG 比纯向量检索更准」这类效果类命题**不写成断言**——它依赖具体问题与语料，写成测试会变成一个脆弱且无意义的用例。改为准备一组对比问题在答辩中演示。

### Seam 2 — Vue 组件挂载

- 关系图渲染出对应节点类型数量的系列
- 节点点击后要素面板可见
- 关系类型过滤改变渲染的连线集合
- 集中度超阈值的节点带有标记
- 同步时间可见
- 图谱数据为空时渲染空状态而非空白画布

## Out of Scope

- 图谱的增量同步与变更捕获（明确不做，见 ADR-0002）
- 通过界面编辑图谱
- 图谱的版本管理与历史回溯
- 社区发现、路径推荐一类的图算法
- 关联方与最终受益人穿透（ADR-0002 列为将来重新审视此决定的信号之一，不在本项目范围）
- 反洗钱场景的关系挖掘
- 图谱数据的独立权限模型（沿用调用方的身份）

## Further Notes

这份 spec 最容易偏离的地方是把 Neo4j 当成第二个数据库用——例如「这个数据在图里查更方便，就直接写到图里」。一旦发生，ADR-0002 想避开的双写一致性问题就回来了，而且会以最难排查的形式出现：两边的数据都像是对的，只是不一样。同步脚本是图谱数据的唯一来源，这一点在实现时要守住。

评分表里 Phase 3 占 20%，另有「GraphRAG 有深度 +3」，验收标准明确要求节点数与关系数的规模以及至少三个多跳场景。构造行业与基金经理数据时要按这个规模来，太稀疏的图谱既演示不出效果，也确实做不出多跳。
