# 07 — 端到端客户旅程

**What to build:** 一条贯穿全系统的长路径能从头走到尾：开户 → 风险评测 → 咨询 → 产品筛选 → 请顾问出具方案 → 顾问审核放行 → 交易 → 风控触发预警 → 工单处置。它验证的是九份 spec 的接缝真能串起来——每一份单独通过不等于合起来通过。

这是整个项目的收口 ticket。

**Blocked by:** 06 — 回放模式与预置演示场景

**Status:** implemented

- [x] 完整旅程作为一个 HTTP 层的长用例通过，**不引入浏览器**
- [x] 用两位测试客户（高净值与普通投资者）各走一遍
- [x] 旅程中的适当性约束全程生效，无任何环节出现越级产品
- [x] 送达客户的方案是顾问定稿，不是 AI 原稿
- [x] 风控预警触发后，投顾侧能看到该客户的风险标记
- [x] 边界情形各自可通：无画像客户咨询、超长对话、非法输入、并发请求
- [x] 统一入口能按 Agent 类型正确路由到四个 Agent
- [x] 全链路的追踪标识可把一次用户可见的结果对应到日志

## 落地要点

- **开户是本 ticket 新增的业务入口**（另一个新增的是只读的 Agent 注册表出口
  `GET /api/agents`，不含业务写操作）：`POST /api/internal/customers`
  （`app/api/customers.py` + `app/customer_onboarding.py`），只有客户经理能开。
  客户不能自助注册——两个身份域（ADR-0004）之下，客户账号由其归属客户经理开立。
- **开户同时建初始画像**（这是串起全程才暴露的缺口）：风评测提交、适当性判定都
  以画像行为前提，而系统此前只有种子数据会建画像——新开户客户提交问卷直接 404。
  开户时采集的自述字段（收入、资产、经验、目标配置）以「默认值」来源写入标签
  （置信度初值 0.30），risk_level 先落 C1 占位，真正的等级由风评问卷按更高的
  来源等级改写。
- **旅程的隔离方式与客服 Agent 自己的测试一致**：fake 模型 + fake 向量化
  （确定性、零外部调用）+ 测试 Milvus 集合（真实向量检索）+ 从不重建的空图谱
  命名空间（实体未命中静默降级，不计降级留痕）。规则引擎、审核流、事件协作、
  工单全部是真实链路——不是回放预置（那条路已由 06 号 ticket 覆盖）。
- **咨询的确定性**：检索问题与知识正文逐字一致，fake embedding（字形二元语法
  哈希向量）下余弦接近 1，稳定越过 0.35 检索阈值（test_customer_service_agent
  的同一 seam）。
- **预警分级用真实规则凑出来**：固定交易时刻在工作时间内（避开 R017）；普通
  分层的客户一笔 10 万恰好命中 R001 → 轻度；私行分层的客户先 6 万（轻度）再
  120 万（R001/R002/R003/R004/R005 多条交叉 + 已有历史预警）→ 重度。越级交易
  不参与——两位客户买的都是自己等级内的产品，适当性约束全程生效。
- **统一入口**：`app/agent/registry.py` 是「按 Agent 类型路由」的唯一出处
  （类型 → 配置 → 身份域 → 入口路径），`GET /api/agents` 把它读出来。entry_path
  写的是调用该 Agent 的那条真实入口路由，端到端测试按注册表的值发请求——路由
  漂移即失败。路由本身不引入运行时意图分发（ADR-0007 拒绝 supervisor 模式）：
  旅程把四个 Agent 各自打到一遍（客服问答、数据分析查询、投顾方案、风控预警
  统计），再用 `/api/internal/traces/agent-response-times` 按 agent_type 分组
  核对四个都在场。
- **追踪标识的闭环**：带 `X-Trace-Id` 的咨询，同一标识出现在响应信封、响应头、
  风险关注记录的 trace_id 列和 `logs/info.log` 的日志行里——一次用户可见的结果
  能对应到日志的具体位置，跨系统的传播也接上了。
- **边界情形各自成用例**：无画像客户咨询（开户后未测评，回答带合法引用）、
  超长对话（12 轮 × 约 1900 token，短期记忆截断最旧、最新问答对保留、全程 200）、
  非法输入（未知分层 400、重复用户名/证件号 409、问卷缺题/选项非法 400、类型
  错误的请求体 400、给不存在客户出方案 404、空理由流转 400）、并发请求
  （8 条并发咨询全部成功且追踪标识互不相同；同一份原稿并发放行恰好一单 200
  一单 409——数据库原子锁兜底）。

## 已知取舍

- 两位测试客户由用例通过 HTTP 现场开立（uuid 后缀），teardown 按外键序删除；
  测试库跨运行持久，不留痕迹，也不碰种子客户。
- 数据分析与风控监测两个查询 Agent 走 `register_fake_query` 的确定性 seam
  （与数据分析 Agent 自己的测试同一装配），不调真实模型；查询先过校验层，
  统计数字来自旅程刚产生的真实预警行。
- 旅程不断言图谱多跳与归档脱敏——它们分别在 06 号 ticket（回放）与
  01/02 号 ticket 的用例里固定；本用例的图谱命名空间刻意保持为空。
- 并发用例共用一个 TestClient（同进程内 portal 派发），只验证应用层并发语义
  （会话隔离、数据库原子锁），不是性能压测——spec Out of Scope 已排除压测。
- `GET /api/agents` 不要求认证：它只暴露静态的路由事实（Agent 类型、工具集、
  身份域、入口路径），不含任何客户数据，与 `/api/health` 同一待遇。
- 客户数据的清理清单（`_delete_customer`）与回放模式测试各持一份——同一形状
  在两个测试模块里重复。抽成 conftest 共享夹具是更优解，但要动到已通过的
  06 号用例，留给后续整理。
