# 记忆体系、置信度与系统集成

Status: ready-for-agent

前置：全部四个 Agent 的 slice

## Problem Statement

到这一步四个 Agent 各自能跑，但它们互相不知道对方发生了什么：风控刚对一位客户发出重度预警，投顾助手仍然照常为他生成激进配置方案；客服察觉到客户在反复打听转账限额，风控那边毫无察觉。

记忆也是零散的：客服 Agent 有短期会话记忆，画像有缓存，知识库有向量——但没有一套统一的说法解释「什么信息存多久、存在哪、怎么取回」。画像标签的置信度在 `customer-profiling-and-suitability` 里算出来就不再变了，一年前的标签和昨天的标签看起来一样可信。

还有一批只有在全部拼起来之后才会暴露的问题：一条完整的客户旅程能不能从头走到尾、某个服务挂掉时系统会怎样、答辩当天网络抖动了怎么办。

## Solution

把三层记忆的分工说清楚并补齐缺口：**短期记忆**是当前会话的消息，存在缓存里有过期时间和 token 预算；**中期记忆**是画像与工单状态，缓存加数据库；**长期记忆**是知识向量、图谱、原始文档与元数据。会话结束后完整流水脱敏归档。

**置信度**从一次性计算变成持续维护：除了各标签自身的基础置信分，增加一层**综合重排**——同一批记忆单元在不同场景下的排序不同（做产品推荐时时效性没那么重要，做风险研判时时效性权重最高）。另有周期任务定期重算全量置信度并标记过期标签。

**Agent 间通过事件总线协作**：风控发出预警，投顾与客服收到并调整行为。

最后是集成：端到端客户旅程、各存储故障时的降级、以及一个**确定性回放模式**用于答辩兜底（ADR-0008）。

## User Stories

### 客户与员工（可感知的行为）

1. As a 客户, I want to 长对话中系统仍记得开头说过的关键信息, so that 我不必反复重申
2. As a 客户, I want to 超长对话不会让系统变慢或报错, so that 我可以放心地一直问下去
3. As a 理财顾问, I want to 为一位刚触发重度预警的客户生成方案时看到风险标记, so that 我不会给出一个不合时宜的激进建议
4. As a 风控专员, I want to 客服察觉到的高风险意图能到达我这里, so that 我能提前关注
5. As a 理财顾问, I want to 一年前的画像标签比上周的标签显示更低的可信度, so that 我知道哪些信息该重新确认
6. As an 内部员工, I want to 某个存储服务不可用时系统仍能提供降级后的服务, so that 一个组件故障不会让整个系统不可用
7. As an 内部员工, I want to 查询任意一次历史会话的完整记录, so that 我能回溯当时发生了什么

### 合规

8. As a 合规负责人, I want to 会话归档中的敏感信息已脱敏, so that 留痕本身不是新的泄露源
9. As a 合规负责人, I want to 每次调用的审计级留痕永久保存, so that 合规举证不受保留期限制
10. As a 合规负责人, I want to 调试级留痕在保留期后被删除, so that 我们不无限期持有完整提示词与检索片段
11. As a 合规负责人, I want to 留痕的清理有明确的时间基准而非依赖运行时当前时间, so that 清理行为可测试可复现

### 开发者与运维

12. As a 开发者, I want to 三层记忆的边界有明确定义, so that 新增一类信息时我知道它该放哪
13. As a 开发者, I want to 会话上下文超出 token 预算时截断最旧的消息, so that 长对话不会撑爆上下文
14. As a 开发者, I want to 缓存不可用时直连数据库并在恢复后自动回填, so that 缓存是优化不是依赖
15. As a 开发者, I want to 向量检索超时时降级为关键词检索, so that 检索链路有兜底
16. As a 开发者, I want to 图谱查询超时时跳过增强只用向量结果, so that 增强失败不阻断回答
17. As a 开发者, I want to 模型调用失败时按退避策略重试，仍失败则切换备用，再失败则返回预设兜底, so that 外部依赖的抖动不直接暴露给用户
18. As a 开发者, I want to 每个请求有贯穿全链路的追踪标识, so that 我能把一次用户可见的失败对应到日志的具体位置
19. As a 开发者, I want to 各 Agent 的响应时间有统计, so that 我知道瓶颈在哪
20. As a 开发者, I want to 置信度的综合重排权重按场景配置, so that 调整策略不改代码
21. As a 开发者, I want to 周期校准任务可手工触发, so that 我不必等到下一个周期才能验证
22. As a 开发者, I want to 一条命令启动确定性回放模式, so that 演示不依赖外部服务健康
23. As a 开发者, I want to 回放数据覆盖典型演示场景, so that 答辩时每条主线都能走通

### 事件协作

24. As a 开发者, I want to 事件的发布方不关心有几个订阅方, so that 新增订阅不需要改发布方
25. As a 开发者, I want to 订阅方处理失败不影响发布方, so that 协作链路不会反向拖垮核心链路
26. As a 开发者, I want to 事件载荷的结构是明确定义的, so that 订阅方不必猜字段

## Implementation Decisions

遵循 `docs/adr/`，核心是 ADR-0008（回放模式）与 ADR-0011（时间基准显式传入）。

### 三层记忆的边界

- **短期记忆**：当前会话的消息列表，缓存中的列表结构，滑动过期，总 token 超预算时截断最旧消息。会话不跨登录延续。
- **中期记忆**：客户画像与工单状态。画像走 Cache-Aside，工单直接查库、热点可缓存。
- **长期记忆**：知识向量、图谱、原始文档、知识元数据。

边界的判据是**信息的生命周期与权威来源**，不是存储技术。新增一类信息时先问它活多久、谁是权威来源，再决定放哪层。

### 归档

会话结束后完整流水写入归档表，**写入前脱敏**：身份证号、手机号、真实姓名、银行卡号按既定规则处理。工具调用记录一并留存。

留痕分两级：**审计级**（使用者、Agent、问题、最终答案、引用文档、内容分类）永久保存；**调试级**（完整提示词、原始检索片段、token 与耗时明细）保留一段时间后删除。

清理任务**接受一个明确的时间基准参数**，而不是在内部读取当前时间——否则这个任务无法被可靠地测试（测试要能断言「基准为某时刻时，恰好删除哪些记录」）。

### 置信度的两层

**基础置信分**（已在 `customer-profiling-and-suitability` 实现）：来源初值、证据增益、冲突惩罚、时间衰减。

**综合重排**（本 slice 新增）：对一批记忆单元按场景加权重排，因子包括语义相似度、时效性、历史准确率、基础置信分、冲突惩罚。不同场景的权重不同——产品推荐更看重语义相似度，风险研判更看重时效性。权重按场景配置，不硬编码。

重排的输出是排序，**不是过滤**：低分单元排在后面，不被丢弃。丢弃的判断留给调用方。

### 周期校准

定期重算全量置信度并把过期标签标记为已过期。可手工触发。

校准同样接受明确的时间基准，理由同上。

### 事件协作

发布方只管发布，不知道订阅方是谁、有几个。订阅方处理失败不影响发布方——协作是增强，核心链路不依赖它。

事件载荷结构明确定义：事件类型、来源、载荷、时间戳、追踪标识。

本 slice 要落地的两条协作：
- 风控发出预警 → 投顾助手在为该客户生成方案时加入风险标记
- 客服识别到高风险意图 → 通知风控关注

### 降级

每一处外部依赖都有明确的降级路径：

| 依赖 | 失败时 |
|---|---|
| 模型调用 | 退避重试，仍失败切备用，再失败返回预设兜底 |
| 向量检索超时 | 降级为关键词检索 |
| 图谱查询超时 | 跳过增强，只用向量结果 |
| 缓存不可用 | 直连数据库，恢复后回填 |
| 事件总线不可用 | 记录日志，核心链路继续 |

降级都要在留痕中记录——否则无法知道系统实际上有多少次在降级状态下工作。

### 回放模式

由环境变量控制（ADR-0008）。开启后预置问答走确定性回放，不依赖模型与向量库。

回放数据要覆盖典型演示场景：客服问答带引用、产品筛选、画像与适当性、数据查询、投顾方案与审核、图谱多跳、风控预警分级。**回放的输出质量不能敷衍**——它要产出结构完整、引用合法的回答，否则演示时会露馅（ADR-0008 已记录这一点）。

### 链路追踪与监控

每个请求有贯穿全链路的追踪标识，出现在响应与所有日志行中。各 Agent 的响应时间有统计。日志按级别分文件。

## Testing Decisions

沿用两个 seam。

### Seam 1 — 后端 HTTP 层

- 超长对话（远超 token 预算）不报错，且最旧消息被截断、最新消息保留
- 重新登录后上一次会话的上下文不可见
- 归档记录中不含未脱敏的身份证号、手机号、姓名、银行卡号
- 调试级留痕在给定时间基准下被正确清理，审计级留痕不受影响
- 综合重排在不同场景配置下产生不同排序
- 周期校准后过期标签状态正确变更
- 缓存不可用时画像仍可读取；恢复后缓存被回填
- 模型调用失败时按退避重试，最终返回兜底回答而非错误
- 向量检索超时时返回基于关键词的结果
- 图谱不可用时返回基于向量的结果
- 事件订阅方抛错时发布方的请求仍然成功
- 风控预警广播后，投顾为该客户生成的内容带风险标记
- 回放模式下全部预置场景返回结构完整的响应，且不发起任何外部调用

综合重排与置信度计算作为纯函数单独测试，与前述两处纯计算的处理方式一致。

端到端客户旅程（开户 → 风评 → 咨询 → 筛选 → 方案请求 → 审核 → 交易 → 风控触发 → 工单处置）作为一个 HTTP 层的长用例，验证各 slice 的接缝能串起来。它**不是**浏览器测试。

### Seam 2 — Vue 组件挂载

- 长对话在界面上正常滚动与渲染
- 降级状态下的回答仍正常渲染（不因缺少引用而报错）
- 画像面板渲染标签的置信度随时间衰减后的值

## Out of Scope

- 分布式任务队列（周期任务用进程内调度即可）
- 事件的持久化与重放（事件总线不保证送达，核心链路不依赖它）
- 多实例部署与水平扩展
- 完整的可观测性栈（指标采集、链路追踪系统、告警）
- 性能压测与容量规划
- 答辩 PPT 与演示脚本的内容撰写（工程之外）

## Further Notes

这份 slice 的性质与前面几份不同：它没有新的用户可见功能，价值在于把已有的东西连起来并让它们在不理想的条件下仍然工作。因此它最容易被压缩——赶进度时「降级路径」和「回放数据」看起来都像是可以放到最后的事。

但按评分表，这里恰好是风险最集中的地方：「项目无法启动 -20」是最重的扣分项，而答辩当天依赖六个容器加外部模型服务同时健康。回放模式是这条风险的对冲，它应该在答辩前很久就可用，而不是前一天晚上才想起来。

关于清理任务接受明确时间基准这一点：它看起来是个小细节，但如果清理任务在内部读当前时间，那么「保留期外的记录被删除」这个行为就只能靠等待或改系统时钟来测试，实际上等于测不了。
