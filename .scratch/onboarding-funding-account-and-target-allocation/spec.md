# 开户的两处缺口：目标配置不是一个「比例」、客户没有资金账户

Status: ready-for-agent

前置：`operation-advice-and-customer-trading`（资金账户与可用余额 `#01`、端到端 `#10`）、`frontend-rebuild`（开户表单）

本 slice **不新增 ADR**，不新增领域术语；它**修改**两处已实现的既有决定（清单见头表与 `Further Notes`）。

## Problem Statement

开户（`POST /api/internal/customers` → `app.customer_onboarding.open_account`）是客户进入系统的唯一入口。它有两处缺口，都是「界面上放得进去、语义上不成立」：

**缺口一：目标配置的合计没有约束。** 开户表单把「各类资产占比，%」五项分别限在 0–100（`OpenAccountForm.vue` 的 `el-input-number :max="100"`），后端对 `target_allocation` 只做「有没有值」的判断（`open_account` 里 `target_allocation or {}`）。于是合计 180% 的目标配置能原样入库。

它不是「数字看起来奇怪」，而是入库之后**下游会算错**：`app.advisory.allocation.suggest_allocation` 把目标配置当基线做调整，它把被侧重的类别记账为 `100 - sum(其余类别)`，这个式子只在合计为 100 时成立。拿一份合计 150 的目标配置进去，权重最大的那个类别会被算成 30——方案给出的配置建议与客户的意愿无关。内部端的「目标配置 vs 实际配置」对比图（ADR-0006）同样如此：实际配置是持仓按市值聚合出来的比例（恒为 100%），两组站在同一根轴上的前提是两边都是比例。

合计不足 100 是同一个问题的另一半：`100 - sum(其余)` 会把差额悄悄记到被侧重的类别上（只填「股票 60」的人会拿到 100% 股票的方案）。

**缺口二：开户不建资金账户。** 「一个客户一个资金账户」是 `CONTEXT.md` 对 **资金账户** 的定义，种子里的每位客户也都有（`seed._seed_customers`）。但 `open_account` 只写 `sys_customer`、`fin_customer_profile` 与画像标签，不写 `fin_funding_account`。新开户的客户登录后「我的资产」页的可用余额恒为「—」（`useAvailableBalance` 在 404 时给「—」），交易页下单回 `404 资金账户不存在`。

这是 `operation-advice-and-customer-trading` 当时认下的代价（该 slice 的 `#10` 与 `docs/demo-script.md` 都写明「新开户客户没有资金账户」），但那个代价建立在一个混淆上：**「不做入金」不等于「没有账户」**。Q20 决定的是余额只来自种子、没有入金入口，它没有决定新客户不存在资金账户。前者是余额恒为 0，后者是客户没有这个实体——后者与 `CONTEXT.md` 的定义冲突，也让客户端把「没有这个账户」与「读不到余额」显示成同一个「—」。

## Solution

**缺口一**：目标配置是一组**比例**，合计必须为 100。校验收在一处（`app/customer_profile/target_allocation.py`），两个写入路径都过它：开户采集（`open_account`）与理财顾问的手工修正（`write_tag`）。合计不是 100、或出现负数/非数字时回 400，文案说明差在哪里。开户表单同一页给出实时合计，提交前先拦一道（后端仍会再校验一次）。

**缺口二**：开户与写画像、写标签在同一个事务里建出资金账户，余额 0。**入金仍然不在范围内**（Q20 不变，已被 ADR-0023 取代）：新客户能登录、能看资产页、能走完风评与产品筛选，但下单会回「可用余额不足」——这不是绕开了 Q20，而是把「没有钱」与「没有账户」这两件事分开。种子的余额对齐逻辑不动。

## 访谈结论清单

| # | 决定 |
|---|---|
| Q1 | 目标配置的合计判据 = **恰好 100**，不是「不超过 100」。比例的定义就是合计为一，缺项（<100）与被下游 `100 - sum(其余)` 吃掉差额一样，都不能构成基线。 |
| Q2 | 判据落在**所有写入路径**（开户 + 顾问手工修正标签），实现为单一函数；种子的直接 ORM 写入不在路径上（种子数据本就都是 100）。 |
| Q3 | 校验失败回 **400**，文案给出实际合计，落到哪个字段由前端承担（字段下方提示）。 |
| Q4 | 开户表单**显示实时合计**并在提交前拦一道；「五项全为 0 = 没有填」的既有语义不变。 |
| Q5 | 开户建资金账户，**余额 0**；不做入金、不引入任何入金入口（Q20 不变，已被 ADR-0023 取代）。 |
| Q6 | 资金账户与客户、画像在**同一个事务**里落库——开户要么整件事成立，要么什么都不留。 |
| Q7 | 不新增 ADR（两处都是既有概念的落实，没有 hard-to-reverse 的新取向）；`CONTEXT.md` 零改动。 |
| Q8 | 合计**比到百分位**为止（`ROUND_HALF_UP`），与开户表单的显示刻度同一把尺子：表单里 `33.33 + 33.33 + 33.34` 在 JS 里不等于 100，按不同的刻度比会出现「界面显示 100%、后端说不是」。 |
| Q9 | 「五项全为 0」与「不带这个字段」在**后端也是同一件事**，不只在前端。校验函数因此对「合计 0」直接放过，而不是回一句「合计 0，应为 100」。 |

## 修改的既有决定

| 既有决定 | 出处 | 本 slice 的修改 |
|---|---|---|
| 「新开户客户没有资金账户（本 slice 不做入金）」 | `operation-advice-and-customer-trading` 的 `#10`、`docs/demo-script.md` 第六幕 | 开户即建资金账户、余额 0。「不做入金」照旧，演示台词改为「余额 0」而不是「账户不存在」。 |
| 目标配置只校验「有没有值」 | `app/customer_onboarding.open_account` | 增加合计必须为 100 的校验。 |

## Testing Decisions

Seam 不变，仍是后端 HTTP 层（`TestClient`）——两处缺口的入口都在这条 seam 上。

- 新增 `backend/tests/test_customer_onboarding.py`：开户这一个入口的行为（目标配置的合计、资金账户随开户出现）。它此前没有自己的测试文件，只有端到端旅程顺带走过；两处缺口正是因此没被拦住。
- 前端：`apps/internal/src/customer-relations/onboarding.ts` 的纯函数（合计与错误文案）加 vitest 用例，不挂组件。

既有测试里「先开户、再直接 INSERT 资金账户给钱」的助手（旅程与四份操作建议用例）改为 UPDATE——账户已存在，再 INSERT 会撞唯一约束。

## Out of Scope

- **入金**（Q20 不变，已被 ADR-0023 取代）：余额仍是 0 起点，没有充值/打款入口。
- 目标配置的类别清单校验（后端仍接受任意类别键）、类别排序、历史版本。
- 把「可用余额读不到」与「余额为 0」在客户端彻底区分（`useAvailableBalance` 的「—」语义不动）。
- 已开户但没有资金账户的历史数据回填（演示库重新 `python -m app.db.setup` 即恢复，不写数据迁移）。
