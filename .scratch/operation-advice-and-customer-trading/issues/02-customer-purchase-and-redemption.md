# 02 — 客户侧的申购与赎回

**What to build:** 客户第一次能自己动钱。申购、赎回在受理服务里校验通过后落成一笔既成交易，并调用 `submit_transaction_event` 走「落库 → 广播 → 过规则引擎」。产品需要一个成交价，因此 `fin_product` 增加当前单位净值。

**Blocked by:** 01 — 资金账户与可用余额

**Status:** implemented

- [x] `fin_product` 增加当前单位净值；成交口径：申购 `份额 = 金额 / 净值`、赎回金额 `= 份额 × 净值`，手续费按费率计
- [x] **持仓的当前市值仍是独立维护的字段，不改成 `份额 × 净值` 的推导值**——没有净值时间序列，改成推导会重写资产页与穿透的所有数字
- [x] 受理校验（在受理服务里、落库之前）：未提交过风险测评 / 适当性越级 / 余额不足 / 低于起投金额 / 产品不在售 / 赎回超过持仓份额
- [x] **未做过风评的拒绝文案是「请先完成风险测评」，不是「风险等级不足」**——开户时写下的 C1 是占位而不是结论
- [x] 风评的判定只看**有没有测评记录**，不看有效期（种子客户的风评早已过期）
- [x] 校验**不放进交易事件入海口**：`submit_transaction_event` 保持窄口（ADR-0018）
- [x] 申购与赎回按 7 个自然日的有效期无关，属即时成交；成交后同步更新持仓（份额、成本、市值）与余额
- [x] 赎回后份额归零时，持仓状态不再为「持有中」，资产页不再显示它
- [x] 客户侧接口：申购、赎回；**客户标识由身份推导**
- [x] **交易的来源不加字段**：客户自助发起的交易没有经办员工（`operator_id` 为空），这条隐式约定要写进测试
- [x] 断言：越级产品申购被拒绝；余额不足被拒绝；未测评客户的交易被拒绝；成交后持仓与余额自洽

**实现落点：** `backend/app/order_acceptance/`（受理服务）、`backend/app/api/customer_transactions.py`
（`POST /api/customer/transactions/purchase` 与 `/redemption`）、迁移 `0024_product_nav`、
测试 `backend/tests/test_customer_purchase_and_redemption.py`。

受理服务是申赎与（下一份 issue 的）转账共用的地方：校验、成交、持仓与可用余额的更新都在
这里，落库由 `submit_transaction_event` 一次提交完成。校验全程在写库之前，因此被拒绝的
受理在库里不留任何痕迹（测试断言了这一点）。

`fin_transaction.amount` 在两个方向上都记**成交金额**（申购是申购金额、赎回是 `份额 × 净值`），
手续费在 `fee` 列单列一行，可用余额的增减是这两个数的组合效果——到账金额不进 `amount`。
种子里的五笔历史成交按同一口径重算并对齐（净值与费率此前各写各的，`seed` 现在按流水号
回写它们，与资金账户余额一样属于「重复 seed 即恢复初始演示状态」）。

赎回后份额归零的持仓改记 `已清仓`，且再申购时从零恢复为「持有中」——不复位状态的话，
买回来的持仓会因为状态不是「持有中」而在资产页上继续隐身。
