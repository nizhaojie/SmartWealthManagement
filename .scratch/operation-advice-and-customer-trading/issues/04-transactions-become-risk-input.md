# 04 — 交易成为风控的真正输入

**What to build:** 这一份 issue 修的就是需求里那句「现在的风控监测不起作用」。风控那一侧本来是完整的，缺的是输入端：交易事件在应用里没有任何真实触发点，种子数据又整批绕过了规则引擎。

做完这一份，项目上第一次有一个能演示的完整状态：**客户发起一笔 50 万转账 → 预警列表出现对应预警。**

**Blocked by:** 03 — 转账与客户侧流水合并读

**Status:** ready-for-agent

- [ ] 客户的申购、赎回、转账**全部**走 `submit_transaction_event` 这一条路径，不新增第二条
- [ ] 内部补录接口收窄：**只对风控专员开放**（现状是所有内部员工都能调）
- [ ] 预警详情与列表增加来源标注（客户发起 / 内部补录），依据是**有无经办员工**，不新增字段
- [ ] 种子里的历史交易改为**按时间正序逐笔**走同一个函数回放——**不另写批量脚本**，那正是今天这个 bug 的成因
- [ ] 回放的预警时间戳**取该笔交易自己的时间**；规则求值的基准本来就是交易自身的时间，求值逻辑不需要改
- [ ] 回放产生的历史预警**不做任何特殊化**：不标记、不隔离，靠时间倒序自然沉底
- [ ] 写下并接受副作用：历史预警计入分级的历史计数，第一个在演示里做大额操作的客户很可能直接判**重度**——这是分级存在的理由，讲之前先想好台词
- [ ] 断言：**客户发起一笔 50 万转账 → 预警列表出现对应预警**
- [ ] 断言：非风控专员调用内部补录接口被拒绝（**新增护栏 7**，同时补进 `docs/adr/0009-compliance-guardrail-tests.md`）
- [ ] 断言：广播通道不可用时，客户侧发起的交易与预警照常落库（既有用例换到客户侧入口上再跑一遍）
- [ ] 断言：回放结果与逐笔调用同一函数的结果一致——把「回放不走旁路」这个事实钉住
