## Problem Statement

**风控监测在常规使用下是空转的。** 规则引擎、20 条规则、分级、预警、工单、风险关注、API、界面、测试全都齐备，但交易事件在应用里没有任何真实触发点：唯一入口是内部接口 `POST /api/internal/transaction-events`，需要员工身份，前端从不调用；而种子数据在 `backend/app/db/seed.py:591-608` 直接以 ORM 写 `fin_transaction`，**绕过了规则引擎**。于是预警列表永远是空的——「风控监测」这块牌子挂在那里，没有任何一笔交易经过它。

根因不是规则写得不对，而是**系统里根本没有交易**。客户不能申购、不能赎回、不能转账；`fin_transaction` 只是一个只读的既成流水表，连一个成交价都没有（`fin_product` 没有净值字段）。风控缺的是输入，不是判断力。

三块业务空白同时挡在这里：

1. **客户没有交易能力。** 客户侧全部是只读页面（资产、产品筛选、方案），「申购」「赎回」只作为交易流水里的两个字符串存在。`product-screening-and-customer-assets` 当时把「真实申购、赎回、支付」明确排除在外，客户被告知「请顾问出具方案」，然后顾问出了方案，客户仍然什么都不能做。
2. **没有资金。** 全库没有资金账户、可用余额、冻结任何一个概念；「钱」只以两种形态出现——持仓市值，和画像里一个叫总资产的数字。申购、赎回、转账因此都无从谈起。
3. **客户经理没有建议的手段。** 客户经理是客户关系的归属人，却只能看、只能留言（`backend/app/api/advisory.py:52` 的生成入口只开放给理财顾问）。他手里最该有的工具——「对你的某只产品做一次申购/赎回」这种单笔的具体建议——系统里不存在。

## Solution

**客户侧第一次有了写操作。** 新增资金账户与可用余额（最小形态：一个客户一个账户、一个余额字段），客户可以在新增的「交易」页做三件事：**申购、赎回、转账**。申购与转账扣减余额、赎回增加余额；全部经过适当性、余额、起投金额、产品状态的校验，然后落成一笔既成交易（`fin_transaction`），并从这一刻起**成为风控监测的输入**。转账没有产品，落在自己的表里（ADR-0019），但客户看到的是一张合并的「交易流水」。

**客户经理有了建议的手段。** 新增第五份 Agent 配置——**业务操作 Agent**（ADR-0017）：客户经理为自己名下的客户选定场景，Agent 在**候选池内**产出**操作建议**（一个产品、一个方向、一个金额、一条理由），经理财顾问放行后送达客户。客户可以**接受或拒绝**；接受即当场成交，拒绝与过期都是建议的终态。

**这条链路不改变红线。** 操作建议是投顾内容，客户经理只发起、顾问才放行；放行走的还是那唯一一条审核流水线（ADR-0020），「未经审核不可送达」的护栏从此守两个出口而不是变成两套。

**风控从空转变成有输入。** 客户的申购、赎回、转账全部接进既有的 `submit_transaction_event`：先事务性落库、再广播、最后过规则引擎。种子里的历史交易也按时间正序逐笔走同一条管线回放一遍——不是另写一个批量脚本，那正是今天这个 bug 的成因，不要复制第二遍。**验收标准是一条具体的演示：客户发起一笔 50 万转账，预警列表出现对应预警。**

## User Stories

### 客户 · 交易

1. As a 客户, I want to 申购一只我看中的产品, so that 我不必只能看着清单等顾问
2. As a 客户, I want to 赎回我持有的一部分或全部, so that 我能把钱取回来
3. As a 客户, I want to 转账给别人, so that 我能把钱付出去
4. As a 客户, I want to 随时看到我的可用余额, so that 我知道自己还能动多少钱
5. As a 客户, I want to 在自己的交易流水里看到申购、赎回与转账, so that 我核对账目时只在一处找
6. As a 客户, I want to 在余额不足、产品越级、未做过风评时看到明确的原因, so that 我知道是我不满足条件而不是系统坏了
7. As a 客户, I want to 未做过风险测评时被引导去测评, so that 我能自己解决这个门槛

### 客户 · 操作建议

8. As a 客户, I want to 看到客户经理为我发起的操作建议, so that 我知道有人给我具体的下一步
9. As a 客户, I want to 看到这条建议是哪个产品、什么方向、多少钱、为什么, so that 我能判断要不要接受
10. As a 客户, I want to 自主决定接受或拒绝, so that 最终决定权在我
11. As a 客户, I want to 看到建议的有效期, so that 我知道什么时候之前必须做决定
12. As a 客户, I want to 在有待我决定的建议时看到提示, so that 我不会错过它
13. As a 客户, I want to 接受失败时知道原因, so that 我能先去解决（比如补足余额、重做风评）再来

### 客户经理

14. As a 客户经理, I want to 为我名下的一位客户发起操作建议, so that 我不必只靠电话和微信说
15. As a 客户经理, I want to 让 Agent 在合规范围内挑出产品并给出理由, so that 我不必自己核对适当性
16. As a 客户经理, I want to 看到我发起的建议现在走到哪一步, so that 我能回答客户的询问
17. As a 客户经理, I want to 我无法放行建议, so that 资质要求在系统里是硬的

### 理财顾问

18. As a 理财顾问, I want to 在同一个审核队列里看到方案与操作建议, so that 我不会漏看一半
19. As a 理财顾问, I want to 从队列里一眼看出每条内容是哪一类, so that 我知道该用什么标准看它
20. As a 理财顾问, I want to 放行或驳回一条操作建议并留下理由, so that 送达客户的内容是我认可过的

### 风控专员

21. As a 风控专员, I want to 客户的每一笔资金操作都自动过规则引擎, so that 监测不再依赖有没有人手工报数
22. As a 风控专员, I want to 在预警详情里看出这笔交易是客户发起的还是内部补录的, so that 我知道该不该信它
23. As a 风控专员, I want to 只有我能补录交易, so that 绕过业务校验的口子只有我一个人拿得到

### 合规负责人

24. As a 合规负责人, I want to 操作建议未经顾问放行在任何客户侧接口都读不到, so that 红线守的是同一条出口
25. As a 合规负责人, I want to 客户经理无法放行自己发起的建议, so that 发起与放行不落进同一个人手里
26. As a 合规负责人, I want to 客户的每笔交易都过适当性与余额校验, so that 越级与透支不能靠界面绕过
27. As a 合规负责人, I want to 内部补录的通道只对风控专员开放, so that 它是修复手段而不是后门

### 开发者

28. As a 开发者, I want to 客户交易复用既有的交易事件管线, so that 风控不出现第二条输入路径
29. As a 开发者, I want to 回放走与实时同一个函数, so that 不会再出现「种子数据绕过规则引擎」这类只有演示时才发现的裂缝
30. As a 开发者, I want to 操作建议的载荷与方案各自建表, so that 方案特有的字段不以空列的形式跟着建议走

## Implementation Decisions

遵循 `docs/adr/`，本 slice 新增 ADR-0017（Agent 分工）、ADR-0018（校验分层）、ADR-0019（转账分表）、ADR-0020（审核单流水线）。

### 资金账户与余额

一个客户一个资金账户，含一个可用余额。不做冻结、不做多币种、不做对账，也不做入金——余额来自种子，给足（Q20）。申购与转账扣减、赎回增加，余额不足直接拒绝。

余额与画像里的**总资产**是两个概念：总资产是客户在所有地方的资产规模（自述、用于画像研判），余额只装客户能在这里动用的钱。术语上必须分开（`CONTEXT.md` 已在 `_Avoid_` 里互相点名），否则「总资产 80 万」会被顺手当成「能买 80 万」。

### 净值与成交

`fin_product` 增加当前单位净值。申购 `shares = 金额 / 净值`、`fee` 按费率计、余额扣减 `金额 + fee`；赎回金额 `= 份额 × 净值 - fee`、余额增加它。**持仓的当前市值仍是独立维护的字段**，不改成 `份额 × 净值` 的推导值（Q12）——本项目没有净值时间序列，只有一个当前值，把市值改成推导等于顺手重写了资产页与穿透的所有数字，那是另一件事。

### 交易受理（客户侧）

校验按 Q11 的五条，在受理服务里、落库之前完成：

| 校验 | 拒绝时的语义 |
|---|---|
| 未提交过风险测评 | 「请先完成风险测评」——**不是**「风险等级不足」 |
| 适当性：产品风险等级高于风险承受等级 | 越级拒绝（护栏 1 的延续） |
| 余额不足（申购含手续费、转账为全额） | 拒绝，并给出还差多少 |
| 低于产品起投金额 | 拒绝 |
| 产品不在售 | 拒绝 |
| 赎回份额超过持仓份额 | 拒绝 |

风评的判定依据是**有没有风险测评记录**，不看有效期（Q18）：开户时写下的 `C1` 是占位而不是结论，拿它去拒绝客户，客户会收到一个他无法理解的拒绝；而种子客户的风评 `valid_until` 全部停留在 2023 年，把过期也算进去会一次性锁死所有人。风评过期只做提示——过期怎么办是全系统的问题，不该由这条需求顺手改掉。

**交易的来源不加字段**（Q22）：客户自助发起的交易没有经办员工，内部补录的必带——`fin_transaction.operator_id` 本来就是可空的，语义也对得上。这条是隐式约定，必须写进 `CONTEXT.md` 并在测试里断言，否则下一个人会给客户发起的交易随手填一个操作员 id。

校验**不放进交易事件入海口**（ADR-0018）：`submit_transaction_event` 是风控的输入端，它的输入是既成事实，不该被适当性与余额夹住。内部补录因此可以产生越级或超额的交易——代价是它只对风控专员开放。

### 转账

转账独立成表（ADR-0019），没有产品，对手方是外部收款人（姓名 + 账号）。它照常产生一笔交易事件进入风控，`TransactionEvent.product_id` 本来就是可空的，风控侧无需改动。

客户侧的交易流水接口必须从 `INNER JOIN fin_product`（`backend/app/customer_assets/service.py:119`）改成**两表合并读**并按时间倒序——否则转账行会整行消失，且不会报错。

### 操作建议：生成、放行、送达

- **生成**：客户经理在名下客户的页面上发起，业务操作 Agent 在候选池内产出原稿（产品、方向、金额、理由）。候选池已完成适当性硬过滤，Agent 不重新做适当性判断——与投顾助手的处理一致。
- **放行**：走与方案同一条审核流水线（ADR-0020）。客户经理看得到、评论得了，放行与驳回只开放给理财顾问。
- **送达**：放行后进入客户可见集合，客户在「我的建议」里看到它。送达视图沿用「服务端裁剪」的做法，不靠前端展示习惯。
- **决定**：`待客户决定 → 已接受 / 已拒绝 / 已过期`。有效期 7 个自然日。接受是一次原子操作——当场跑一遍受理校验，通过则成交并产生交易事件，不通过则**接受失败、建议留在待客户决定**（客户补足余额后可以再来一次）。过期的建议不能再接受，客户经理可重新发起一条。

建议本体的三条硬边界（Q9）：一次只对应一个产品一个方向、金额必填、禁止收益预测与配置比例表述。理由是它们让「操作建议」与「配置方案」保持是两个东西——一旦允许一次建议多个产品，两边的产物就重合了，业务操作 Agent 也就没有存在的必要。

### 界面

**客户侧**：新增「交易」页（可用余额 + 申购 / 赎回 / 转账）与「我的建议」页（带待决定角标）。两者语义不同，因此不合并——交易是客户主动做的事，建议是等他做决定的事（收件箱），而「我的方案」是资料库（只读回看）。把建议塞进只读页面，客户不会发现有待他决定的东西。

**内部侧**：客户经理的发起入口放在既有 `customer-relations` 模块（那是他唯一的地盘，符合「角色可见性留在应用内」的既有做法）；顾问侧**不新开模块**，把操作建议并入既有审核队列并标注内容类型——审核是同一类工作，分两个队列只会让顾问漏看一半。

预警详情页增加一行来源标注（客户发起 / 内部补录），依据是经办员工的有无。

### 风控接入与回放

客户的申购、赎回、转账全部调用既有的 `submit_transaction_event`：先事务性落库，再广播，最后过规则引擎。三条路径**只有一条**。

种子里的历史交易按**时间正序逐笔**走同一个函数回放，预警的时间戳取该笔交易自己的时间（Q15）。规则求值的基准本来就是交易自身的时间（`backend/app/risk_monitoring/evaluator.py:35-45`、`context.py:47-54` 的两个函数内部都不读系统时钟），所以窗口类规则会按历史真实的时间线正确命中，不需要改求值。

回放产生的历史预警**不做任何特殊化**（Q19）：它们是真实命中的预警，按时间倒序自然沉底，而演示中当场产生的预警永远在最上面——列表里同时有「监测一直在跑」的证据和「现在是活的」的证据。要认下的副作用是它们计入分级的历史计数（`alerting.py:156`），第一个在演示里做大额操作的客户很可能直接判重度。

## Testing Decisions

沿用两个 seam。

### Seam 1 — 后端 HTTP 层

护栏相关：

- **未放行的操作建议在任何客户侧接口都读不到**（护栏 5 的第二个出口）
- 客户经理调用放行接口被拒绝
- **越级产品的申购被拒绝**（护栏 1 的延续——客户直接挑产品时没有候选池兜底）
- 余额不足的申购与转账被拒绝
- 未提交过风险测评的客户交易被拒绝，且提示是「请先完成风险测评」而不是风险等级不足
- **非风控专员调用内部补录接口被拒绝**（新增护栏 7，见 ADR-0009）
- 客户 A 的凭证拿不到客户 B 的余额、建议与转账记录

链路相关：

- **客户发起一笔 50 万转账 → 预警列表出现对应预警**（本 slice 的验收标准）
- 广播通道不可用时交易与预警照常落库（既有断言的延续，换到客户侧入口上再跑一遍）
- 种子回放后：历史交易各自产生了正确的预警，且预警时间戳等于对应交易的时间
- 回放走的是与实时同一个函数——用一条断言把这个事实钉住（例如回放不新增任何「批量写库」的代码路径，或直接断言回放结果与逐笔调用一致）
- 转账不出现在 `fin_transaction`，但出现在客户侧合并的流水里
- 客户侧流水含三类记录，按时间倒序，转账行没有产品名而有收款人
- 申购后持仓份额与成本、余额三方自洽；赎回后份额归零时持仓状态不再是「持有中」
- 操作建议的有效期到期后，接受被拒绝且状态为已过期
- 接受建议时余额不足 → 接受失败，建议仍是待客户决定
- 接受建议成功后，产生不少于一笔交易且它经过了规则引擎

**要改写的既有断言**：

- `backend/tests/test_transaction_events_api.py` —— 入口从「只有内部接口」改为「客户侧受理 + 内部补录两条」，`_BrokenPublisher` 一类用例要在客户侧入口上重跑
- `backend/app/customer_assets/service.py:119` 的 `INNER JOIN` 一旦改动，`backend/tests/` 中所有断言流水条目数量的用例都要跟着看一遍
- `docs/adr/0009-compliance-guardrail-tests.md` 的护栏清单要加第 7 条

### Seam 2 — Vue 组件挂载

- 「交易」页渲染可用余额；三类操作各有入口与确认动作
- 余额不足、越级、未测评三种失败各自渲染对应文案（未测评的那条要能点到测评页）
- 「我的建议」页渲染待决定 / 已接受 / 已拒绝 / 已过期四种状态；有待决定项时角标出现
- 接受失败时渲染原因，且该条建议仍在待决定区
- 空状态：无建议、无交易、无持仓时都不留空白
- 内部侧审核队列同时渲染两类内容并各自带类型标注
- 客户经理侧能发起建议；放行 / 驳回入口在该角色下不存在
- 预警详情渲染来源标注

## Out of Scope

- **入金**（Q20）：余额只来自种子；也不做冻结、多币种、对账、利息
- 内部账户互转（转账的对手方只做外部收款人）
- 交易的部分成交、撤单、预约与定时执行
- 净值时间序列与净值波动（只有一个当前净值）
- 风评过期的处置（只提示，不拦也不引导强制重测）
- 客户经理建议行为的风险监测（Q6：建议类风控规则是后续扩展）
- 风控的事前阻断（Q5：只事后监测）
- 操作建议的收益预测、组合配置、多产品一次建议（Q9 的三条硬边界）
- 客户对建议的追问与二次沟通（只有接受与拒绝）
- 建议的推送通知渠道（沿用 `advisory-agent-and-review-flow` 与 `advisory-plan-visibility` 的排除）
- 资金的收益计算与结息

## Further Notes

- **这条需求表面上在讲「风控不起作用」，实际要补的是输入端。** 风控那一侧（规则、算子、分级、预警、工单）本来是完整的，缺的是「交易从哪来」。所以本 slice 的重心是客户交易，风控那部分反而只有接一根线和回放一遍。排查时不要从规则入手——先问有没有交易。
- **种子里那 5 笔历史交易绕过规则引擎，是一个只会在演示时暴露的裂缝。** 修它不是顺手，是必须：不修的话，「历史交易回放」这个动作本身就成立了反面教材。回放走同一个函数这条约束要写进测试，否则下一个人会为了「快一点」再写一个批量脚本。
- **回放会让演示的第一次操作直接落重度预警**（Q19）。这在答辩时是素材而不是缺陷——「这笔转账单看只是中度，但它叠加了该客户的历史预警记录，所以判重度」正是分级存在的理由。讲之前先想好这句台词。
- **`INNER JOIN fin_product` 那处改动是本 slice 最容易漏的地方**：漏了不会报错，只是转账记录在客户侧整行消失。改完后要有一条断言专门盯「流水里有转账」。
- **`operator_id` 为空表示客户自助发起，这是一条隐式约定。** 它现在是对的（客户自己下单没有经办员工），但没有任何机制拦着别人给它填值。`CONTEXT.md` 的「内部补录」与测试断言是它唯一的护栏。
- **建议与方案是同一条审核流水线，但产物不同。** 实现时若发现操作建议在复用方案的候选池快照、配置建议字段，说明边界破了——那两样东西是配置方案特有的，操作建议只有「一个产品、一个方向、一个金额、一条理由」。
