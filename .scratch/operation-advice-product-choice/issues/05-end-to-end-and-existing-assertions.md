# 05 — 端到端与既有断言收口

**What to build:** 把「经理选品选金额 → 顾问放行 → 客户看到 → 客户接受并部分赎回」串成一条能跑通的旅程，并把被这次改动推翻的既有断言逐条改对。改断言不是收尾杂活：这次改动动的正是原来那些断言所编码的行为，漏改一条就是一条**断言仍在通过、行为已经不同**的用例。

**Blocked by:** 04 — 客户经理的发起表单（03 亦须完成）

**Status:** implemented

- [x] 端到端：选品选金额发起 → 顾问放行 → 客户读到产品与金额 → 接受 → 成交（申购）
- [x] 端到端：部分赎回建议 → 客户接受 → 剩余份额与持仓状态正确
- [x] 断言：**可选项端点与发起受理对同一组输入给出同一结论**——调用的是同一个函数，用一条直接的断言钉住两个入口，而不是分别测两遍
- [x] 改写 `backend/tests/test_operation_advice_draft.py`（10 条）中受影响的用例
- [x] 改写 `backend/tests/test_end_to_end_customer_journey.py` 中「经理只提交方向」的路径
- [x] 核对 `docs/adr/0009-compliance-guardrail-tests.md`：**不新增护栏**——护栏 1 的执法方式收紧了，但范围本身一个字没变
- [x] 核对 `docs/roadmap.md` 的护栏分布表：同样不改
- [x] 审核页仍不渲染方案特有的字段（既有断言：边界没破）
- [x] 客户经理视角仍不存在放行 / 驳回入口（既有断言）

**注意：** 本次最主要的实现风险是「选品规则被表达两次」。收口时若发现前端也在按方向过滤或算买不买得起，回来删掉它——那处漂移的表现是「下拉里有这只产品，一提交被拒」，**不会有任何断言失败**，只有一条直接的「两个入口同一结论」断言能提前发现它。

**注意：** 端到端旅程若在其它用例里依赖「经理只提交方向」的旧契约（例如注册表的入口示例、Swagger 示例），一并核一遍。
