# 操作建议的产品与金额由发起人决定

Status: ready-for-agent

前置：`operation-advice-and-customer-trading`（操作建议链路的 `#06` 与 `#09`）、`customer-profiling-and-suitability`（候选池）

**本 slice 修改已实现的既有决定**（不是新增，是改动，实现时先读这两处）：

| 被改的既有决定 | 改动内容 |
|---|---|
| `operation-advice-and-customer-trading` 的 `#06`：「发起场景就是方向，产品/金额/理由由 Agent 给出」 | 发起表单从「客户 + 方向」变成「客户 + 方向 + 产品 + 金额（申购）/ 份额（赎回）」；业务操作 Agent 收窄为**只产出理由** |
| 同 `#06`：「金额只有一个来源：产品要素与持仓（申购取起投、赎回取全部份额）」 | 金额不再取下限或上限，改由发起人在后端给出的合法区间内填；**「成交口径只有一处」这条不变** |

**明确不改**的三条既有决定（实现时容易顺手改掉，列在这里当护栏）：赎回的产品范围仍是「持有 ∩ 候选池」；「生成的建议里产品全部来自候选池」仍是硬保证；金额与份额的合法性仍由受理侧的同一套口径算，前端不复算。

## Problem Statement

**客户经理能提的建议只有一半。**

发起建议的表单只有两个字段：客户与方向（`apps/internal/src/operation-advice/CustomerAdviceSection.vue:84-103`，请求体见 `backend/app/operation_advice/schemas.py:7`）。产品由 Agent 在候选池里按内部排序取第一只（`backend/app/operation_advice/graph.py:105-123`），经理既看不见有哪些产品可选，也表达不了「就这只」。

这件事的严重性在于：**这位客户是谁，是客户经理唯一比系统多知道的事**，而那个内部排序只用产品要素（`expected_return` / `term_days`，见 `graph.py:90-102`），对客户一无所知。系统把他最该做的那次判断拿走了，还给了一个他无法否决的答案。

金额更机械：申购固定取**起投金额**（`graph.py:121-122`），赎回固定取**全部份额**（`graph.py:150`）。一条「建议申购 1000 元」的建议看不出是对谁说的——起投金额是产品目录上的一个门槛数字，不是任何人对这位客户的判断。

赎回那一侧还留着一处隐性不一致。草案只存 `amount`、**不存份额**（`backend/app/db/models.py:892`），而客户接受时执行的是**接受那一刻的全部持仓份额**（`backend/app/operation_advice/decision.py:331`）。于是 `amount` 列只是一个会过期的展示值：它显示的成交金额与最终成交金额可以不等，而且不会有任何断言失败——这正是这类缺陷最难发现的地方。

而能力早就有了：受理侧的赎回**本来就支持部分赎回**（`backend/app/order_acceptance/service.py:250-267` 按份额比例同时减持成本与市值），客户侧自助赎回本来就是按份额填的、可以是部分（`backend/app/api/customer_transactions.py:31-38`）。缺的不是能力，是入口。

## Solution

**选品与金额回到发起人手里，业务操作 Agent 从「选品 + 金额 + 理由」收窄为「只写理由」。**

- **表单**：客户 → 方向 → 产品（在候选池内选）→ 金额（申购）或份额（赎回）。单位与客户侧自助交易同一口径：申购按金额、赎回按份额。
- **可选项的口径与现在 Agent 的两条选品规则完全一致**，只是把「Agent 自动取第一只」换成「人可选的集合」：申购 = 候选池 − 已持有，赎回 = 持有 ∩ 候选池。余额不足以覆盖起投 + 手续费的产品**仍然列出但禁用**，注明原因——直接藏掉会让经理以为候选池里少了一只。
- **可选项由后端算**，前端只渲染、只读 `affordable` 一个布尔，不自己按方向过滤、不自己算买不买得起。规则若在前端再表达一次，漂移的表现是「下拉里有这只产品，一提交被拒」，不会有断言失败。
- **合法区间由后端给**：申购的 `min_amount`（起投）与 `max_amount`（可用余额能覆盖的上限，走 `purchase_cost`），赎回的可赎回份额（持仓份额）。前端只用这两个数做输入约束。
- **赎回从「全部」变成「一个份额数」**：草案加一列存份额，接受时按那一列执行。副作用是「生成时的份额」与「接受时的持仓」之间有了时间差——份额不足现在是接受失败（与余额不足同一套语义），而不是静默按当下的全部成交。
- **理由照旧由 Agent 产出**：`purchase_reason` / `redemption_reason` 不动，它们只吃产品要素与客户自己的数字，每一句都能被顾问逐项核对。

**不动的东西**：产品仍必须来自候选池（护栏 1 的延续）；发起与放行仍是两个人；审核流水线仍是一条（ADR-0020）；金额的成交口径仍只有一处（`purchase_cost` / `redemption_amount`）。

## User Stories

### 客户经理

1. As a 客户经理, I want to 在发起建议时看到这位客户能选的合规产品有哪些, so that 我不必猜 Agent 会挑哪一只
2. As a 客户经理, I want to 指定这条建议针对哪只产品, so that 建议能对上我对这位客户的判断
3. As a 客户经理, I want to 自己填金额（申购）或份额（赎回）, so that 建议的分量是我的判断而不是一个默认值
4. As a 客户经理, I want to 在提交前就知道金额的合法区间, so that 我不会提交一条注定被拒的建议
5. As a 客户经理, I want to 看到买不起的产品并知道为什么不能选, so that 我不会以为候选池里少了一只
6. As a 客户经理, I want to 发起一条部分赎回的建议, so that 我不必只能建议客户清仓

### 理财顾问

7. As a 理财顾问, I want to 建议里的产品与金额来自发起人而不是模型, so that 我审的是一份人的判断加一份可核对的事实
8. As a 理财顾问, I want to 理由仍然引用这位客户自己的持仓与余额, so that 我能逐项核对
9. As a 理财顾问, I want to 赎回的建议带着一个具体份额数, so that 我知道客户接受后还剩多少

### 客户

10. As a 客户, I want to 收到具体的赎回份额而不是「全部」, so that 我知道这条建议执行后我还剩多少
11. As a 客户, I want to 建议生成之后我自己动过持仓时接受失败并给出原因, so that 我不会被静默地按当下的全部成交

### 合规负责人

12. As a 合规负责人, I want to 经理能选的产品仍然全部来自候选池, so that 护栏 1 不因为选择权移交而松动
13. As a 合规负责人, I want to 金额与份额的合法区间只由受理侧算出, so that 前端与受理不会漂移
14. As a 合规负责人, I want to 客户经理仍然无法放行自己发起的建议, so that 发起与放行不落进同一个人手里

### 开发者

15. As a 开发者, I want to 可选项与受理校验调用同一个函数, so that 两条规则不会各写一遍
16. As a 开发者, I want to Agent 的图里不再有排序与选品, so that 「谁选的」在代码里一眼可见

## Implementation Decisions

### 新增一个「可选项」读取端点，不动候选池端点

`GET /api/internal/customers/{customer_id}/candidate-pool`（`backend/app/api/suitability.py:27`）返回的是**候选池**，而候选池在 `CONTEXT.md` 里是一个与方向无关的合规事实（适当性硬过滤的结果）。把方向过滤与金额区间并进那个端点，会让它同时回答两个问题。

因此新增 `GET /api/internal/customers/{customer_id}/operation-advice-options?direction=申购|赎回`，返回该方向下的可选项：

```
{ "direction": "申购", "products": [
    { "product_code", "product_name", "product_type", "risk_level", "term_days",
      "min_amount", "max_amount", "affordable" } ] }
```

赎回方向的 `max_amount` 不适用，改为 `max_shares`（持仓份额）。

可选项的**组装函数与发起受理的校验函数是同一个**——这是本 slice 最主要的实现约束。前端做方向过滤就是第二次表达，而漂移不会报错。

### 请求体的形状

`OperationAdviceRequest`（`schemas.py:4-7`）增加字段：`product_code` 必填；`amount`（申购）与 `shares`（赎回）二选一，由 `direction` 决定哪个必填。与客户侧 `PurchaseRequest` / `RedemptionRequest` 同口径（`api/customer_transactions.py:31-38`）。

校验在 `generate_operation_advice` 里、编译图之前，与既有的 `_ensure_own_customer`（`operation_advice/service.py:37-42`）同一处：方向合法；产品在候选池内；方向资格成立（申购未持有、赎回已持有且份额大于零）；申购 `amount ≥ 起投` 且 `purchase_cost(amount) ≤ 可用余额`；赎回 `0 < shares ≤ 持仓份额`。

**校验不放进 `submit_transaction_event`**（ADR-0018 不变）：它仍然是既成事实的入海口。

### 图的变化

`select_product` 节点从「排序取第一只」变为「按给定的 `product_code` 加载产品、采用给定的金额或份额」。`_ranked`、`_purchase_selection`、`_redemption_selection`（`graph.py:105-150`）从这张图里消失——排序是「Agent 选品」的产物，选品权移交之后它没有存在的理由。`build_reason` 与 `reasons.py` 不动。

顺带要改的是三条错误文案（`graph.py:55-56`）：`NO_CANDIDATE_MESSAGE` / `NOT_ENOUGH_BALANCE_MESSAGE` / `NO_HOLDING_MESSAGE` 现在说的是「Agent 选不到」，而失败原因已经变成「发起人选的不合法」。文案必须跟着语义走，否则经理收到一个描述别人行为的错误。

### 赎回份额的持久化与兼容

`biz_operation_advice_draft` 新增可空列 `redeemed_shares`：

- 新写入的赎回建议**一律带份额**。
- 该列为空表示「全部赎回」，即改动之前的语义。这只服务改动之前已有的行——不是特例，是忠实于既有语义。`decision.py:331` 遇到空值时保持原有的「按当下的全部持仓份额」执行。

赎回的执行从 `_current_holding_shares(db, draft=draft)` 改为读草案里的份额。

### 前端

`CustomerAdviceSection.vue` 的表单加两个字段：产品（选完客户与方向后加载可选项）与金额 / 份额。选项文案含五要素（Q13）。买不起的选项 `disabled` 并注明「可用余额不足」。空态沿用既有两句文案，不改写。

客户经理视角仍然**没有**放行 / 驳回入口（`#09` 的既有断言）。审核页仍只渲染「一个产品、一个方向、一个金额、一条理由」——现在这个金额来自发起人，审核页不需要任何改动。

### 文档

- 新增 ADR-0021。
- `CONTEXT.md`：「操作建议」与「业务操作 Agent」两条词条各加一句——产品与金额由发起人选定，Agent 不裁量。

## Testing Decisions

沿用两个 seam。

### Seam 1 — 后端 HTTP 层

护栏相关：

- **发起时指定候选池外的产品被拒绝**（护栏 1 的延续——现在这条决定权在人手里，比 Agent 代劳时更需要断言）
- 申购已持有的产品、或赎回未持有的产品被拒绝
- 申购金额低于起投被拒绝；`purchase_cost(amount)` 超过可用余额被拒绝
- 赎回份额为零或超过持仓份额被拒绝
- 非名下客户的发起被拒绝，理财顾问与风控专员发起被拒绝（既有断言的延续）
- 客户经理调用放行接口被拒绝（既有断言的延续）

链路相关：

- **草案里的产品、金额 / 份额与请求里的完全一致**——断言 Agent 不再改变它们（这条替换掉原来「生成的建议里产品全部来自候选池」中「Agent 选品」的那半边）
- 理由仍只引用候选池要素与客户自己的持仓 / 余额，不含配置比例与收益预测（既有断言的延续）
- 可选项端点：申购方向不出现已持有产品；赎回方向只出现「持有 ∩ 候选池」；买不起的带 `affordable: false` 而不是消失
- **可选项端点与发起受理对同一组输入给出同一结论**（同一函数，一条断言钉住）
- 部分赎回：接受后剩余份额、成本与市值按比例减持，持仓状态仍是「持有中」
- 赎回建议生成后客户自己动过持仓导致份额不足 → **接受失败，建议仍在待客户决定**
- 改动之前的赎回建议（份额列为空）接受时仍按当下的全部份额成交

**要改写的既有断言**：

- `backend/tests/test_operation_advice_draft.py`（10 条）——凡断言「Agent 从候选池里挑了哪只」的，改为断言「提交的那只被原样采用」
- `AppError` 的三条文案（见上）被断言的地方
- 端到端旅程若走过「经理只提交方向」的路径，要补上产品与金额

### Seam 2 — Vue 组件挂载

- 选完客户与方向后渲染可选项，每项显示五要素
- 买不起的选项禁用并渲染原因
- 候选池为空 / 全部买不起时渲染两句既有空态文案，不留空白
- 未选产品或未填金额时提交被拦
- 提交请求体含 `product_code` 与 `amount`（申购）/ `shares`（赎回）
- 客户经理视角仍不存在放行 / 驳回入口
- 审核页仍不渲染方案特有的字段（既有断言：边界没破）

## Out of Scope

- 让顾问在审核页改产品与金额（本 slice 只在发起环节；顾问仍只能放行或驳回。要改这条得先加一张定稿表，见 `#06` 的「放行不产生第二份载荷」）
- 独立的候选池浏览面板（Q5）
- 放宽「赎回的产品必须在候选池内」这条硬保证
- 金额或份额的建议值、试算与推荐（Agent 不给数字建议）
- 一次建议多个产品或组合配置（三条硬边界不变）
- 入金、余额调整、资金冻结
- 净值时间序列（仍只有一个当前值）

## Further Notes

- **这次改动把业务操作 Agent 收窄了**：从「选品 + 金额 + 理由」变成「只写理由」。这是有意的，见 ADR-0021。若将来有人觉得「这个 Agent 什么都不干了」，先读那条 ADR——把数字交回模型，等于让顾问审一个没有依据的数字。
- **「选品的两条规则只在一个地方表达」是这次最主要的实现风险。** 可选项由后端算、受理校验也由后端算，两处必须调用同一个函数。放在前端做方向过滤就是第二次表达，而漂移的表现是「下拉里有这只产品，一提交被拒」，**不会有断言失败**——所以要用一条直接的断言把两个入口钉在一起。
- **`redeemed_shares` 为空表示「全部赎回」是既有语义，不是特例。** 这一列只为改动之前的历史行服务；新写入的赎回建议一律带份额。若有人把它读成「可选的全部赎回」，就会顺手给新行也写空值，那时 `decision.py` 的旧分支会被重新激活，而演示里看不出来。
- **赎回的 `amount` 列从此是可推导的值**（份额 × 净值，净值只有一个当前值），它不再有「过期」的问题。改动之前它才是会过期的——因为执行用的是当下的全部份额。
- 这条需求与「护栏 1」的关系值得讲清楚：把选品交给人的**不是放开范围**，反而是把范围检查从「Agent 顺手只挑池内的」变成「人可能挑池外的、必须明确拒绝」。范围本身一个字没变。
