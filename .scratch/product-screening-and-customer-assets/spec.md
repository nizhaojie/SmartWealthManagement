# 产品筛选与客户端资产页

Status: ready-for-agent

前置：`customer-profiling-and-suitability`（风险承受等级、候选池）

## Problem Statement

客户想知道「有哪些产品符合我的条件」，也想知道「我现在持有的到底是什么」。前者现在只能翻产品手册，后者只能看一份对账单上的产品名称列表——一堆名字，看不出自己的钱实际分布在哪些资产上、整体风险偏到哪一侧。

一个客户持有五只基金，可能自以为分散，实际上五只都重仓同一个行业。他手上的信息不足以发现这件事。

同时这里有一条容易越过的线：客户问「有什么年化 5% 以上的稳健型理财」，回答这个问题很自然会变成推荐——而向客户做推荐必须由持证人员经过审核，不能由系统直接给出。

## Solution

**产品筛选**：客户按客观已披露要素（风险等级、产品类型、期限、起投金额、业绩基准）过滤产品，得到符合条件的清单。清单**强制按产品代码排序**，不做任何评分、排名或适配性表述，并明确标注这不是推荐；同时提供「请顾问出具方案」入口，转为一份待审核的投顾内容异步处理（ADR-0005）。

候选池已经做过适当性硬过滤，因此客户看到的清单里不存在越级产品——不是列出来置灰，是根本不出现。

**资产页**：客户看到自己的持仓明细、总市值、持仓只数、风险承受等级，以及两张图——**实际配置**（钱实际分布在哪几类资产上）和**持仓按产品风险等级的分布**（整体风险偏向哪一侧）。持仓可逐层展开到底层资产，看清自己实际间接持有了什么。

## User Stories

### 客户 · 产品筛选

1. As a 客户, I want to 按产品类型筛选产品, so that 我能只看自己感兴趣的品类
2. As a 客户, I want to 按期限与起投金额筛选, so that 我能排除自己用不上的产品
3. As a 客户, I want to 看到每款产品的已披露要素（代码、类型、风险等级、业绩基准、期限、起投金额、费率）, so that 我掌握判断所需的客观信息
4. As a 客户, I want to 筛选结果里不出现超出我风险承受等级的产品, so that 我不会看上一个自己根本买不了的东西
5. As a 客户, I want to 看到明确的说明「这是符合条件的产品清单，不是推荐」, so that 我不会把一份清单误当成建议
6. As a 客户, I want to 清单不按收益率排序, so that 排在第一位的不会被我误读成「最好的」
7. As a 客户, I want to 在需要建议时有一个「请顾问出具方案」的入口, so that 我不是被拒绝，而是有一条明确的去路
8. As a 客户, I want to 提交方案请求后能看到它的状态, so that 我知道顾问有没有在处理
9. As a 客户, I want to 查看一款产品的详情, so that 我能了解它的完整要素
10. As a 客户, I want to 筛选无结果时看到明确提示与放宽建议, so that 我知道是条件太严而不是系统故障

### 客户 · 资产

11. As a 客户, I want to 看到我的持仓明细（产品、份额、成本、市值、盈亏）, so that 我掌握自己的资产状况
12. As a 客户, I want to 一眼看到持仓总市值与持仓只数, so that 我不必自己把表格里的数字加起来
13. As a 客户, I want to 看到我的钱实际分布在哪几类资产上, so that 我对自己的整体配置有直观印象
14. As a 客户, I want to 看到持仓按产品风险等级的分布, so that 我知道自己的整体风险偏向哪一侧
15. As a 客户, I want to 把一笔持仓逐层展开到底层资产, so that 我知道自己实际间接持有了什么
16. As a 客户, I want to 看到自己的交易流水, so that 我能核对每一笔申购与赎回
17. As a 客户, I want to 按时间与类型筛选交易流水, so that 我能找到某一笔特定交易
18. As a 客户, I want to 在没有任何持仓时看到友好的空状态而不是空白表格, so that 我知道系统正常只是我还没买

### 合规

19. As a 合规负责人, I want to 客户只能看到自己的持仓与交易, so that 客户可见视图的边界是硬的
20. As a 合规负责人, I want to 产品清单的排序键在服务端固定, so that 前端无法通过参数把它改成按收益率排
21. As a 合规负责人, I want to 筛选结果少于三条时「这不是推荐」的说明仍然显示, so that 结果越接近推荐时说明越不能省

### 开发者

22. As a 开发者, I want to 持仓穿透由数据库递归查询完成, so that 我不必在应用层写循环拉取
23. As a 开发者, I want to 两张图共用一套图表封装, so that 后续加图表不必重复处理主题与响应式

## Implementation Decisions

遵循 `docs/adr/`，核心是 ADR-0005（筛选不是推荐）与 ADR-0006（实际配置）。

### 筛选的排序键

排序键固定为产品代码，**在服务端写死，不接受客户端传入**。这一条是 ADR-0005 的直接落实：排序本身传递推荐语义，列在第一位的看起来就是最优的，所以排序键必须与优劣无关。

前端产品表格**不提供任何可排序表头**。这与 Element Plus 表格的默认习惯相反，需要显式关闭——而这正是后期「优化体验」时最容易被无意打开的地方，由护栏测试 4 守住。

筛选条件只允许客观已披露要素。不提供「适合我的」「推荐指数」一类条件。

### 「不是推荐」的说明

说明常驻，不因结果条数变化而隐藏。结果少于三条时结果事实上接近推荐，此时说明更不能省（ADR-0005）。

### 方案请求

「请顾问出具方案」产生一条待审核的投顾内容，进入理财顾问的审核队列（队列本身在 `advisory-agent-and-review-flow`）。本 slice 只负责创建请求与展示其状态，不负责生成内容。

### 实际配置

**实际配置由持仓聚合得出**，不读画像里的目标配置（ADR-0006）。客户端只展示实际配置；目标与实际的对比是投顾视角，在投顾那份 spec 中。

### 持仓穿透

沿产品的底层持有关系逐层展开，用数据库递归查询实现（ADR-0002：实际穿透深度通常两三层，递归查询足够且无同步延迟）。需要防御成环：产品间的持有关系若出现环，查询必须有深度上限并能报出异常，不能挂死。

### 图表

两张图，都在客户端资产页：

**实际配置** — 用饼图或环图。类别是资产大类，数量在四到六个之间，每个类别占比之和为整体，这正是饼图适用的形状（部分与整体、类别少、只读占比不做精确比较）。

**持仓按产品风险等级分布** — 用**横向条形图**，按 R1 到 R5 固定顺序排列，不按数值大小重排。理由：R1–R5 是有序类别，重排会破坏这个顺序所携带的信息；而条形的长度可以沿同一基线直接比较，饼图做不到。

两张图共用一套图表封装（在 `packages/shared`，它只承载图表壳与主题，不含业务语义，符合 ADR-0003）。配色不沿用 Element Plus 的主题色——UI 主色是单一色相，而分类数据需要色相拉开的调色板。**本组色板要做对比度校验，不靠肉眼挑**：本团队在上一个项目里踩过这个坑（单色化改造后图表系列失去辨识度，不得不返工）。

空状态与加载态要显式设计，不能让图表区域在无数据时留一块空白。

### 客户可见边界

持仓、交易流水、已签署文件、风险测评等级结论构成客户可见视图。客户侧接口只返回属于请求者本人的数据，且这个约束在服务端由身份推导，**不接受客户端传入的客户标识**。

## Testing Decisions

沿用两个 seam。

### Seam 1 — 后端 HTTP 层

- **产品清单按产品代码排序；传入任何排序参数都不改变顺序**（护栏测试 4 的服务端一半）
- C1 客户的筛选结果里不出现 R2 及以上产品（护栏测试 1 的延续）
- 客户 A 的凭证拿不到客户 B 的持仓或交易
- 请求体中伪造他人客户标识时，返回的仍是本人数据或被拒绝
- 持仓穿透返回正确的层级与底层资产
- 持有关系成环时穿透查询有界终止并报出异常，不挂死
- 无持仓客户的资产接口返回空集而非错误

### Seam 2 — Vue 组件挂载

- **产品表格不渲染任何可排序表头**（护栏测试 4 的前端一半）
- 「这不是推荐」的说明在结果为 1 条、2 条、20 条时都渲染
- 「请顾问出具方案」入口存在且可点击
- 资产页渲染总市值、持仓只数与风险承受等级
- 无持仓时渲染空状态，图表区域不留空白
- 风险等级分布图的类别顺序是 R1 到 R5，不随数值重排

图表的具体像素输出不做断言——测的是数据到图表配置的映射（类别顺序、系列数量、空数据处理），不是渲染结果。

## Out of Scope

- 产品推荐、排序打分、适配性表述（这些是投顾内容，在 `advisory-agent-and-review-flow`）
- 目标配置与实际配置的对比（投顾视角，同上）
- 集中度风险的识别与提示（需要穿透结果的进一步分析，同上）
- 方案请求的内容生成与审核流程
- 产品净值走势图（需要净值时间序列，本项目未建该数据）
- 真实申购、赎回、支付
- 产品对比功能

## Further Notes

这份 spec 有一个反直觉之处：**我们主动让产品列表变得更难用**——不能按收益率排序，不能按「推荐度」排，还要常驻一句「这不是推荐」。这不是疏漏，是 ADR-0005 的刻意结果。任何觉得「加个排序会更好用」的后续改动，都应该先去读那条 ADR。

图表配色是本 slice 里唯一一处已知会踩坑的地方，教训来自本团队上一个项目的真实返工。做图表时先跑对比度校验再落色值。
