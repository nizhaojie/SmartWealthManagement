# 风控监测 Agent

Status: ready-for-agent

前置：`internal-workbench-shell`（内部工作台外壳）

## Problem Statement

风控专员现在每天人工抽查交易流水。抽查意味着大部分交易根本没被看过，遗漏率高；而且「可疑」的判断散在每个人脑子里，同一笔交易不同的人可能给出不同结论。

更难的是分级：一笔五十万的转账单独看值得关注，但如果这位客户同时还在频繁交易、还有历史预警记录，它的严重程度完全不同。人工抽查很难把这些信号叠起来看。

还有一个不能出错的地方：风控判断如果交给语言模型去做，那么「这笔交易是否超过五万元」这种确定性的数值比较，就变成了一次概率性的推断。金额比较错一次，就是一次漏报。

## Solution

每笔交易事件进入系统时自动过一遍规则引擎，20 条反洗钱可疑交易识别规则逐条匹配，命中即产生**预警**。

**阈值判断不经过模型**（`CONTEXT.md` 对风控规则的定义）：规则是存储在库中的声明式条件——字段、运算符、阈值、预警等级——由代码中有限的算子求值。模型在这条链路上只负责把结果讲成人话，不负责判断。

预警分级由命中的规则数与历史情况共同决定：单条规则命中为轻度，多条交叉命中为中度，多条命中叠加历史预警记录为重度。

预警是**事实记录**，陈述「什么被触发了」；处置过程由它派生的**工单**承载，有受理人、状态与处置结论。预警产生后通过事件总线广播，其他 Agent 可据此调整行为。

## User Stories

### 风控专员

1. As a 风控专员, I want to 每笔交易都被自动检查, so that 不再依赖抽查
2. As a 风控专员, I want to 看到预警列表并按等级、状态、时间筛选, so that 我能先处理最严重的
3. As a 风控专员, I want to 看到一条预警触发了哪些规则, so that 我理解它为什么被标记
4. As a 风控专员, I want to 看到触发规则的具体依据（哪个字段、什么值、超过了什么阈值）, so that 我能快速判断是不是误报
5. As a 风控专员, I want to 看到关联的交易与客户信息, so that 我不必切换页面查上下文
6. As a 风控专员, I want to 看到这位客户的历史预警记录, so that 我判断这是偶发还是模式
7. As a 风控专员, I want to 看到预警的置信度, so that 我能据此排序
8. As a 风控专员, I want to 从一条预警派生工单, so that 处置过程有明确的载体与责任人
9. As a 风控专员, I want to 处置工单时必须填写理由, so that 每次流转都有据可查
10. As a 风控专员, I want to 把一条预警判定为已排除并说明原因, so that 误报能被关闭且原因留痕
11. As a 风控专员, I want to 升级一条预警, so that 超出我权限的情况能交上去
12. As a 风控专员, I want to 看到工单列表及其状态, so that 我掌握手头的工作量
13. As a 风控专员, I want to 用日常语言问「今天有哪些高风险预警」, so that 我不必自己组合筛选条件
14. As a 风控专员, I want to 预警详情页有独立 URL, so that 我能把它发给同事

### 理财顾问与客户经理

15. As a 理财顾问, I want to 我负责的客户触发重度预警时能知道, so that 我在出方案时会考虑这个情况
16. As a 客户经理, I want to 看到我名下客户的预警状态, so that 我在对接客户时心里有数

### 合规

17. As a 合规负责人, I want to 阈值判断由代码求值而非模型推断, so that 数值比较不会出错
18. As a 合规负责人, I want to 交易事件先落库再广播, so that 广播通道失败不会丢失交易记录
19. As a 合规负责人, I want to 预警的每次状态流转都记录处置人与非空理由, so that 处置过程可审计
20. As a 合规负责人, I want to 置信度只用于排序与展示而不用于自动关闭预警, so that 没有预警会被系统悄悄消化掉
21. As a 合规负责人, I want to 规则的阈值可调整且调整有记录, so that 监管口径变化时能及时响应且可追溯

### 开发者

22. As a 开发者, I want to 规则存在库中而非硬编码, so that 调整阈值不需要改代码发版
23. As a 开发者, I want to 规则的算子集合是有限且封闭的, so that 规则数据不能表达任意逻辑
24. As a 开发者, I want to 事件广播失败不影响交易与预警的落库, so that 核心链路不依赖广播

## Implementation Decisions

遵循 `docs/adr/`，核心是 `CONTEXT.md` 中预警、工单、风控规则、交易事件的定义。

### 规则是数据，算子是代码

规则存储在库中：字段、运算符、阈值、预警等级、权重。求值由代码中**有限且封闭的算子集合**完成——大于、小于、区间、计数、时间窗内聚合等。

这意味着规则数据无法表达任意逻辑：规则作者能配的只有算子支持的形状。这是刻意的——如果规则能表达任意逻辑，它实质上就成了存在数据库里的代码，既不可测也不可审。

需要实现的 20 条规则覆盖大额交易、同日累计、频繁交易、快进快出等场景。每条规则要能被单独启停。

**阈值判断的任何环节都不经过模型。** 模型只在预警产生之后参与，把结构化的命中结果讲成自然语言描述。

### 交易事件：先落库再广播

交易事件到达时先事务性写入，再向事件总线广播。广播失败记录日志但不回滚——交易记录不能因为广播通道的问题而丢失。

反过来也成立：订阅方收不到广播不会导致数据不一致，因为数据已经在库里，订阅方可以补查。

### 预警与工单的关系

**预警是事实记录**：什么规则在什么交易上命中了，带等级与置信度。它不承载处置过程。

**工单是流程载体**：受理人、状态、处置结论。一条预警最多派生一张工单；工单也可来自预警之外的源头（客户投诉、转人工）。

这个区分是本项目对需求文档的明确采纳（需求文档设计了两张表，`CONTEXT.md` 定义了两者关系）。实现时不要把工单的状态字段塞进预警表——那会让「预警是什么」变得含糊。

工单每次状态流转必须记录处置人与**非空理由**，空理由的流转请求被拒绝。

### 分级

- 单条规则命中 → 轻度
- 多条规则交叉命中 → 中度
- 多条命中且该客户有历史预警记录 → 重度

分级逻辑是确定性的代码，不经过模型。

### 置信度

预警带置信度，**仅用于排序与分级展示**。系统不会因为置信度低而自动关闭预警——任何预警的关闭都必须由人做出并留下理由。这条明确写出来，因为「低置信自动关闭」是一个很容易被当作优化提出的想法，而它会让预警被系统悄悄消化掉。

### 事件广播

预警产生后向事件总线广播，载荷含预警标识、客户标识、预警等级、命中的规则标识。

订阅方按需响应：投顾助手据此在生成方案时加入风险标记；智能客服据此准备应对客户询问。订阅方的具体行为在各自的 slice 中实现，本 slice 只负责广播。

### Agent 配置

作为运行时上的一份配置（ADR-0007），工具集包含预警查询、工单操作、规则查询。风控专员可以用自然语言提问，Agent 把问题转成对预警数据的查询——这条路径复用数据分析 Agent 的语义视图机制（ADR-0010），不另开一套。

### 界面

内部工作台的模块，落在既有外壳里：预警列表（可筛选）、预警详情（含命中依据、关联交易、客户历史）、工单列表、工单处置页、规则管理（查看与启停）。

预警详情页有独立路由。

命中依据要展示到字段与值的粒度——「金额 520000 ≥ 阈值 500000」，而不只是「命中大额交易规则」。风控专员靠这个判断误报。

## Testing Decisions

沿用两个 seam。

### Seam 1 — 后端 HTTP 层

- 20 条规则各自在构造的交易上正确命中与不命中（边界值各测一次：恰好等于阈值、刚好低于阈值）
- 单条命中产生轻度、多条交叉产生中度、多条加历史产生重度
- 预警的状态流转在理由为空时被拒绝
- 预警关闭必须有处置人，系统不自动关闭任何预警
- 交易事件在广播通道不可用时仍然落库，且预警照常产生
- 一条预警最多派生一张工单，重复派生被拒绝
- 工单可来自预警之外的源头
- 规则被停用后不再参与匹配
- 风控专员以外的角色调用处置接口被拒绝

规则求值作为纯函数单独测试——输入一笔交易与一条规则，输出是否命中。它无外部依赖，直接测输入输出。这与 `customer-profiling-and-suitability` 中置信度计算的处理方式一致。

### Seam 2 — Vue 组件挂载

- 预警列表按等级筛选后渲染的集合正确
- 预警详情渲染命中依据到字段与值的粒度
- 处置操作在理由为空时无法提交
- 工单状态流转后列表反映新状态
- 无预警时渲染空状态

## Out of Scope

- 反洗钱可疑交易报告的监管报送
- 规则的可视化编辑器（本 slice 只做查看与启停）
- 机器学习驱动的异常检测
- 实时流式交易接入（交易事件由接口提交）
- 客户风险评级的动态调整（预警只广播，是否影响画像由订阅方决定）
- 关联方与最终受益人分析
- 预警的自动聚合与去重

## Further Notes

这份 spec 里有两处是明确写给「将来想优化的人」看的：**阈值判断不经过模型**、**置信度不用于自动关闭预警**。两者都是很容易被当作改进提出的方向——「让模型来判断更灵活」「低置信的自动关掉能减少工作量」——而两者都会把风控从确定性系统变回概率性系统。

需求文档要求 20 条规则全部实现，评分表 Phase 4 占 20%。规则数量是硬性的，边界值测试的工作量也随之而来——把规则求值做成纯函数，这部分测试才写得动。
