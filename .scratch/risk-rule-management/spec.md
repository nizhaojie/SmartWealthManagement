**明确不改**（实现时最容易顺手改掉，列在这里当护栏）：

- 算子集合与字段集合仍是**有限且封闭**的（`operators.py:9-11`、`fields.py:3-8`）。本 slice 只让规则数据**能写**，不让它**能表达任意逻辑**。
- 求值仍是纯函数、仍不经过模型；预警分级仍只看命中条数与历史（`grading.grade_alert_level` 不读 `weight`，也不读规则自身的 `alert_level`）。
- 交易受理侧的校验仍只有一处（护栏 7）。
- 预警仍是事实记录：不做回算、不自动关闭、`rule_hits` 快照仍在命中那一刻固化（`alerting.py:363-364`）。
- 规则列表的排序键仍是 `rule_code` 升序，分页仍走 `PageParams`（ADR-0024）。

## Problem Statement

**规则管理页能调，不能加。**

`risk-monitoring-agent` 的用户故事 22 写得很清楚：「规则存在库中而非硬编码，**so that 调整阈值不需要改代码发版**」。这条承诺只兑现了一半——`PATCH /{id}/enabled` 与 `PATCH /{id}/threshold` 让专员能改既有规则的灵敏度，但 20 条种子是**唯一的规则来源**（`rules.py:84-322`）。专员想加一条本地口径的规则——比如「本公司客户单笔转账超过 30 万」——只能找开发改 Python 常量、出迁移、重启服务。规则数据的「存在库里」与「由专员维护」之间差着一个编辑器。

**而且现在有一个会崩的组合，任何人都挡不住。**

`fin_risk_rule` 的三条 CHECK 各自守住一列：`field` 属于 11 个、`operator` 属于 14 个、时间窗算子必须有 `window_hours`。但**没有任何地方校验这两列的搭配**。于是 `field = product_id`（取值是字符串 `"P001"`，`fields.py:149-150`）配上 `operator = gt`（阈值被 `_require_number` 归一化成 `Decimal`，`operators.py:240-249`）是合法的：两列各自合规，DB 收下，`POST /api/internal/transaction-events` 也收下。它直到**下一笔交易到达**才炸——`operators._gt` 拿 `"P001"` 去比 `Decimal`，`TypeError`，整笔交易的判定跟着失败（这正是 `operators.py:242-244` 明确说要挡在写入侧的那种故障）。

现在这条路径只有手改数据库才走得通，所以它是潜伏的。这个 slice 给了它一个按钮。

**还有一条界线的代价没被认下。**

规则一旦可以被删除，「删了之后历史怎么办」就不再是理论问题：`fin_risk_alert.rule_codes` 是 JSON 快照（预警本身不会坏），但 `fin_risk_rule_change` 有指向 `fin_risk_rule.id` 的外键，硬删会连带丢掉这张表的全部意义——而「阈值是监管口径的落点，说不清它是初始口径还是被谁调过」（`0015:13-14`）正是它存在的理由。

## Solution

**给风控专员一个规则编辑器，但只开放「组合」的自由度，不开放「表达」的自由度。**

- **创建**：四步表单 —— 分类 → 字段 → 算子 → 阈值。可选项**全部来自后端**（`GET /api/internal/risk-rules/schema`），包括每个字段允许配哪些算子、阈值该落在什么值域。专员能配出什么，完全由注册表划定；他不能配出新形状。
- **修改**：只能改「基本信息」（名称、规则分类、描述、预警等级、规则权重）。**判定形状（字段、算子、时间窗）对所有规则一律不可改**——要换判定方式就删除后重建（ADR-0026）。阈值与启停各有专门入口，各自单独留痕。
- **删除**：软删。行留在库里，列表默认过滤，可在「显示已删除」筛选下看到（置灰只读、可查看变更记录），但**不提供恢复**。
- **校验**：写入时当场三档校验——阈值形状与算子匹配（复用 `normalize_threshold`）、字段与算子互相允许、阈值落在字段的值域内。配错当场 400 并说清哪里错，不留到求值时炸，也不留一条「永远不命中」的规则在库里。
- **留痕**：五个 `change_type`（规则新建 / 规则修改 / 规则删除 / 阈值调整 / 启停变更），一次写操作一条记录，`old_value` / `new_value` 装整份快照，**理由一律必填**。

**清楚认下的代价：新规则从下一笔交易起生效，界面上看不到即时效果。** 不做回算（Q18），成功提示里要明说这一点。

**Q1 写下来是因为它在访谈里真的制造过一次混淆**：需求原话里的「规则可以限制几种类型（比如交易金额大于）」听起来像 `category`，但举的例子是「字段 × 算子」的组合。这两层在库里都是列，在界面上都是下拉，而在 `CONTEXT.md` 里只有前者没有词条。钉子见 `CONTEXT.md` 的「规则分类」。

**Q18 写下来是因为它与「新建一条规则」的直觉相反**：专员点完新建，预警列表里什么都不会发生。四条理由：(1) `create_alerts_for_event` 不是幂等的——它不检查这笔交易是否已有预警（「一笔交易最多一条预警」说的是单次调用内），回放两次就会产生两条预警并各广播一次；(2) 分级读 `_customer_has_prior_alert`，先回算哪一笔决定了后面那一笔算不算「有历史」，同一批交易按不同顺序回放会得出不同的重度/中度；(3) 与 `alerting.py:363-364` 「依据在命中这一刻固化……」那条注释直接冲突，且库里没有任何字段能标出「这条预警是补算的」；(4) 阈值调整不回算已是既有行为，两条路不一致会让「我改了为什么没生效」反复出现。

**Q2 与 Q4 合起来是一条界线**：可写的是**组合**（在给定字段、算子、值域里挑），不可写的是**表达**（拼逻辑、造新算子）。前者让规则从 20 条变成专员能自己维护的配置，后者会让规则数据变成存在数据库里的代码——`operators.py:9-11` 与 `fields.py:3-8` 两处开篇都写着这件事。

## User Stories

### 风控专员

1. As a 风控专员, I want to 新建一条规则并自己选分类、字段、算子与阈值, so that 本地口径的规则不必再等开发改代码发版
2. As a 风控专员, I want to 在选字段之后只看到这个字段能配的算子, so that 我不会配出一条下一笔交易就会炸的规则
3. As a 风控专员, I want to 在提交时就被告诉阈值哪里不对, so that 我不会留下一条永远不命中的规则
4. As a 风控专员, I want to 修改一条规则的名称、规则分类、描述、预警等级与规则权重, so that 规则的口径表述能跟上业务
5. As a 风控专员, I want to 删除一条不再适用的规则并写下理由, so that 规则集不会无限膨胀
6. As a 风控专员, I want to 看到某条规则被谁在什么时候因为什么改过, so that 我能解释它现在的样子
7. As a 风控专员, I want to 看到已删除的规则及其变更记录, so that 删除这件事本身也可查
8. As a 风控专员, I want to 知道新规则从下一笔交易起才生效, so that 我不会以为它没起作用

### 合规负责人

9. As a 合规负责人, I want to 每次写操作都必须填理由, so that 没有一次规则变更来路不明
10. As a 合规负责人, I want to 删除是软删而不是抹除, so that 历史预警与变更记录都还能解析出规则名
11. As a 合规负责人, I want to 规则编号永不复用, so that 历史预警快照里的 `R0xx` 永远指向同一条规则
12. As a 合规负责人, I want to 规则的判定形状不可改, so that 改过的规则不会顶着旧编号解释旧预警
13. As a 合规负责人, I want to 规则数据只能表达注册表内的组合, so that 规则库仍然可测、可审
14. As a 合规负责人, I want to 只有风控专员能写规则, so that 判定口径不会被任意角色改动

### 开发者

15. As a 开发者, I want to 字段与算子的可选项由后端下发, so that 前端不会成为注册表的第四份副本
16. As a 开发者, I want to 校验复用 `normalize_threshold` 与字段元数据, so that 写入侧与求值侧不会各有一套口径
17. As a 开发者, I want to 种子只在建库时播种一次, so that 专员删掉的规则不会在下次启动时复活

## Implementation Decisions

### 参数清单（Q14）

| 参数 | 库约束 | 表单 | 规则 |
|---|---|---|---|
| `rule_code` | NOT NULL / unique | 不出现 | 系统分配 `R%03d`，只读 |
| `rule_name` | NOT NULL / 128 | 文本，必填 | 去空白后非空，≤ 128 字 |
| `category` | NOT NULL，本 slice 补 CHECK | 下拉，必选 | 7 选 1，**无默认** |
| `description` | NOT NULL / Text | 文本 | **可留空，留空自动生成** |
| `field` | NOT NULL / CHECK 11 | 下拉，必选 | 11 选 1，无默认 |
| `operator` | NOT NULL / CHECK 14 | 下拉，必选 | 按所选字段过滤后的算子集，无默认 |
| `window_hours` | 可空；时间窗算子必须非空 | 数字框 | **仅时间窗算子出现**，必填正整数；其余算子提交时置 NULL |
| `threshold` | NOT NULL / JSON | 按算子形状渲染 | 必填（`value` 或 `min` + `max`） |
| `alert_level` | NOT NULL / CHECK 3 | 下拉，必选 | **无默认**（它不参与分级，只进命中依据） |
| `weight` | NOT NULL | 数字框 | **可填，默认 1.00，区间 [0.50, 5.00]** |
| `enabled` | NOT NULL，默认 1 | 开关 | **默认启用** |

`description` 留空时的自动生成沿用 `evaluator` 拼 `evidence` 的口径：`{作用域}{字段标签}{算子的 measure} {符号} 阈值 {阈值文本}`，例如「7 小时内交易金额的笔数 ≥ 阈值 10」。作用域里时间窗算子写作「{window_hours} 小时内」、自然日算子写作「同日」、单笔算子留空（`evaluator._scope_text`）。

### 写入侧三档校验（Q8）

追加在既有的 `normalize_threshold` 之前，按顺序：

1. **名录**：`category` ∈ 7 个分类常量；`field` ∈ `FIELD_KEYS`；`operator` ∈ `OPERATOR_KEYS`；`alert_level` ∈ 3 个等级。
2. **搭配**：`(field, operator)` 必须落在允许矩阵内。矩阵是新增的一份显式声明（放在 `fields.py` 或 `operators.py` 的一张表里），不在 `if` 里推。
   - 取值不是数值的字段（`product_id`）只允许不比较数值的算子（时间窗去重计数）；
   - 取值语义是「小时」「百分比」「等级差」的字段，不允许求和类聚合；
   - 其余组合照旧。
3. **值域**：阈值必须落在该字段的物理值域内——`hour_of_day` ∈ [0, 23]，`risk_level_gap` ∈ [-4, 4]，`amount_to_assets_ratio` > 0，`reverse_interval_hours` > 0，金额类字段 > 0。

值域与搭配矩阵都要能被 `GET /schema` 读出来，前端据此把不可能的选项直接禁掉；**但后端必须是唯一裁判**——前端禁掉的选项与后端拒掉的组合一旦漂移，表现是「下拉里能选、一提交被拒」。

### 接口

新增：

- `GET /api/internal/risk-rules/schema` —— 分类、字段（label / description / 允许的算子 / 值域）、算子（label / symbol / scope / `threshold_keys`）。门控跟列表走 `require_internal`。
- `POST /api/internal/risk-rules` —— 创建。请求体是全部可填参数 + `reason`。
- `PATCH /api/internal/risk-rules/{id}` —— 修改基本信息（名称/分类/描述/等级/权重）+ `reason`。**不接受 `field` / `operator` / `window_hours` / `threshold` / `enabled`**，带了就 400（不接受比静默忽略更能说清界线）。
- `DELETE /api/internal/risk-rules/{id}` —— 软删 + `reason`。

保留不动：`PATCH /{id}/enabled`（理由由「可空」收紧为「必填」）、`PATCH /{id}/threshold`（唯一改阈值的入口）、`GET ""`、`GET /{id}/changes`。

列表加一个查询参数 `include_deleted`（默认 `false`）。**必须在服务端过滤**——前端过滤会让分页总数对不上（ADR-0024）。

全部写接口门控 `require_employee_role(RISK_OFFICER)`，与既有两个 `PATCH` 一致。

### 数据层（迁移 0032）

- `fin_risk_rule` 加 `deleted_at DATETIME NULL` + 索引。
- `fin_risk_rule` 补 `ck_risk_rule_category` CHECK，清单与 `rules.py` 的 7 个分类常量一致。
- `fin_risk_rule_change` 的 `ck_risk_rule_change_type` 扩为 5 个值。
- `enabled_rule_specs`、`list_rules`、`rule_code` 分配（取 `max(rule_code)`，**不过滤软删行**）三处都要认 `deleted_at`。

`_seed_risk_rules` 改为「表为空才播种」：判断用 `count(*)` 而**不是** `count(*) where deleted_at is null`——20 条全被软删后表仍非空，若按后者判断会重新播种并撞 `uk_risk_rule_code`，服务起不来。

### 前端（`apps/internal/src/risk/RiskRulesTab.vue`）

- 「新建规则」按钮 → 对话框，四步表单按分类 → 字段 → 算子联动，阈值输入按算子的 `threshold_keys` 渲染。
- 「编辑」按钮 → 同一对话框：编号只读，判定形状与阈值四项控件只读，并附一句「要改判定形状请删除后重建，要改阈值请用『调整阈值』」。
- 「删除」 → `ElMessageBox.prompt` 收理由（`inputValidator` 强制非空），成功后就地刷新。
- 启停开关 → 改为「点一下先弹理由」，与删除同一个 prompt 范式。
- 「显示已删除」筛选（默认关）；已删行置灰、只读、只留「查看变更记录」。
- 「查看变更记录」 → 只读对话框，渲染 `GET /{id}/changes`（**这个接口此前没有前端入口**）。
- 新建成功的提示必须带「新规则从下一笔交易起生效，历史交易不会被重新判定」。

## 验收标准

**规则可写（后端）**

- 创建一条合法规则：库中出现该行、`rule_code` 按序列分配、`fin_risk_rule_change` 多出一条「规则新建」且理由非空
- 创建时 `category` / `field` / `operator` / `alert_level` 任一不在名录 → 400
- 创建 `field = product_id` + `operator = gt` → 400（搭配校验），**且库里不落行**
- 创建 `field = hour_of_day` + `threshold = 30` → 400（值域校验）
- 创建 `threshold` 形状与算子不匹配 → 400（复用既有 `normalize_threshold`）
- 创建时间窗算子但不给 `window_hours` → 400；非时间窗算子带 `window_hours` → 落库为 NULL
- `description` 留空 → 落库为自动生成的那句话
- `PATCH /{id}` 带 `field` / `operator` / `window_hours` / `threshold` / `enabled` 任一 → 400
- `PATCH /{id}` 只带 `rule_name` → 变更记录里 `old_value` / `new_value` 是整份快照，而非只有名称
- 理由为空的创建 / 修改 / 删除 / 阈值 / 启停 → 全部 400
- 非风控专员调用任一写接口 → 拒绝

**删除与编号**

- 删除后：列表默认查不到；`include_deleted=true` 能查到且带软删标记
- 删除后：该规则的 `GET /{id}/changes` 仍可读，历史预警详情不受影响
- 删除后新建一条规则 → 拿到的是**曾经的最大编号 + 1**，不是被删掉的那个编号
- 该规则的 `fin_risk_rule_change` 行仍在（软删没有级联删掉留痕）

**种子语义**

- 建库后规则表非空；重启服务不新增也不改写任何行
- 把 20 条全部软删后重启 → **表仍为空判断为假**，不重新播种、不报 `uk_risk_rule_code` 冲突

**不回算（Q18）**

- 新建一条「单笔金额 ≥ 1」这种必然命中的规则后，**已有交易不产生任何新预警**
- 该规则在下一次 `POST /api/internal/transaction-events` 时正常命中并产生预警
- 前端新建成功的提示包含「从下一笔交易起生效」

**前端（Seam：Vue 组件挂载）**

- 选完字段后算子下拉只剩允许的那几个
- 阈值输入框的数量与键名随算子变化（`gte` 一个、`between` 两个）
- 编辑对话框里判定形状与阈值共四个控件是只读的
- 删除对话框理由为空时无法提交，且错误提示就地出现
- 「显示已删除」打开后已删行置灰且没有编辑按钮
- 变更记录对话框渲染出 `old_value` → `new_value`

## Out of Scope

- **对历史交易回算**（Q18=A）：回放不是幂等的、会扰动分级、会凭空广播，要做也是一条独立 slice（要幂等键、「是否补算」标记、广播豁免）
- **恢复已删除的规则**：删除是终态，`enabled` 已经承担了可逆的「让它不生效」
- 新增字段或算子（要改代码 + 出迁移，`operators.py:9-11`）
- 多条件组合（AND / OR）与规则表达式编辑器
- 规则的复制、导入导出、批量启停
- 规则生效时间窗（「从某日起生效」）与版本化
- 规则的可视化命中率统计
- 规则的审批流（本 slice 的写入口只对风控专员开放，写入即生效）

## Further Notes

**这个 slice 给「规则存在库中而非硬编码」这句承诺补上后半句。** 前半句（可调）在 `risk-monitoring-agent` 就兑现了，所以那时的边界是「只做查看与启停」——一个只有读与两个 `PATCH` 的模块，不需要回答「规则的身份是什么」。一旦规则可以被创建和删除，那个问题就必须回答：改了什么就不再是同一条规则？删掉之后历史怎么解释？编号能不能回收？这三件事分别落在 ADR-0026 与 ADR-0027。

**最容易被当作优化提出的两件事，提前写在前面。**

第一件是「回算历史交易」——新建规则后看不到效果确实别扭，但回放会同时撞上幂等、分级顺序与广播三处，而且它会让「预警是事实记录」变成「预警是定期重算的结论」。要做就单独做。

第二件是「把字段和算子也放开让专员改」——这会让 `fin_risk_rule` 变成一张能表达任意逻辑的表，`operators.py` 与 `fields.py` 两处开篇写的「封闭集合」随之失效，护栏 3（只许只读查询）那一类为了防注入而存在的东西会在规则引擎上重演一遍。规则能配的是组合，不是表达。

**一处已知的不一致，认下而不是假装没有**：`PATCH /{id}/enabled` 的理由从可空收紧为必填，是为了让五个 `change_type` 的留痕形状一致；代价是列表里那个开关从「一下点开」变成「点一下先弹框」。如果你更看重开关的手感，「启停变更」可以退回理由可空——那时它会是五个类型里唯一一个理由可空的，而这需要在 `CONTEXT.md` 之外的地方也写清楚，否则下一个人会把它当漏写补上。
