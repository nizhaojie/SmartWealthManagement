# 数据分析 Agent 的查询只作用于语义视图，不触及基础表

需求文档的做法是把基础表的建表语句注入模型，让它直接对基础表生成 SQL。本项目改为预先定义一组**语义视图**——已脱敏、内置行级权限过滤的只读视图——模型只看得到视图，生成的查询也只能作用于视图。

## Considered Options

- **按文档字面做，注入基础表 DDL**——被拒绝。脱敏与权限过滤就只能靠「提示词里嘱咐模型别查身份证号」和「事后正则检查生成的 SQL」，两者都是概率性的防线。一次提示词注入或一次模型不听话，就是一起数据泄露。
- **注入基础表但在执行前做 SQL 解析与重写**——被拒绝。要正确处理子查询、JOIN、CTE、函数调用中的字段引用，等于自己写一个 SQL 分析器，而任何一处解析疏漏都是漏洞。
- **只做只读账号 + 正则黑名单**——被拒绝。只读账号挡得住写操作，挡不住越权读取；正则黑名单挡关键字，挡不住 `SELECT * FROM` 一张含敏感字段的表。

## Consequences

安全性从概率变成结构：敏感字段不在视图里，因此无论模型生成什么查询都取不到；行级权限内建在视图定义中，因此「查别人的数据」这件事在 SQL 层就不成立。正则校验仍然保留，但它退化为第二道防线而不是唯一防线。

代价是每类分析需求都要先有对应的视图。视图没覆盖的问题，Agent 答不上来——这是刻意的：宁可答不上来，不可越权答出来。视图集合会随需求增长，这部分维护成本是这个决定的常态开销，不是临时成本。

另一项后果是需求文档提到的「动态 Schema 筛选」（按关键词只注入相关表的 DDL）仍然需要，但对象从基础表变成视图。
