# 三层记忆的分层判据是信息的生命周期与权威来源，不是存储技术

记忆分三层，但分层不按「存在 Redis / MySQL / Milvus」来划，而按两个问题来划：

1. **这条信息活多久**——它只在一次会话内有效，还是跨会话存在，还是长期稳定。
2. **谁是它的权威来源**——它是对话本身产生的，还是某个业务流程写下的，还是外部知识导入的。

由此得到三层：

| 层 | 内容 | 生命周期 | 权威来源 | 读取方式 |
|---|---|---|---|---|
| 短期记忆 | 当前会话的消息列表 | 一次登录的会话，滑动过期（`chat_memory_ttl_minutes`），总量受 token 预算约束 | 本次对话本身 | Redis 列表，超预算时截断最旧消息 |
| 中期记忆 | 客户画像、工单状态 | 跨会话存在，但会被业务改写 | 画像由离线计算产生、工单由流程流转产生，均落在 MySQL | 画像走 Cache-Aside，工单直接查库（热点可加缓存，但缓存不是权威） |
| 长期记忆 | 知识向量、图谱、原始文档与知识元数据 | 长期 | 知识元数据（MySQL）为权威，Milvus / Neo4j / MinIO 都是它的投影 | 检索与多跳查询，投影可全量重建 |

## 新增一类信息时的判据

依次问三个问题：

- 它是否随会话结束而失去意义？是 → **短期记忆**。
- 它跨会话存在且会被业务改写、有明确的写入方？是 → **中期记忆**。
- 它长期稳定、由知识导入或全量重建产生、只读？是 → **长期记忆**。

存储技术是实现细节，可以随性能与运维需要替换（例如短期记忆从 Redis 换成别的缓存，不改变分层）。

## Consequences

**会话归档不属于三层记忆。** 会话结束后短期记忆仍按 TTL 过期，归档是留给合规举证的只读留痕（`conversation_archive`），不参与上下文组装，也不会被读回对话。把它当作「第四层记忆」会让「为什么这句话没进上下文」与「归档里明明有」产生混淆——归档回答的是「当时发生了什么」，而不是「系统现在记得什么」。

**置信度也不是一层记忆。** 它是中期记忆（画像标签）上的一个派生数值，按 ADR-0011 接受明确的时间基准计算，不单独存储为独立的一层。

**缓存永远不是权威。** 画像缓存与工单热点缓存只是加速，失效时直连 MySQL（Cache-Aside）；缓存不可用不影响正确性。长期记忆的向量与图谱同理，它们是投影，坏了按 `docs/adr/0002` 的规则从 MySQL 全量重建。
