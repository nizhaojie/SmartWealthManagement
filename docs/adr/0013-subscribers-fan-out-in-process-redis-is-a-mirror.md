# 事件协作是进程内的订阅扇出，Redis 只是出站镜像

需求文档把多 Agent 协定的实现写成「基于 Redis Pub/Sub 的跨 Agent 事件通信」，并画了
一张「风控 publish → Redis → 投顾订阅 / 客服订阅」的时序图。本系统只有一个后端进程，
四个 Agent 是同一套运行时上的四份配置（ADR-0007），因此这条时序图在部署上退化成
「自己发给自己」；而 Redis Pub/Sub 是 fire-and-forget，订阅方离线期间的消息直接丢失。

于是需要明确：**协作靠进程内的订阅扇出落地，Redis 广播是出站镜像。**

## 决定

1. **订阅关系收在注册表里**（`Subscriptions`：事件类型 → 订阅方列表）。发布方按事件
   类型从注册表取订阅方，不认识具体订阅方。新增一条协作只是往注册表加一条，发布方
   一行都不用改。

2. **发布方先出站、再分发给本进程的订阅方。** 出站失败（Redis 掉线、配错地址）只记
   日志，既不回滚、也不阻断进程内的分发——本进程的订阅方与出站通道是两件事，通道抖动
   不该让同一进程里的协作也停下来。这是「事件总线不可用，核心链路继续」的落点。

3. **订阅方逐个隔离失败。** 一位订阅方抛错只记日志（日志里带订阅方名字），不影响其余
   订阅方，也不上抛给发布方：发布方的请求此时已经成功了。

4. **订阅方另开自己的数据库会话**（绑定同一个引擎），不共用发布方请求的事务。共用会
   让「听众写失败」把发布方的事务也拖进失败状态，而这正是要隔离的东西。

5. **订阅方写下自己的「风险关注」记录**（`biz_risk_focus`），而不是去读发布方的表。
   投顾读关注记录加风险标记，风控读关注记录看客服察觉到的高风险意图——发布方与订阅方
   之间没有共享的读模型。

6. **关注记录不存原始事件载荷**，只留读取方要看的那几样：谁提的、提醒什么、什么时候、
   什么等级。存下整份载荷等于把「广播是通知」悄悄改成「广播是数据通道」，而事件既不保证
   送达也不重放（spec 的 Out of Scope）。需要完整追溯时回到权威来源——预警在
   `fin_risk_alert`，对话原文在会话归档。

## Consequences

**进程内分发是同步的**，因此「广播之后订阅方已经处理完」可以被直接断言，HTTP 层的行为
测试不需要等待、轮询或引入假时钟。这是选择同步扇出而非后台消费线程的主要理由。

**事件不保证送达，也不重放。** 广播漏了就少一条关注记录。这与 spec 的 Out of Scope
一致（「事件的持久化与重放」不在范围内）：协作是增强，核心链路不依赖它，权威事实仍在
各自的表里（预警在 `fin_risk_alert`），需要补查时回到权威来源，而不是让关注记录承担
第二份真相。

**多实例部署时每条关注记录会写多份**，因为每个实例都会收到同一频道上的广播并各自落库。
去重与分布式锁不在本 slice 的范围内（spec Out of Scope 明确不做多实例与水平扩展）；
真要上多实例时，先补的是订阅侧的去重，而不是把分发挪回 Redis。
