# 分块正文镜像到 MySQL，支撑关键词检索

需求文档 F5.3 要求「Milvus 检索超时（超时阈值 2s）→ 降级为 MySQL LIKE 关键词检索」。
但分块正文此前只存在 Milvus 里，`fin_knowledge_meta` 只存元数据——没有正文，MySQL
里根本没有可 LIKE 的对象。降级路径要成立，正文必须在向量库之外还有一份。

> **修订（2026-09-22，见 ADR-0022）**：关键词检索从「只在降级时使用」升级为一等召回臂
> （正常路径与向量并行召回、RRF 融合），打分从「LIKE 命中字词占比」换成 `rank_bm25`
> 的 BM25，「Milvus 是唯一检索面」随之调整为「Milvus 是向量检索的权威面」。本 ADR 的
> 第 1、3、4 条（新增镜像表、可见性按文档状态过滤、镜像写入失败即入库失败）**全部不变**。
> 下方「决定」与「Consequences」按修订后的口径重述。

## 决定

1. **新增 `fin_knowledge_chunk`：分块正文的 MySQL 镜像。** 入库时与向量写入在同一
   个 store 阶段完成，一起成功或一起失败（失败时镜像行一并清掉）。

2. **Milvus 是向量检索的权威面（authoritative for vector retrieval）。** 镜像不做
   向量相似度检索；但自 ADR-0022 起它承载关键词召回（BM25），正常路径与向量**并行**
   读取，不再只在向量超时时被读。「哪些分块可见」仍由文档状态在两边同时决定。

3. **可见性口径两边一致：按文档状态过滤。** 删除文档只把
   `fin_knowledge_meta.status` 置为 expired，镜像行保留；关键词检索与向量检索一样
   join 文档状态并只取 active。两套存储的「哪些分块可见」由同一个字段决定，不会
   因为降级而让已删除的文档复活。

4. **镜像写入失败即入库失败。** 它不是为了性能而冗余的副本，而是降级路径的前提；
   允许它缺失等于允许「超时之后什么都查不到」，那降级就没有意义。

## Consequences

**多一份正文存储，占用与一致性成本都由入库这一个写入点控制。** 全仓没有第二处写
分块的地方（没有增量更新、没有重灌流程），所以漂移的来源只有一个：绕过入库直写
Milvus——现状不存在，将来引入时必须同时补镜像。

**关键词检索与向量检索互补，不再是「质量更低的那条路」。** 打分在 ADR-0022 之后是
`rank_bm25` 的 BM25 分（此前是「查询切出的二字词命中了几个」的占比），它作为一等召回臂
参与正常路径的 RRF 融合。`ChunkResult.source` 如实标出命中来源（`vector` / `keyword` /
`hybrid` / `graph`）；本 ADR 早期版本写的「降级结果的 `source` 仍标 `"vector"`」与代码
不符，一并更正——那个字段区分的是命中路径，不是算分方式。

**另有一处已知代价：如果镜像缺失（例如迁移前入库的文档），超时降级会返回空结果，
回落到「检索不到依据」的兜底话术。** 这是可接受的：宁可明确说查不到，也不拿无关
片段充数。迁移不批量回填历史分块——回填需要重新解析原始文档，成本落在启动路径上
不划算；重新入库一次即可补齐。
