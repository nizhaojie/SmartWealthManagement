# 业务校验属于交易受理，交易事件入海口不承载它

客户可以直接申购、赎回、转账，这些操作要过适当性、余额、起投金额、产品状态等校验。我们把这些校验放在客户侧的交易受理服务里，在交易落库之前完成；风控的交易事件入海口（`submit_transaction_event`）**保持窄口**——只做类型与主体存在性检查，然后老老实实做「落库 → 广播 → 过规则」三步。

理由：风控的输入是**既成事实**。让它去管适当性与余额，会让「监测」与「受理」两种职责混在一个函数里，并且直接造成两个后果——外部系统报进来的既成交易会被业务规则挡在门外，内部补录也会因为一条适当性规则而无法修复数据。

## Consequences

- 内部补录的交易因此可以越级、可以超过余额。这是刻意的，代价是它必须收窄：只对风控专员开放，且补录必带经办员工——客户自己发起的交易没有经办员工，这是分辨两者的唯一依据（见 `CONTEXT.md` 的「内部补录」）。
- 「交易事件」这个词从此专指风控视角的输入，不是「客户下单」的同义词；客户下单是交易受理，两件事的边界就在这里。
- 以后再加业务校验（限额、冷静期、双录），加在受理侧，不要往入海口塞。
