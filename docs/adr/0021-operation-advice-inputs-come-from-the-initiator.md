# 操作建议的产品与金额由发起人决定，Agent 只写理由

客户经理要为名下客户发起一条操作建议。产品与金额原来由业务操作 Agent 在候选池内定：申购取「排序最靠前、且买得起」的那一只、金额取起投金额，赎回在「持有 ∩ 候选池」里取一只、金额取全部份额。我们改为**由发起人在候选池内选定产品与金额，Agent 只就这两个输入产出理由**。

理由是：产品与金额是同一类判断——「给这位客户配哪只、配多少」——而做这个判断需要的上下文（这位客户是谁、他为什么来）只存在于客户经理那里，候选池里的产品要素里没有。让 AI 选品又让 AI 写理由，顾问审的就是两份模型输出；把产品与金额交回人，顾问审的是一份人的判断加一份可核对的事实。项目一贯的纪律也是把数字交给确定性来源而不是让模型编一个（「阈值判断不经过 LLM」、「金额只有一个来源」、「Agent 不重新做适当性判断」）。「AI 不选品」听起来像把 Agent 掏空：并没有——它产出的正是顾问真正要审的那份东西，即理由。

## Consequences

- ADR-0017 的分工不变（产物仍是单笔操作建议），但业务操作 Agent 的职责收窄为「就发起人选定的输入产出理由」。以后再加 Agent 时先看这条：**这个项目的 Agent 不在对外建议里自行决定金额**。
- 候选池仍是唯一的产品范围（护栏 1 的延续）。选择权移交不等于范围放开——正因为人可能挑到池外，服务端在受理前必须再校验一次，这条校验比 Agent 代劳时更需要断言。
- 金额与份额的合法区间只由受理侧的成交口径算出（`purchase_cost` / `redemption_amount`），前端只使用后端给出的上下限，不复算费率。
- 选品规则因此只剩一处表达（组装可选项的函数）。前端若再做一次方向过滤，漂移的表现是「下拉里有这只产品，一提交被拒」，不会有断言失败。
- 赎回建议从「全部份额」变成携带一个具体份额数（草案新增一列），接受时按它执行。生成与接受之间客户自己动过持仓时，结果是接受失败而不是静默按当下的全部成交。份额列为空表示改动之前的语义。
- 「一次只对应一个产品一个方向、金额必填、禁止收益预测与配置比例表述」三条硬边界不变。
