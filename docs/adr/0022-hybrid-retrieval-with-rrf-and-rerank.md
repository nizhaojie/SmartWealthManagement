# 检索改为「向量 + BM25 混合召回 → RRF 融合 → LLM 重排」，图谱仍是增强

知识检索原来只有向量一路：关键词检索（`backend/app/knowledge/service.py` 的 `keyword_search_chunks`）只在 Milvus 超时或不可用时作为降级出现，正常路径一次都不碰它（ADR-0014）。但中文财务问句里有相当一部分判别信号是**字面**的——「T+1」「七日年化」「业绩比较基准」「R1 到 R5」、客服电话的数字串；向量对这类短实体与代码串的区分力不如字面匹配，而一路召回的代价是「向量排错了，重排与生成都救不回来」。我们改为**向量与 BM25 两路并行召回、用 RRF 融合，再用一次 LLM 调用重排候选**；图谱段落仍只通过加权和参与融合，不进入重排。

选 RRF 而不是给两路分数配权重，是因为「余弦」与「BM25」之间没有稳定的归一化关系（一个是 0~1 的相似度，一个随语料 df/avgdl 漂移的无界分）。RRF 只用位次，天然跨量纲，也免掉一组迟早要重调的权重。重排交给 LLM 而不是 cross-encoder，是因为这个项目已经有模型调用的超时 / 退避 / 备用配置 / token 留痕链路可复用，而本地 cross-encoder 要新增依赖与模型下载，和「回放与测试必须离线确定性运行」（ADR-0008）冲突。

## 决定

1. **关键词检索升级为一等召回臂。** 正常路径向量与 BM25 并行召回，各出 `hybrid_recall_top_k`（默认 20）条。BM25 跑在既有的 MySQL 分块镜像 `fin_knowledge_chunk` 上（ADR-0014 第 1 条），用 `rank_bm25` + `jieba`；「向量不可用 → 只剩关键词臂」的旧降级路径保留，并复用同一条 BM25 查询。ADR-0014 中「关键词只在降级时使用」「降级结果的 `source` 仍标 `"vector"`」两条描述随之修订。

2. **RRF 只融「相似度」两路，图谱走原来的加权和。** 图谱段落是查出来的确定事实、分数恒为 1.0、次序本身无意义，把它的位次喂进 RRF 只会把噪声当信号。两路都命中的分块合并为一条（`source = "hybrid"`），去重身份是 `(knowledge_id, chunk_index)`。

3. **重排是增强，不是链路的一环。** 它超时、失败时静默退回 RRF 序并记一条 `rerank` 依赖的降级留痕；被关闭（`rerank_enabled` 为假）、或运行在 fake / 回放模式下时**同样退回 RRF 序、但不记降级留痕**——那三种是「按配置本来就不调用」，不是依赖不可用（见下）。给它独立于主链路的短超时（默认 5s）与单次调用——主链路「30s × (1+3 次重试) 再切备用配置」是为「回答尽量产出」设计的，搬到检索链上会把 2s 的检索变成 30s+。

4. **「有没有依据」由分臂证据决定，与排序无关。** 兜底判定改为：向量臂最高余弦 ≥ `retrieval_score_threshold`，**或** 关键词臂最高 BM25 ≥ `retrieval_keyword_score_threshold`，**或** 有图谱段落。RRF 与重排只决定先后。这是 `CONTEXT.md` 新增词条「证据分」的由来。

5. **重排不得把已达标的块挤出上下文。** 达标块保底占位、未达标块按重排序补足名额。若允许重排挤掉全部达标块，就会出现「判定说有依据、送进模型的上下文里一个达标块都没有」——那等于让一次增强环节改变了合规结论。**「达标」按块的来源臂各自那条阈值判**（`vector` 用 `retrieval_score_threshold`、`keyword` 用 `retrieval_keyword_score_threshold`）；`hybrid` 块的 `evidence_score` 是两路取大、事后分不清属于哪条臂的量纲，因此按两臂中**较松**的一条判——保底宁可多占一个名额，也不让一条可能达标的分块被挤掉。

6. **两条阈值由 golden 集校准产出，不再手写。** golden 集与校准脚本随本决定一并落地；CI 用 fake embedding 只钉「正例得分高于负例」的相对关系，绝对数值由脚本在真实 embedding 下产出后写回默认值。

7. **`ChunkResult` 拆出 `evidence_score`。** `score` 仍只表示最终排序分（今天就是加权和），`evidence_score` 承载该块在来源臂上的原始分（余弦 / BM25 / 图谱 1.0），供分臂判定与校准使用。两者混用是这套设计最容易失控的地方，因此用字段而非约定来分开。

## Consequences

**关键词路径的语义变了，调试口径要跟着变。** 旧口径下结果里出现关键词路径意味着「向量库坏了」；新口径下它只是「这条被字面命中了」。判断降级要看 `biz_degradation_trace` 的 `vector_store` 记录，不能再看 `source` 的取值分布。

**阈值是语料相关的，且关键词那一侧尤其如此。** BM25 的 df/avgdl 随语料规模变化，同一个问题在不同语料上的 BM25 分不同，因此 `retrieval_keyword_score_threshold` 不是一次校准就永久有效的常数。语料显著变化后要重跑校准脚本。这是选 Python 侧 `rank_bm25` 而不是 MySQL FULLTEXT（TF-IDF 变体、同样语料相关）之外多出来的一份维护成本：多两个依赖、多一套分词口径。

**每次查询都要读全表并重新分词。** df/avgdl 需要全语料统计，因此 BM25 索引是每次查询现建的。当前语料是百级分块、单次几十毫秒；语料规模上来后若成为瓶颈，可以加进程内缓存，但失效必须走数据库版本号而不是进程内事件——多 worker 下进程内事件会漂移。这一条现在不做。

**「重排与 RRF 不改变有无依据」是这套设计最需要守住的不变量。** 它意味着：任何「重排失败 → 整体检索失败」的实现都是错的；任何「用重排序决定兜底」的实现也是错的。`rerank` 这一条降级留痕的存在意义，是让「重排超时或失败了多少次」可统计。

**跳过（关闭 / fake / 回放）不计入降级统计。** 这三条是「按配置本来就不调用」，与「依赖不可用」不是一回事：把它们记成降级，会让每一次 fake provider 与回放模式的响应都变成「降级响应」（`ChatTurnResult.degraded` 直接反过来读 `biz_degradation_trace`），统计口径当场失效。若将来真的需要回答「有多少请求是在没有重排的情况下服务的」，那要按配置审计去查（`RERANK_ENABLED` 与 provider 取值），而不是往降级留痕里掺一条语义不同的记录。

**RRF 分与归一化分只服务于排序。** 重排成功时 `score` 是模型给的相关性（0~1），跳过 / 降级时是归一化 RRF（本次候选最高记 1.0）。后者仍是 0~1 且单调不增，但跨查询不可比——要展示「这条有多相关」应当读 `evidence_score`。重排成功但模型漏排了某条候选时，那条记 0.0 并沉到尾部：成功路径上 `score` 只保留「模型相关性」这一种量纲，留着归一化 RRF 会让它在 `fuse_and_rank` 的加权和里反超模型真正排过的块。

**降级路径少了一次外呼、多了一次本地计算。** 原来「向量超时 → 另起一次关键词检索」；现在关键词臂本来就在跑，向量超时只是少了一路召回，`service._keyword_only_results` 不再单独发起检索。留痕的写入点与原因码都不变，降级统计口径不受影响。
