# 充值独立建表，入金进风控而不是在受理侧拒收

充值没有产品，与转账一样是「我动过的钱」，但不进 `fin_transaction`。我们把充值放进自己的表 `fin_deposit`，客户侧的「交易流水」合并读从两表升为三表；受理侧只拦两条——金额为正、资金账户存在——大额入金交给规则引擎申报与预警，而不是在受理侧拒收。

理由：这是对 ADR-0019 与 ADR-0018 两条既有决定的延续。分表理由与转账逐字相同——把产品外键改成可空会让资产页、语义视图、持仓穿透以及所有按产品读流水的地方都开始处理空值，而它们拿一笔没有产品的流水几乎无事可做；把充值塞进 `fin_transfer` 则会让收款人两列在充值行上恒为空。受理侧不设限额、不要风评，是因为反洗钱的规范动作是申报与预警（5 万申报阈值本来就在规则引擎里），拒绝客户不能替代申报口径——把大额入金挡在受理之外，等于在已经修好的输入端再开一个盲区。

## Consequences

- 客户侧的「交易流水」从两表合并读升为三表扇入。这是这套读模型第二次扩张，也是它唯一的非平凡改动；漏读一张表不会报错，只会让那一行整行消失。
- 充值的预警不填 `transaction_ids`（那一列存的是 `fin_transaction` 的标识），金额与类型仍在命中依据里。
- 风控的历史回溯必须读第三张表：`_history_events` 漏掉 `fin_deposit` 不会报错，只会让窗口与累计类规则一起少算入金，且从结果上看不出来。
- 若将来要给充值加来源建模、限额或到账中间态，加在受理侧，不要往入海口塞（ADR-0018）。
