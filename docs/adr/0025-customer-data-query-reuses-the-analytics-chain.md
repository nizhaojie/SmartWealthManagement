# 客户数据查询复用分析链路，以客户域视图隔离，且只筛不排序

**后续修订（2026-09-27，ADR-0029）**：本文里的「员工侧的脱敏与口径已被护栏测试固化，不动它」是当时拒绝「改造员工侧视图加客户分支」的理由，**两域不合并这一条仍然成立**；但员工侧视图的姓名口径后来自己改了——`va_customer_overview.customer_name` 由脱敏值改为实名（迁移 `0034`），理由是脱敏让「客户王守成的持仓情况」这类问题必然问空、并被答成「该客户没有持仓」。客户域视图与 `mask_pii` 一行未动。

智能客服 Agent 也要让客户用自然语言查自己的数据（持仓、交易流水、资金账户）。决定：复用数据分析 Agent 的「选视图 → 生成 → 校验 → 执行 → 解读」链路，由客服图的 classify 确定性路由进入，不为客户另建一条 NL2SQL 管线；视图层面新建客户域语义视图，行级条件内建「客户 = 凭证客户」，未设置时返回零行（fail closed），与员工侧五个视图完全分开——员工侧的脱敏与口径已被护栏测试固化，不动它。

最容易被质疑的一步：允许把客户的风险承受等级作为产品查询的过滤条件（Cn 只筛 R1–Rn）。这不违反「智能客服工具集内不存在推荐类能力」（边界见 ADR-0005）：风险承受等级结论本来就是客户可见视图的一部分，用它筛自己的产品陈述的仍是客观事实；与候选池的分界在于**只筛不排序**——不评分、不排序、只按产品代码排序（与护栏 4 同款），排序与阐述仍是投顾助手的输入范围。

## Considered Options

- **把「查询数据」做成 LLM 自主调用的 tool**——被拒绝。客服图的分支本来就是确定性的，tool-calling 会引入新的运行时行为；analytics 链路的只读校验、fail-closed、行数与超时上限需要原样复用而不是重接一遍。
- **改造员工侧视图加客户分支**——被拒绝。员工侧的脱敏与行级口径已固化且被测试覆盖；在同一个视图里合并两种身份范围条件，会让「未设置身份返回零行」的 fail-closed 语义变得复杂难验。

## Consequences

失败与越界是回答的一部分：NL2SQL 失败或超时降级为「去资产页查看」的话术并写降级留痕，绝不回退到知识检索——拿知识库答案冒充数据答案是危险形态；问题落在白名单之外时明确告知可查什么，不猜测。结果以文本解读送达，不扩展 SSE 表格帧。护栏测试 3 扩展为员工/客户两段，客户段断言行级范围锁死为凭证客户且注入身份也改变不了范围。
