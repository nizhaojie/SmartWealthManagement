# 规则删除是软删、编号不复用、种子只在建库时播种

规则可以被删除之后，三件事必须一起定，否则删除这个动作会同时破坏审计与引用完整性。

**软删。** `fin_risk_rule_change` 有指向 `fin_risk_rule.id` 的外键，硬删要么级联丢掉整张留痕表，要么报错——而那张表存在的全部理由是「阈值是监管口径的落点，说不清它是初始口径还是被谁调过」（`0015`）。删除因此只写 `deleted_at`：行留在库里，列表默认过滤，可以在「显示已删除」下看到并读到它的变更记录，但**不提供恢复**——`enabled` 已经承担了可逆的「让它不生效」，删除是终态。

**编号不复用。** 新规则的编号取「曾经出现过的最大值 + 1」，已软删的编号照样占位。`fin_risk_alert.rule_codes` 是历史快照且永不回收，编号一旦被它引用就不再是「这一行的名字」，而是一个跨表的外部标识；复用编号会让两条不同的规则共用一个标识，预警详情按编号回查就指向错的那一条。

**种子只在建库时播种一次。** `_seed_risk_rules` 从「只补缺失的，不回改已经存在的」改为「表为空才播种」。原来的写法让删除失去意义——专员删掉的规则会在下次启动时复活。代价明确认下：以后想往 20 条里再加一条种子规则，不会自动补进既有库，需要一条迁移或手工插入。判断「表为空」必须用 `count(*)` 而不能过滤软删行，否则 20 条全被软删后会重新播种并撞上 `uk_risk_rule_code`，服务起不来。

## Considered Options

- **硬删，预警详情对已删规则显示「已删除规则 R0xx」**——被拒绝。行确实消失了，但 `fin_risk_rule_change` 的外键不会消失；要么级联删掉审计记录（与这张表的目的相反），要么在删规则的同一事务里报错。
- **给已删规则留一张 tombstone 表，种子跳过它们**——被拒绝。它要新表、新迁移与一条新的同步关系，换来的只是「保留种子继续补种的能力」，而那个能力正是让删除失效的东西。
- **不做删除，只做「停用 + 从列表隐藏」**——被拒绝。这与停用没有区别，只是把同一个开关换了个名字；删除要表达的是「这条规则不该存在」，而不只是「暂时不判定」。
- **提供恢复已删规则的入口**——被拒绝。它会把删除降级成一次可撤销的开关，同时让「编号不复用」这条变得难以解释：一个已被占位的编号，对应一条随时可能回来的规则。

## Consequences

规则集合不再是一份固定的 20 条清单——它随专员的增删变化，而种子只在建库那一次决定了它的起点。任何引用「20 条规则」的地方（`docs/demo-script.md`、评分材料）都要改成「初始 20 条」。
