# 客户数据回答携带结果表，文本只留口径

客户侧 NL2SQL 已按 ADR-0025 落地：客服图的「数据查询」分支复用 analytics 链路（选视图 → 生成 →
校验 → 执行 → 解读），身份锁死在凭证客户，结果以文本解读经既有 SSE 送达。当时把「不扩展 SSE
表格帧」写进了那份 ADR 的 Consequences，理由是「前端零改动是本 slice 的边界」。这条边界随后自己
显形了：客户侧解读为确定性模板（不走模型），模板把**每一行的每个字段念一遍**（`{列名} 为 {值}；…`），
而客户域四张视图的列名是英文 snake_case（迁移 `0030`）——于是客户读到的是
`product_name 为 稳健增利，market_value 为 120000` 这样的句子。数据查询的回答本该是表格：内部数据
分析页早就是「口径解读 + 结果表」（`analytics-chat-ui`）。

要改的就是那条边界。改动面有三处：`done` 帧的 `ChatResponse` 增加客户侧结构化结果、客户侧文本收敛为
口径与行数、归档也存结构化结果——否则客户「历史记录」里这一轮只剩「N 行 + 口径」，实时与回看的信息量
会差一个量级。

## 决定

1. **有行时，客户侧数据回答携带结果表。** `ChatResponse` 新增可选 `data_answer`
   （`columns: [{key, label}] / rows / row_count / truncated / views`），只在数据查询分支且结果非空时
   出现。不新增 SSE 事件名——客户侧 `parseFrame` 的非 `done` 分支把载荷当 `delta` 用
   （`apps/customer/src/chat/api.ts:117-121`），新事件名会在答案尾部追加 `undefined`；也不新增端点，
   结果本来就在内存里，多一次往返会引入「帧到了表没到」的时序。

2. **结构化结果只允许来自客户域语义视图。** 员工侧五个视图的结果永不进客户契约。`views` 以中文
   `label` 出现、`customer_id` 列在出契约时剔除、SQL 不给客户。列标签进 `catalog.py` 的 `ViewSpec`
   （视图级中文名与口径已经在那一处），缺标签时运行时回落列名，并加测试让漂移在 CI 里红——宁可表头
   难看，不可悄悄吞掉一列数据。

3. **客户侧文本收敛为「口径 + 行数 + 截断」。** 逐行明细与低基数列计数从客户文本里去掉：表格是数据的
   唯一出处，文本负责回答「这些数字是怎么来的」。零行、失败/超时、白名单外三种出口 `data_answer`
   为空，仍是文本——一张空表会把「没有数据」与「查询挂了」在观感上抹平。

4. **归档存结构化结果，客户历史回看重绘同一张表。** 归档举证的正是「客户当时看到了什么」（ADR-0012），
   所以实时与回看必须是同一张表。结构化行**不过** `mask_pii` 的三条文本正则：它的字段面是视图定义的
   封闭列集合，不存在「自然语言里混入不可预知 PII」的风险；对账号再打一次码只会让回看与实时不一致。
   内部端（客户经理视角）的会话详情不加这个字段——它该忠于的是客户视角，要看数据有授权面更宽的视图。

5. **回放模式下客户侧不采信预置解读文本。** `ANALYTICS_PRESETS` 的解读是员工口吻，且会写出内部视图名
   （「语义视图 `va_product_element`」），而其中一条的目标视图同时在客户候选集里。本次顺带收口：客户
   口径一律走确定性模板，预置 SQL 照旧使用（演示的确定性不丢），并以断言钉住「客户可见的文本与结构里
   不出现 `va_`」。

## Considered Options

- **新增一条 SSE 事件（如 `event: table`）承载表**——被拒绝。客户侧 `parseFrame` 的实现会让新事件变成
  一段 `undefined` 文本，而 `done` 帧本来就是整轮跑完才产出，表没有「边跑边出」的语义。
- **新增 REST 端点按 `trace_id` 取结果表**——被拒绝。没有跨请求取表的场景：客户会话不跨登录，表与产生
  它的那一轮同生共死。
- **只做实时回合，归档不动**——被拒绝，但代价被看见：文本收敛后回看里那一轮只剩「N 行 + 口径」。
- **归档里存一份带逐行明细的文本快照，界面渲染表格**——被拒绝。归档是审计级留痕，写进客户没看到的
  形态会掏空它的举证语义。
- **让 LLM 生成 SQL 时给中文列别名（`AS 产品名称`）**——被拒绝。客户侧解读是确定性的、不经过模型；
  把标签押在模型输出上会让「客户看到什么」变得不可预测。
- **客户侧复用内部端的 `el-table`**——被拒绝（实现层，不是架构层）。客户侧三处表格已有自己的形态
  （原生 `<table>` + `--wm-*` 令牌 + `.table-wrap` 横向滚动 + `data-testid`），且客户侧 EP 是全量注册，
  插进来会让同一个应用里出现两套表格观感。

## Consequences

**这是客户侧 SSE 契约的第一次结构扩展。** 后端既有断言按键取值不会破，前端
`apps/customer/src/chat/api.spec.ts` 的深度相等断言必须同步改——契约变更的成本记在这里，别让它以后变成
「加了字段没人知道」。

**客户侧的一切都走客户契约，而不是共用内部序列化**（与 ADR-0016 同一条纪律）。视图名、SQL、英文列名与
`customer_id` 都不进客户端，这条由测试钉住，不靠约定。

**回看与实时一致，代价是归档多了一列数据。** `conversation_archive` 从「文本 + 引用 + 工具调用」变成也
含结果集；它仍是只读留痕、不参与上下文，客户姓名照旧打码（ADR-0015 决定 5 的代价继续成立，只是不适用于
数据列）。

**回放模式的预置解读对客户失效。** 演示时客户问出预置原句，看到的是确定性模板 + 结果表；员工侧预置解读
不受影响。
