# 员工侧语义视图给出客户实名，姓名因此可精确查

迁移 `0008` 把 `va_customer_overview.customer_name` 定义成脱敏值（保留姓、其余星号），依据是
`data-analysis-agent` spec 的「真实姓名按脱敏规则出现」。这条口径在真实提问下现形了，而且不只是
「查不到」——它会**答错**：

- 员工在工作台的其他每一处（客户列表、客户画像、预警列表、工单、投顾工作台）看到的都是明文姓名，
  于是问「客户王守成的持仓情况」时带的是全名；
- 而视图里存的是「王**」，生成的查询是 `WHERE customer_name = '王守成'`，恒 0 行；
- 0 行被解读成结论——系统答「客户王守成当前无任何持仓记录，资产规模为 0」。王守成名下确有一笔
  20420 元的持仓（2026-09-27 实测，真实 provider + 真实库）。

修掉第二半（0 行不再交给模型下结论）只让答案变诚实，仍然答不出员工问的事。而脱敏姓名本身也
筛不了：同姓客户的脱敏值是同一个字符串，补了「按姓氏前缀筛」的口径后，模型在 `= '王**'`（同姓
撞多行，报 1105）与 `LIKE '王%'`（一次命中多位同姓客户，谁是提问点名的那位无从判断）之间摇摆。
把「能不能查到名下某位客户」押在提示词上，与合同是稳不住的。

## 决定

1. **`va_customer_overview.customer_name` 改为客户实名**（新迁移 `0034` 重建视图，其余列与行级
   条件一字不动）。员工侧另外四张视图不含姓名列，因此不受影响。
2. **敏感字段的边界不变**：身份证号、手机号、银行卡号、密码散列仍然结构性不进任何视图，执行账号
   仍然只对视图有 SELECT。变的只有姓名——它是员工已经在别处看得到的信息。
3. **客户域与归档不动**：`va_my_*` 四张视图继续是本人数据、不含姓名列；会话归档文本的 `mask_pii`
   （ADR-0015 决定 5）继续给客户自己的姓名打码。
4. 按姓名查客户成为精确等值查询（`customer_name = '王守成'`），姓氏前缀筛选不再是推荐问法。

## Considered Options

- **维持脱敏，只在口径里写明「按姓氏前缀筛」**——被拒绝。实测模型在等值比较与前缀匹配之间摇摆，
  而前缀匹配在种子数据里几乎必然命中同姓的两位客户；结论要么错要么含糊，且稳定性押在模型上。
- **维持脱敏，加一列非 PII 的客户账号**——被拒绝。员工在工作台里看不到客户账号（客户列表只画
  姓名、风险等级与分层），拿它在问句里指人这件事不成立。
- **保留脱敏列，另加 `customer_real_name`**——被拒绝。同一份数据两个名字，模型会挑错列；脱敏列
  在改名之后没有任何消费者，留着只会让人以为还有一道防线。
- **在 analytics 链路里加「姓名 → customer_id」的旁路解析**——被拒绝。那要读基础表，ADR-0010
  的结构性保证就没了：安全从「模型看不到」退回「代码别写错」。

## Consequences

**真实姓名从此进入 LLM 提示词与结果集，模型托管在外部 provider。** 这是本决定的主要代价，也是
它值得单独记一条 ADR 的原因：对**员工**而言没有新增暴露面（同一批姓名他在客户列表里就能看到，
行级范围也仍然是角色与归属关系那一条），新增的暴露面在**模型 provider** 与**浏览器**——数据分析
页把整条线程（含结果行）存进 `sessionStorage`（`analytics-chat-ui` Q7 当年正是拿「customer_name
是姓 + 星号」当理由的）。若将来要收回这一点，正确做法是在视图层引入「姓名 → 匿名标识」的映射并
让员工用标识问人，那是另一条 ADR，不是把 `LEFT() + REPEAT('*')` 加回来。

**护栏测试随之改向。** `test_customer_names_are_masked_in_views` 反转为「员工侧客户概况视图给出
实名，且其余视图不含姓名」；`SEED_SECRETS` 拆成「PII 值（处处不得出现）」与「种子姓名（只允许
出现在这一张视图里）」。这两条改写本身就是本决定的一部分，别在后续改动里被顺手改回去。

**「按姓名找人」不再是模型的能力问题。** 生成为精确等值比较之后，0 行的含义回到它本来的意思
（这个人不在这张视图的行级范围里），员工侧的 0 行确定性话术（员工侧解读不经模型）继续成立。
