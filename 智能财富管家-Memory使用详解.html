系统记得什么、记多久、谁说了算：
本系统中三层记忆的使用方式

记忆分三层，但分层不按「存在 Redis / MySQL / Milvus」来划，而按两个问题划：这条信息活多久， 以及谁是它的权威来源（ADR-0012）。短期记忆是当前会话的消息列表（Redis，30 分钟滑动过期、2000 token 预算）； 中期记忆是客户画像与工单状态（MySQL 为权威，缓存只做加速）；长期记忆是知识向量、图谱与原始文档（知识元数据为权威， 其余都是它的投影，坏了可全量重建）。会话归档与置信度常被误当成「第四层记忆」，它们都不是——本文说明理由。

SECTION 00

全景总览

三层记忆的判据是「生命周期」与「权威来源」，存储技术只是实现细节——短期记忆从 Redis 换成别的缓存，分层不变。

层内容生命周期权威来源读取方式
短期记忆 当前会话的消息列表 一次登录的会话内，滑动过期（chat_memory_ttl_minutes = 30），总量受 token 预算约束 本次对话本身 Redis 列表，超预算时截断最旧消息
中期记忆 客户画像、工单状态 跨会话存在，但会被业务改写 画像由离线计算产生、工单由流程流转产生，均落在 MySQL 画像走 Cache-Aside；工单直接查库（缓存不是权威）
长期记忆 知识向量、知识图谱、原始文档与知识元数据 长期 知识元数据（MySQL）为权威，Milvus / Neo4j / MinIO 都是它的投影 检索与多跳查询；投影可全量重建

存储分工

  • Redis：短期记忆列表 agent:memory:{session_id}、画像缓存 customer_profile:{id}、登录会话白名单
  • MySQL：中期记忆（fin_customer_profile / fin_profile_tag / biz_work_order）、长期记忆的权威元数据（fin_knowledge_meta）、归档（conversation_archive）
  • Milvus / Neo4j / MinIO：长期记忆的三处投影——向量、图谱、原始文档字节

谁在读这些记忆

  • 短期记忆：智能客服 Agent（run_customer_service_turn）、数据分析 / 风控问答链路（run_query）
  • 中期记忆：画像供投顾助手与推荐使用，工单供内部工单页与风控处置使用
  • 长期记忆：智能客服的知识检索、客服「数据查询」分支与数据分析 Agent 的视图检索、GraphRAG 增强

设计不变式

  • 缓存永远不是权威：失效时直连 MySQL；缓存不可用不影响正确性
  • 短期记忆只用于组装上下文，不是留痕——留痕归归档与调试留痕
  • 记忆丢失不阻断开服务：缓存抖动退化成「没有上下文的一轮」，仍然正常作答
  • 投影坏了就全量重建，不做双向同步、不做增量捕获
要新增一类信息时，依次问三个问题（ADR-0012 的判据）
① 它随会话结束就失去意义？是 → 短期记忆
② 跨会话存在、会被业务改写、有明确写入方？是 → 中期记忆
③ 长期稳定、由知识导入或全量重建产生、只读？是 → 长期记忆
都不是？那它多半不是记忆——例如会话归档与置信度
当前视角：只看降级路径。所有「依赖不可用时怎么办」的节点已高亮（红色描边），其余节点淡化。点击顶栏「全流程」恢复。
SECTION 01

短期记忆：一轮对话的上下文

实现只有一处（agent/memory.py）：一个 Redis List，键 agent:memory:{session_id}。它随会话结束失去意义，因此按会话隔离、滑动过期、受 token 预算约束；读不到就不带上下文地作答——缓存是优化不是依赖。

1

读：取上一轮为止的消息列表 agent/memory.py::read_history

LRANGE agent:memory:{session_id} 0 -1 → 反序列化成 [{"role","content"}, …]。返回的不是裸列表而是 HistoryRead(history, degraded)——调用方需要知道这次读取有没有走降级，才能决定是否留痕。

只需要消息列表时用便捷读法 get_history（数据分析链路就是这种用法，它不关心降级留痕）。

出处：backend/app/agent/memory.py

2

注入上下文：历史作为提示词的一部分 agent/graph.py::generate_node · llm/provider.py

历史随图状态进入运行时（graph.invoke({"question", "history", …})），由生成节点的消息组装函数拼成：

messages = [ system(检索约束+引用要求), *history, user(编号片段 + 本轮问题) ]
  • 只有需要多轮语境的节点吃历史：知识生成节点与客服的「数据查询」分支都带历史；闲聊节点不带——闲聊不引用片段，也就没有需要承接的上下文。
  • 数据分析 / 风控问答链路用历史问题参与视图检索与 SQL 生成，支撑「那上个季度呢」「那今天呢」这类不含主语的追问。
  • 历史是用户与助手的逐轮原文，不压缩、不摘要——超出预算的部分在写入时已经截掉了。

出处：backend/app/llm/provider.py::build_grounded_messages、app/agent/graph.py、app/analytics/service.py

3

写回：一轮两条消息，每次追加都续期 agent/memory.py::append_turn

  • 本轮结束后追加两条：role="user"（问题）+ role="assistant"（最终定案回答）——写的是最终答案，不是流式过程中的半成品
  • RPUSH 追加后 EXPIRE 重置为整窗 30 分钟：这就是滑动过期，不再说话就自然消失
  • 返回值是布尔：缓存不可用时返回 False 而不是抛错，本轮的答案不受影响

出处：backend/app/agent/memory.py::append_turn、app/agent/graph.py:649-654、app/analytics/service.py:143-154

4

截断：token 预算之内，最新一条一定保留 agent/memory.py::_truncate_to_budget

预算 chat_memory_token_budget = 2000。追加后立刻重算消息列表总 token，超预算就从最旧的消息开始丢，LTRIM 落回 Redis。

while 总量 > 2000 且 剩余条数 > 1：丢掉最旧一条
  • 「剩余条数 > 1」这个条件是刻意的：再长的对话也不会被截成空列表，最新一条永远在——否则用户会看到系统突然失忆成陌生人。
  • token 口径与知识库分块一致（knowledge/tokenizer.py::count_tokens）：一个汉字算一个 token，因此 2000 token 大致相当于 2000 个汉字。
  • 截断失败不影响本轮：消息已经写进去了，下一轮读出来时调用方仍按同一预算处理。

出处：backend/app/agent/memory.py:78-96、backend/app/settings.py:134

5

隔离：会话不跨登录，用途靠命名空间区分 agent/memory.py::_key · analytics/service.py::_memory_session

  • 按会话隔离：session_id 取自登录凭证（sid），每次登录新签发——会话不跨登录延续，「重新登录」是唯一结束会话的方式。
  • 按身份隔离：客服链路用凭证里的 sid 直接做键；客户只能读到自己的会话，这一层由鉴权保证。
  • 按用途命名空间隔离：内部侧同一员工可能在多个链路提问，键里带上命名空间与员工号——
    analytics:{employee_id}:{session_id}　|　risk_query:{employee_id}:{session_id}
    同库存储、靠键前缀区分，数据分析与风控问答的多轮上下文互不串味；客服链路是裸 session_id（客户身份域本就独立）。
  • session_id 由请求体给出时优先于凭证 sid（内部侧可显式指定会话），缺省则回落到凭证。

出处：backend/app/analytics/service.py:42-48、app/agent/risk_query.py:33、app/api/analytics.py:42、app/auth/service.py

6

降级：读返空、写跳过，本轮照常作答 agent/memory.py · agent/graph.py::run_customer_service_turn

  • 读降级：RedisError → 返回空列表 + degraded=True，调用方写一条降级留痕，然后照常跑图——这一轮退化成「没有上下文的一轮」，答案仍然可用。
  • 写降级：append_turn 返回 False，静默跳过，不抛错、不回滚回答。
  • 一轮最多留一条：写回失败时，只在读时没有记过降级的前提下补记一条；两条都失败也只留一条，避免一轮刷两行。
  • 超时是必须的：Redis 客户端连与读写都设超时——没有超时，一次「连得上但不应答」的抖动会把请求线程一直吊着，降级路径永远触发不了。
缓存不可用 → 无上下文的单轮回答 降级留痕 cache / unavailable

出处：backend/app/agent/memory.py:45-75、app/agent/graph.py:618-627,655-664、app/redis_client.py、app/degradation.py

7

回放模式：不连 Redis，用进程级替身 app/redis_client.py · app/replay/local_cache.py

演示回放（demo_replay）下不发起任何网络调用：登录会话白名单、短期记忆、画像缓存共用同一个进程级单例内存替身。

  • 必须是单例——每个请求各发一个新实例的话，登录时写进的会话在下一个请求就读不到了。
  • 替身实现各消费者用到的方法子集且从不抛 RedisError：回放态下缓存永远可用，降级路径不会被触发。

出处：backend/app/redis_client.py:35-54（ADR-0008）

键agent:memory:{session_id}（客服）· agent:memory:analytics:{employee_id}:{session_id}（数据分析）· agent:memory:risk_query:{employee_id}:{session_id}（风控问答）

  • 数据分析 Agent / 风控监测问答（analytics/service.py::run_query）：读历史问题用于视图检索与 SQL 生成，成功后写回

出处：backend/app/settings.py:133-134 · docs/system-architecture.md（Redis 键与 TTL 表）· ADR-0012

SECTION 02

中期记忆：跨会话存在，但会被业务改写

中期记忆有明确的写入方与权威来源，因此：权威在 MySQL，缓存在 Redis 只做加速。读缓存失败不是错误——直连数据库，恢复后自动回填（Cache-Aside）。

1

客户画像 · 读路径：先缓存，未命中就回源并回填 customer_profile/service.py::get_internal_profile

GET customer_profile:{customer_id} → 命中即返回；未命中 / 降级 → 读 MySQL → 尝试回填（TTL 300 秒）
  • 缓存值是整份画像快照的 JSON；_cache_get 返回 (snapshot, degraded)，把「没缓存」与「缓存坏了」分开——前者正常，后者要留痕。
  • 回填失败不影响这次读取：缓存是优化，不是依赖。

出处：backend/app/customer_profile/service.py:37-92,308

2

客户画像 · 失效点：写画像后、置信度校准后 service.py::_finish_write · calibration.py

  • 每次写标签 / 手工修正后：提交事务，然后按客户删缓存——先落库再失效，读方最差拿到 300 秒内的旧快照，不会拿到未提交的脏数据。
  • 离线置信度校准后：按客户逐个失效，让下一次读重新计算置信度。
  • 失效本身可能失败：此时旧快照会留到 TTL 自然过期——属于缓存降级，要留痕以便统计。

出处：backend/app/customer_profile/service.py:95-101,128-138、customer_profile/calibration.py

3

置信度不是一层记忆，是画像标签上的派生数值 service.py::compute_confidence · rerank.py::MemoryUnit

  • 不单独存储：读取时由来源、被证据确认次数、冲突次数与观测时间现算，时间基准显式传入（ADR-0011「清理必须带显式的 now」）。
  • 标签参与重排：每个标签被适配成一个记忆单元 MemoryUnit，排序因子含语义相似度、时间新鲜度、历史准确率、基础置信与冲突惩罚——「这条记忆该不该被采信」是一次打分，不是一次查表。
  • 冲突不被静默覆盖：相反证据会写进冲突记录表，并在打分里形成惩罚。

出处：backend/app/customer_profile/rerank.py、customer_profile/service.py（fin_customer_profile / fin_profile_tag / fin_profile_tag_conflict）

4

工单状态：直接查库，不做缓存 work_order/ · biz_work_order

工单是「会被流程持续改写」的权威事实：状态机每流转一次就落一行留痕。这里不引入缓存——缓存只能加速读，却要为状态流转的可见性承担失效责任，得不偿失。

ADR-0012 留了口子（「热点可加缓存」），但代码目前没有加：工单页与风控处置直接读表。

出处：backend/app/work_order/、app/api/work_orders.py、ADR-0012

5

降级：画像直连数据库，缓存坏了也能读 service.py::get_internal_profile

  • 缓存不可用 / 超时 → 直连 MySQL 读画像，结果照常返回，同时写一条 cache / unavailable 降级留痕。
  • 缓存恢复后下一次读自动回填，不需要人工干预。
  • 结论：缓存抖动不会让「客户画像」这个能力消失，只会让响应慢一点、降级统计多一条。
缓存不可用 → 直连 MySQL 失效失败 → 旧快照留到 TTL

出处：backend/app/customer_profile/service.py:308-337、backend/tests/test_degradation_paths.py

SECTION 03

长期记忆：MySQL 为权威，其余都是投影

长期记忆长期稳定、由知识导入产生、对读方只读。因此它只有一个权威：知识元数据（MySQL）；向量、图谱、原始文档都是它的投影读模型——只读、单向、坏了全量重建。

落地装什么角色坏了怎么办
MySQL 知识元数据 fin_knowledge_meta + 分块镜像 fin_knowledge_chunk 权威：文档状态（processing / active / failed / expired）、有效期、分块正文 真实来源，不需要重建；分块镜像同时是关键词臂的语料（ADR-0014）
Milvus 分块向量（1024 维，COSINE 度量） 投影：语义检索臂 维度不一致时删集合重建，按 MySQL 分块重新向量化
Neo4j 客户 / 产品 / 行业 / 风险等级 / 基金经理的关系网 投影读模型：GraphRAG 多跳查询 全量重建（rebuild_graph）：清空命名空间后按 MySQL 当前状态重新生成
MinIO 原始文档字节（bucket wealth-knowledge，键 knowledge/{knowledge_id}/{filename}） 投影：原文归档，供引用溯源 删除文档时打 archived 标签归档而非物理删除
1

写入：一次入库，三处落地，失败整体回滚 knowledge/service.py::_run_ingestion_pipeline

员工上传知识文档后走四阶段流水线 parse → chunk → embed → store：MySQL 落元数据与分块镜像、Milvus 落向量、MinIO 落原文。任一写入失败则三处一起回滚（删对象、删向量、清镜像行），元数据置 failed；全部成功才置 active。

为什么强调这一点：投影与权威不能各自为真。半写入的投影比没有投影更危险——检索会命中一个权威不承认的分块。

出处：backend/app/knowledge/service.py、knowledge/vector_store.py、knowledge/object_store.py

2

读取：检索与多跳查询，只读不回写 knowledge/service.py::search_chunks · knowledge_graph/graphrag.py

  • 检索：向量臂（Milvus）∥ 关键词臂（MySQL 分块镜像 BM25）→ RRF 融合 → 重排；命中后回查 MySQL 元数据，仅 active 文档可返回——权威说了算，投影只是候选来源。
  • 多跳查询：GraphRAG 用固定的六个查询工具读图谱，把事实写成句子掺进候选。图谱是增强不是依赖：查不到段落就按相似度结果继续，分数不打折。

出处：backend/app/knowledge/service.py、app/knowledge_graph/（详见同目录的《RAG 流程详解》）

3

重建：全量、幂等、有互斥与留痕 knowledge_graph/service.py::rebuild · sync.py::rebuild_graph

  • 唯一同步方式：删光命名空间内全部节点与关系，再按 MySQL 当前状态重新生成；幂等，不做增量同步或变更捕获。
  • 互斥：重建期间不允许第二次重建；运行状态与结果落在 biz_graph_sync_run（running / success / failure）。
  • 触发：内部 API POST /api/internal/graph/rebuild（要求内部身份域，回放模式下明确拒绝），或命令行种子脚本 scripts/seed_demo.py。

出处：backend/app/knowledge_graph/service.py:44、knowledge_graph/sync.py:284、app/api/graph.py（ADR-0002）

4

降级：投影缺席，权威仍在 knowledge/hybrid.py · agent/graph.py

  • 向量库超时 / 报错 → 关键词臂（MySQL 分块镜像）单独出结果，仍能给出带引用的回答——这正是分块镜像存在的理由（ADR-0014）。
  • 图谱不可用 → 跳过图谱增强，按知识片段继续，证据分一个都不打折。
  • 投影整体损坏 → 全量重建；因为权威是 MySQL，重建不丢事实，只丢重建期间的服务能力。
投影可缺席 · 权威不可缺席
SECTION 04

会话归档：不是第四层记忆

会话归档（conversation_archive）永久保存、脱敏后只读，不参与上下文组装。它回答的是「当时发生了什么」，不是「系统现在记得什么」——把它当成一层记忆，就会在「为什么这句话没进上下文」与「归档里明明有」之间产生混淆。

对照短期记忆会话归档
生命周期滑动过期，30 分钟不活跃即消失永久
是否进上下文是——它就是上下文否——只读回看与举证
写入时机本轮结束后追加两条消息本轮结束即刻落库，不等会话断开
内容角色 + 文本使用者、Agent、问题、最终答案、引用、工具调用、内容分类、结果表
脱敏不脱敏（只在 Redis 内、按会话隔离）落库前脱敏（PII 正则 + 真实姓名）
为何不合并合并会同时失去两个特性：归档要长期可读，就必须脱敏；上下文要能引用原文，就不能被脱敏改写。二者是不同的用途，只能各存一份。
1

即刻落库：每轮两行，进程中途退出也不丢 agent/archive.py::record_turn

一轮问答结束时立即提交：一行提问（role=user）、一行回答（role=assistant），而不是等会话断开再批量写。工具调用记录、引用文档与内容分类随回答那一行留下。

数据查询的那一轮还多留一份客户看到的结果表（ADR-0028）：回看因此能重绘出与实时同一张表。

出处：backend/app/agent/archive.py:76-124、app/agent/graph.py:666-679

2

落库前脱敏：三类正则 + 真实姓名 archive.py::mask_pii

形态处理方式
身份证号（18 位）保留前 6 位（地区码）+ 后 4 位，中间打码
银行卡号（16–19 位）只保留后 4 位，其余打码
手机号（1 开头 11 位）保留前 3 + 后 4，中间打码
真实姓名按当前客户姓名做字面替换：首字保留 + 其余打码
  • 结果表不过脱敏：三条正则认的是自然语言文本里的 PII 形态，而结果表的字段面是视图定义的封闭列集合、值就是客户可见视图里的值——对账号再打一次码，只会让回看与实时不是同一张表。
  • 文本脱敏是形态识别，不是语义理解：18 位身份证与 18 位银行卡在字符上无法区分，统一按身份证处理（保留地区码）——这是可接受的折衷，脱敏文本没有字段语义可供消歧。

出处：backend/app/agent/archive.py:35-73、ADR-0028

3

读取：两个身份域，两套可见范围 api/conversations.py · api/customer_conversations.py

内部端/api/internal/conversations
  • 要求内部员工身份；列表可按会话标识或客户标识筛选
  • 客户经理只见自己名下客户的会话，与工单、预警同一口径
  • 返回工具调用与内容分类等合规字段
客户端/api/customer/conversations
  • 要求客户身份；列表排除当前会话（当前会话在对话页可见，历史只收已结束的登录会话）
  • 详情按 session_id + user_id 过滤：别人的会话即使知道标识也查不到，与「不存在」同等待遇（404，不暴露存在性）
  • 只给 role / 文本 / 引用 / 时间 / 结果表——工具调用与内容分类是内部字段

分页口径：列表按会话分组后分页（ADR-0024），total 是「多少场会话」而不是归档行数；排序键是最后一次发言时间倒序 + 会话标识兜底——发言时间是秒精度，同一秒结束的两场会话若不分先后，翻页时会在两页之间来回跳。

出处：backend/app/api/conversations.py、api/customer_conversations.py、agent/archive.py（ADR-0015 / ADR-0024）

4

界面：客户侧有历史抽屉，内部侧只有 API apps/customer/src/chat/ChatHistoryDrawer.vue

客户在对话页可以打开「历史会话」抽屉：列表取会话标题（该会话第一条客户提问，批量查询取标题，避免一页历史退化成每场会话一次查询）、消息数与起止时间；点进去是只读流水。

内部端归档 API 已具备（供合规与留痕追溯），但没有对应的前端页面——内部界面上的「历史」是数据分析的查询历史，与归档不是同一个能力。

出处：apps/customer/src/chat/ChatHistoryDrawer.vue、apps/customer/src/chat/history.ts

SECTION 05

降级路径总表

降级不是失败：外部依赖不可用时改走备用路径，响应仍是成功响应，只是依据更弱、上下文更少。每一处降级都留下可统计的痕迹（biz_degradation_trace）。

位置依赖不可用时后果留痕
短期记忆 · 读
memory.read_history		 返回空列表 + degraded=True 本轮退化成「无上下文的单轮回答」，答案照常给出 cache / unavailable
短期记忆 · 写 / 截断
memory.append_turn		 返回 False，静默跳过 本轮答案不受影响；后续轮次少一段上下文 仅当读时未记过时补一条
画像缓存 · 读
get_internal_profile		 直连 MySQL 读画像 结果照常返回，只是慢一点；缓存恢复后自动回填 cache / unavailable
画像缓存 · 失效
invalidate_profile_cache		 删除失败 读方可能拿到旧快照，直到 TTL（300 秒）自然过期 cache / unavailable
向量检索臂 超时 / 报错 关键词臂（MySQL 分块镜像 BM25）单独出结果，仍有引用 检索侧降级
知识图谱 查询不可用 / 无实体命中 跳过图谱增强，按知识片段继续，证据分不打折 图谱降级标记
回放模式
redis_client()		 不连 Redis，改用进程级内存替身 替身从不抛 RedisError，因此回放态下缓存永远可用、降级路径不触发 —（不发外部调用）
会话归档
archive.record_turn		 —（与缓存无关，直接落 MySQL） 文档：本轮对话不会因为缓存抖动而丢掉审计级留痕 —
为什么缓存降级不能只做一半
  • 超时必须显式设置：连得上但不应答的抖动如果没超时，线程会被一直吊着，「缓存不可用就直连数据库」这条路径永远触发不了——因为永远等不到那个异常。
  • 降级要可统计：留痕不为了给用户看，而是让「有多少次协作其实没发出去 / 有多少轮对话其实没有上下文」成为可查询的数字（内部有降级统计接口）。
  • 降级不改结论：上下文缺失、图谱缺席都不改变「有没有依据」这个合规判断——那由证据分闸门单独判定。

出处：backend/app/degradation.py、app/redis_client.py、backend/tests/test_degradation_paths.py
