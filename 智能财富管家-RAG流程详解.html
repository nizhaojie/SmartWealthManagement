检索增强生成（RAG）在本系统中的完整旅程

本系统有两个 Agent 用到检索增强生成：智能客服 Agent 走完整的知识库 RAG 链路 （向量 + BM25 混合召回 → RRF 融合 → LLM 重排 → GraphRAG 图谱增强 → 受限生成）； 数据分析 Agent 在 NL2SQL 链路里检索语义视图定义与示例注入提示词，再生成受限查询。 两条链路全程埋着 20 道权限校验，本文件逐一记录。

2个 Agent 使用 RAG
4类存储协同（Milvus / MySQL / MinIO / Neo4j）
20道权限校验
SECTION 00

全景总览

同一份知识内容在三处落地、各有分工；检索时向量库与关系库并行召回，图谱做增强。身份域（客户 / 内部员工）在入口即隔离，是全部权限校验的地基。

存储分工

  • MinIO：原始文档字节（删除时归档而非物理删除）
  • Milvus：1024 维向量，COSINE 度量，Strong 一致性
  • MySQL：文档元数据 + 分块镜像 fin_knowledge_chunk（BM25 语料）
  • Neo4j：知识图谱，MySQL 的只读投影（GraphRAG 增强）

两个 Agent

  • 智能客服 Agent（客户域）：知识库 RAG，产出带强制引用的事实性内容
  • 数据分析 Agent（内部域）：检索语义视图与示例 → NL2SQL → 受限执行 → 解读
  • 客服的「数据查询」分支复用数据分析链路（客户身份 + 客户口径）

设计不变式

  • 检索不到依据不作答，给人工客服热线
  • 重排与融合只决定先后，不改变「有没有依据」的合规结论
  • 图谱是增强不是依赖：没有图谱段落时检索按相似度结果继续（问题不含实体是正常结果，不是异常）

SECTION 01

原始数据入库

员工在内部工作台上传知识文档，走一条四阶段状态机流水线：processing → active / failed，阶段记录到 parse / chunk / embed / store，任何一阶段失败都落失败原因。

1

上传入口与身份校验 POST /api/internal/knowledge/documents

仅内部员工可上传。依次经过：Bearer token 提取 → JWT 验签（HS256，校验 audience 必须等于 internal-app、类型必须为 access、未过期）→ Redis 会话白名单（auth:session:{sid}，登出即删）。

P04 仅内部员工身份域 P02 跨域凭证 403 P03 会话白名单 P07 回放模式拒绝写操作

出处：app/api/knowledge.py、app/auth/dependencies.py、app/auth/tokens.py

2

格式与类型校验，建档 create_pending_document

文件格式白名单 txt / md / docx，不支持则拒绝（业务码 1006）。知识类型为 FAQ / 产品 / 政策；政策法规默认有效期 1 年、产品说明默认半年，FAQ 不设期限。先落一条 processing 状态的元数据，实际解析交给后台任务异步执行。

P08 格式白名单

出处：app/knowledge/service.py、app/knowledge/parsers.py

3

parse · 解析成语义节 stage = parse

  • txt：按 Tab 嗅探「问题⇥答案」问答对，一组问答自成一节——不会与相邻问答或普通段落混进同一个分块，也不会被从中间跨组切断；单组问答本身超过 512 token 时仍会被滑窗切成多块（切点只落在这一组内部）。其余行累积成普通节
  • md / docx：按标题层级切节，每节携带 heading_path（标题路径），供引用定位

出处：app/knowledge/parsers.py

4

chunk · 滑动窗口分块 stage = chunk

按 token 滑窗切分：块长 512 token、重叠 64 token（token = ASCII 字母数字串，或单个非空白且非字母数字的字符；一个汉字算一个 token，因此 512 token 大致相当于 512 个汉字）。每个分块继承所在节的标题路径。

出处：app/knowledge/service.py（CHUNK_SIZE=512, CHUNK_OVERLAP=64）·app/knowledge/tokenizer.py（分词与切分实现）

5

embed · 向量化 stage = embed

OpenAI 兼容接口（DashScope text-embedding-v3，1024 维），单次请求最多 10 条、按批发送；无 key 时走确定性 fake embedding（SHA-256 bigram 哈希），保证测试与回放离线可复现。

出处：app/knowledge/embeddings.py

6

store · 三处落地，失败整体回滚 stage = store

  • MinIO：原始文档字节 → knowledge/{knowledge_id}/{filename}（bucket wealth-knowledge）
  • Milvus：向量 + 分块正文写入集合 knowledge_chunks（COSINE / Strong）
  • MySQL：分块镜像 fin_knowledge_chunk 覆盖式写入——它跟着 Milvus 一起成功或一起失败

任一写入失败：删除已上传的 MinIO 对象、按 knowledge_id 删 Milvus 向量、清空镜像行，状态置 failed 并记录失败阶段与原因。全部成功才置 active。

出处：app/knowledge/service.py::_run_ingestion_pipeline、object_store.py、vector_store.py

7

下架（删除） DELETE /documents/{id}

同样要求内部员工身份。Milvus 向量物理删除；MinIO 原文打 archived 标签归档而非物理删除；元数据置 expired，从默认列表消失。已下架文档的命中块在检索侧会被状态过滤挡掉（见 P09）。

P04 仅内部员工P07 回放模式拒绝

出处：app/knowledge/service.py::delete_document

4

RRF 融合 knowledge/hybrid.py::rrf_fuse

进什么、出什么：两臂各出 hybrid_recall_top_k = 20 条（各自带分臂原始分），融合成一张按融合分排好的候选池，取前 20 条交给重排——这就是重排看到的那一整池。融合的 20 与最终送进模型的 retrieval_top_k = 5 是两个量：一个是「候选池」，一个是「取货」。向量臂超时 / 不可用时并不是换一段代码，而是把输入的臂从两路变成一路，同一个融合函数照样跑一遍（service._keyword_only_results），只是那一次会写一条 vector_store 降级留痕。

选 RRF 而不是配权重，因为余弦（0~1）与 BM25（随语料漂移的无界分）之间没有稳定的归一化关系——RRF 只用位次，天然跨量纲：

rrf_score(chunk) = Σ臂 1 / (rrf_k = 60 + rank臂)，rank 从 1 起
  • rrf_k = 60 是平滑常数，它把「第几名」的差距压平：第 1 名记 1/61 ≈ 0.0164、第 20 名记 1/80 = 0.0125，只差 24%。k 越大越平，「一条臂排第一」不再一票定生死，而「两条臂都进前列」稳定胜过「一条臂排第一」——这正是混合召回想要的取舍
  • 去重身份是 (knowledge_id, chunk_index)：两路都命中的块只出现一次，代表块取先被遍历到的那条（两臂顺序是向量在前），source = "hybrid"，evidence_score 取两路里的较大值（分臂判定用）
  • score 写归一化 RRF（本次候选最高记 1.0，其余按比例）：它仍是 0~1 且单调不增，与图谱分（1.0）同一量纲，下游的加权融合因此继续成立。它跨查询不可比，要展示「这条有多相关」应当读 evidence_score
  • 同分怎么定序：按 (knowledge_id, chunk_index) 升序兜底。融合结果因此不依赖字典 / 集合的遍历顺序，回放与测试可确定性复现（ADR-0008）
  • 两臂还分着的时候算好各臂最高原始分带出（RetrievedChunks.evidence）——事后无法从融合结果反推：hybrid 块的证据分是两路取大，拿 BM25 的量纲去冒充余弦，会让向量臂凭空达标
5

LLM 重排（增强步骤） knowledge/rerank.py::rerank_chunks

把整池候选交给一次模型调用重排序：专用提示词只要求输出 JSON 排序，不做判断、不生成文本。可配独立的 rerank_llm_* 小模型；单次调用、5 秒超时、不重试、不切备用配置——重排是排序增强，不该把 2 秒的检索拖成 30 秒以上。

  • 关闭 / fake / 回放时恒等保序、不发调用（按配置本来就不调用）
  • 达标块保底组装：已达标的块保底占位、未达标块按重排序补足名额（知识候选最终取 retrieval_top_k = 5 条；图谱增强会在此之后另追加图谱段落，总数不设上限）。重排不得把达标块挤出上下文——否则一次增强环节就改写了「有没有依据」的合规结论
  • 模型输出是不可信输入：越界序号、重复序号、非数值分一律丢弃，相关度截断到 [0,1]；结构本身不合预期（不是 JSON / 没有 ranking / 一条可用的都没有）时走降级退回 RRF 序，而不是拿一个空排序去覆盖它
6

graph_augment · GraphRAG 图谱增强 knowledge_graph/graphrag.py

图谱是什么：把 MySQL 里的业务数据「抄」成一张关系网——客户 —持有→ 产品，产品 —投向→ 行业，产品 —适合→ 风险等级，产品 —管理→ 基金经理。它是只读投影（单向、全量重建），只用来查、不回写。

为什么客服要用它：知识库文档只能回答「说明书上怎么写的」（某产品是混合型、风险等级 R3）；但「这位客户的持仓集中在哪些行业」这类需要跨好几张业务表连起来的事实，文档里没有。图谱把这类事实查出来，写成句子补进上下文。

这一步做三件事：

  • ① 认人认物（实体识别）：拿问句去比对图里节点的名字——客户姓名、产品名、基金经理、行业名，命中即算识别到；风险等级 C1–C5 是五个值的封闭词表，用正则直接认。因为比对来源就是图节点本身，识别出的名字天然对应图中真实节点，不需要额外校验。客户侧提问只认登录客户本人：别人的姓名即使与图中节点同名也不算命中，别人的持仓因此进不了上下文（P10）。
  • ② 顺着关系查（多跳查询）：从识别到的实体出发，用六个固定查询取事实——某客户持有哪些产品、某客户持仓的行业占比、某产品投向哪些行业、适合某个风险等级的产品、两位客户共同持有哪些产品、某位基金经理管理哪些产品。参数只有实体标识，语句写死、不拼接（P11）。
  • ③ 把事实写成句子掺进候选：每条查出来的事实拼成一句自然语言，例如「产品「稳健增利」底层资产中「医药」行业占比约 32%。」这就是「图谱段落」——它是查出来的确定事实，不是相似度算出来的，所以分数固定 1.0；在引用列表里标识成「知识图谱 + 查询工具」，不指向任何文档。

怎么和知识片段排到一起：两类候选先各自按权重打分，再合并成一张清单、从高到低排给模型看——知识片段得 0.6 × 它的排序分，图谱段落得 0.4 × 1.0。所以图谱段落大致落在中游：排在最相关的那些知识片段之后，但多数普通片段之前；图谱段落之间按内容去重（不同查询可能得到同一条事实）。

知识片段：0.6 × 排序分　|　图谱段落：0.4 × 1.0　→ 合并排序

注：「排序分」是候选在 RRF / 重排之后的位次分，不是原始余弦——原始分只在证据分闸门里用。

图谱是增强不是依赖：3 秒软超时；没查到图谱段落时，就按原来那批知识片段继续，分数一个都不打折（不会乘 0.6）。问句里认不出任何实体是正常结果，不是异常。

一句话边界：实体识别是「问句里出现图中已有的名字」这种直接匹配，不是语义理解——所以「我持有的产品都投了什么行业」里没有任何名字，这一步就没有段落；说成「王守成持有…」，或问句里带上产品名 / 基金经理名 / C1–C5，才会命中。

走一遍例子：客户问「王守成持有的产品都投了哪些行业？」
  • ① 认人：问句里出现「王守成」，与图中的客户节点同名 → 识别到这位客户（若是客户本人提问，则只认他本人）。
  • ② 查事实：先顺着「持有」关系查出他持有的产品，再顺着「投向」关系查出这些产品对应哪些行业、各占多少。
  • ③ 写成句子：得到几条图谱段落，例如「王守成持有产品「稳健增利」（混合类，风险等级R3），份额…，市值…元。」「王守成的持仓中「医药」行业占比约 32%，市值合计…元。」
  • ④ 掺进候选并排序：这几条按 0.4 分进榜；知识库片段按 0.6 × 排序分 进榜；两类合起来从高到低排成一张清单。
  • ⑤ 生成回答：模型拿这张清单作答，每句论断带 [N]；角标要么指向知识文档，要么指向「知识图谱」。
P10 客户实体只认本人 P11 固定 Cypher 防注入

出处：app/knowledge_graph/entities.py（实体识别）· tools.py（六个查询）· graphrag.py（段落拼装）· app/agent/fusion.py::fuse_and_rank（融合排序）

7

证据分闸门：该不该作答 agent/graph.py::route_after_retrieve

「有没有依据」是合规结论，由分臂证据判定，与排序无关——RRF 与重排只决定先后，不能让一次增强环节的抖动改写合规结论：

有依据 ⟺ 向量臂最高余弦 ≥ 0.57  或  关键词臂最高 BM25 ≥ 13.0  或  存在图谱段落
  • 两条阈值量纲不同（余弦 / BM25），由 golden 集校准产出（2026-09 校准：无关负例最高余弦 0.46、语义正例最低 0.68；负例 BM25 最高 10.63、正例最低 15.52）
  • 比的是融合前各臂原始分，不做权重缩放——图谱一参与，相似度分就被乘上 0.6，拿综合分判兜底会凭空抬高门槛
  • 不达标 → fallback 不作答：「不想给您一个没有出处的答案」+ 人工客服热线

SECTION 03

检索出结果之后：两个 Agent 分别怎么做

检索只是上半场。客服 Agent 把候选上下文变成「带强制引用、可审计」的回答；数据分析 Agent 把检索到的视图定义变成「受限、可执行」的 SQL。本节先讲客服 Agent 的下半场，数据分析 Agent 在第四节整节展开。

3.1 智能客服 Agent：从候选分块到带引用的回答

generate · 受限生成 + 强制引用 llm/provider.py::generate_grounded_answer

系统提示词钉死三条：只能依据检索片段（不得使用片段外知识）、不得做产品推荐或收益预测、每句论断必须用 [N] 标注依据片段序号，严格 JSON 输出 {answer, citations}。提示词 = 系统约束 + 会话历史（Redis 短期记忆，30 分钟滑动过期、2000 token 预算）+ 带编号片段 + 问题。

  • 短期记忆写回：本轮问答追加进 Redis 列表（写不进去也不影响本轮的答案）
  • 审计级留痕 ConversationArchive（永久）：使用者、Agent、问题、最终答案、引用、内容分类——合规举证
  • 调试级留痕 AgentDebugTrace（保留 30 天）：完整提示词、检索片段、token 与耗时
  • 高风险意图识别（关键词确定性，不过模型）：察觉转账限额规避、可疑资金流转等意图 → 事件总线广播 risk_intent_detected（载荷只带结论不带原文）→ 风控监测订阅方写一条风险关注——协作是增强，不改变本轮回答
  • SSE 流式：先把整轮跑完，再把定案回答逐字转成传输帧——推流过程不做任何决策

3.2 数据分析 Agent：检索之后做什么（摘要）

它的「检索」检出的是语义视图定义与 few-shot 示例（不是知识分块）。检索之后：视图定义注入提示词 → 模型生成单条 SELECT → 代码校验（第二道防线）→ 受限账号 + 行级身份执行 → 结果解读 → 审计留痕。完整链路见下节。客服 Agent 的「数据查询」分支复用同一条链路：执行身份锁死为凭证客户本人，解读改为面向客户的事实陈述；有结果时随回答附结构化结果表，剩下的文本只讲口径与行数。失败 / 越界 / 零行三种出口各自有话术（且不带结果表——空表会把「没有数据」与「查询挂了」抹平），绝不回退到知识检索拿泛泛之谈冒充数据答案。

SECTION 04

数据分析 Agent：NL2SQL 里的检索增强

入口 POST /api/internal/analytics/query（内部员工）。链路：select_views → generate_query → validate_query → execute_query → interpret_result。风控监测 Agent 与客服的数据查询分支都复用这条链路，各自只换视图范围与身份。

1

入口与员工身份 api/analytics.py

内部身份域 JWT + 会话白名单之外，还要员工确实存在（current_employee 查库）。任何内部员工都可提问；能查到哪些行不取决于问题文本，而取决于视图内建的行级权限与登录身份。

P06 员工身份核验
2

select_views · 检索相关视图与示例 analytics/catalog.py

按问题关键词（含历史问题，支撑「那上个季度呢」这类追问）从视图目录检出相关视图，同时检索同域的「问题 → 查询」示例。视图的列清单不手维护，从 information_schema 实时内省，保证注入的定义与迁移创建的视图不漂移。

  • 目录分两域：员工侧 5 张（客户概况 / 持仓分布 / 交易统计 / 产品要素 / 预警统计）、客户域 4 张（我的持仓 / 流水 / 资金账户 / 风评结论）
  • 每个 Agent 在自己的配置里声明看得到哪一域（view_names），两域互不可见；唯一的例外是产品要素——它无行级过滤且是已披露信息，客服的候选集里也声明了它（客服共 5 张），不声明的话客户拿自己的风险等级筛产品就走不通。示例同样按域收窄，员工侧看不到「怎么查客户自己的账」的样例
  • 一个都匹配不上 → 「超出可查范围」，模型看不到也生成不出别的域的查询
P15 视图候选集按 Agent 收窄
3

generate_query · 生成 SQL analytics/llm.py

提示词注入：视图定义（场景口径 + 列清单）+ 同域示例 + 历史。硬性规则写进系统提示词：只输出一条 SELECT、只能查给定视图、不得注释 / 分号 / SET / 变量。客户口径额外两条：视图已锁定本人数据、不要再按客户标识筛选；涉及产品只允许按风险等级筛选（Cn 筛 R1–Rn）、只按产品代码排序——按收益排序就是在替客户比较产品，那是投顾助手的产物。

4

validate_query · 安全校验（第二道防线） analytics/validation.py

字符串字面量与反引号标识符先抹掉再扫描，然后逐条拒绝：注释（-- # /*）、多语句（;）、会话变量（@——行级权限的提权面）、非 SELECT 首词、写类 / DDL / 权限关键词（INSERT、UPDATE、DELETE、CREATE、DROP、SET、GRANT、INTO 等 24 个）。刻意不做完整 SQL 解析：宁可误拒一条合法查询，不可放过一条拼接。

P17 SQL 校验防线
5

execute_query · 受限执行（第一道防线是结构性的） analytics/execution.py

  • 受限账号 wealth_analytics 只对这组语义视图有 SELECT，对基础表无任何权限——访问视图外对象在 MySQL 层即被拒绝
  • 执行前在同一连接上写入身份：员工 SET @analytics_employee_id / @analytics_employee_role，客户 SET @analytics_customer_id；行级权限内建在视图定义里——员工侧理财顾问 / 风控专员全量、客户经理只见名下客户，客户域锁死为凭证客户本人；身份未设置时视图返回零行（fail closed）
  • max_execution_time 5 秒；结果上限 200 行，超出截断并置标记
  • 归还连接池前重置两域身份；清理失败则作废该连接——不让下一个借用者继承上一个人的行级范围
P16 受限账号只对视图有 SELECT P18 行级权限 fail closed P19 连接身份归还前重置
员工在这条链路上能看到名下客户的什么、看不到什么

客户范围分两种：客户经理只有自己名下的客户，理财顾问 / 风控专员是全部客户；三类人看到的字段完全一样——字段就是下面这 5 张视图里定义的列：

视图能看到的字段
客户概况客户编号 · 姓名（实名） · 客户分层（普通 / 金卡 / 白金 / 钻石 / 私行）· 风险等级（C1–C5）· 资产规模 · 持仓数量 · 开户时间
持仓分布客户编号 · 产品代码 / 名称 / 类型 · 产品风险等级 · 份额 · 成本金额 · 当前市值 · 盈亏金额 · 盈亏比例 · 持仓状态
交易统计交易流水号 · 客户编号 · 产品代码 / 名称 / 类型 · 交易类型 · 金额 · 份额 · 净值 · 费用 · 交易状态 · 交易时间
预警统计预警编号 · 客户编号 · 预警类型 · 预警等级（轻度 / 中度 / 重度）· 预警状态（未处理 / 已排除 / 已升级）· 触发时间
产品要素产品代码 / 名称 / 类型 · 风险等级 · 预期收益 · 起投金额 · 期限 · 费率 · 基金经理 · 产品状态（无客户维度，因此这张没有行级过滤）

看不到的：

  • 敏感身份字段：身份证号 · 手机号 · 银行卡号 · 密码散列——结构性不进视图，不是靠权限挡，而是这些列在视图里根本不存在，任何问法都问不出。
  • 预警的自由文本：触发详情与处置结论两列（可能夹带任意内容）；只能看到类型、等级、状态、时间。
  • 客户域的四张视图（我的持仓 / 我的流水 / 我的资金账户 / 我的风评结论）：那是客户侧的数据，员工身份看不到另一域。
  • 基础表的原始数据：执行账号对 sys_customer、fin_holdings 这类基础表没有任何 SELECT 权限；视图没定义的列，也问不出来。
  • 别人名下的客户（客户经理）：行级过滤直接命中不了行，结果是零行——不是「无权限」报错，也不是「查不到这位客户」。

一句话记：范围由归属关系决定（sys_customer.manager_id），字段由视图定义决定，两者都是代码、模型改不了。姓名列在迁移 0034 改为实名（ADR-0029）——脱敏会让「按姓名查人」恒零行，进而被解读成「该客户无持仓」；敏感字段的边界没有放宽。

6

interpret_result · 解读与留痕 analytics/interpretation.py · service.py

  • 员工侧由模型解读：必须说明数据口径、不得编造结果中不存在的数字；低基数列的完整计数由代码算好放进提示词，模型不得凭样例重新计数
  • 客户侧不交给模型——模型会把口径说明里的字段名写成具体数字。客户侧文本由结果集直接生成，只说行数、截断与口径；逐行数据由随回答一起送达的结构化结果表承载（中文列标签、剔除客户标识列、SQL 不给客户）——表格与文本都不过模型，表格是数据的唯一出处（P20，ADR-0028）
  • 解读这一步若失败，用带口径的模板文本兜底，不让一次成功的查询整体失败
  • 审计留痕 AnalyticsQueryAudit：成功与被拒绝的尝试都记——事后可追溯谁试图查了什么
  • 内容分类默认事实性内容；命中报告类问法提升为投顾内容，进入必须审核的口径

SECTION 05

权限校验总表（20 道）

按三层归组：身份与入口、知识检索链、数据查询链。编号与流程图中的红色标记一一对应。

A · 身份与入口层
双身份域隔离

客户与内部员工是不同的表、不同的 token 受众（customer-app / internal-app）、不同的前端应用；不存在「同一个人既是客户又是员工」的账号。

JWT 验签三件套

HS256 签名 + audience 校验 + 类型（access / refresh）与过期校验；audience 不匹配是 403「身份域不匹配」，其余无效是 401。

Redis 会话白名单

凭证里的 sid 必须在 auth:session:{sid} 白名单内；登出即删，令牌未过期也失效。

知识库管理仅内部员工

上传 / 列表 / 删除 / 检索试验全部挂在 /api/internal/knowledge/*，要求内部身份域。

客服对话仅持牌客户

/api/customer/chat/* 要求客户身份域；会话标识取自凭证，短期记忆按会话隔离、不跨登录延续。

员工存在性核验

数据分析等内部接口在身份域之上再查一次员工表，员工不存在即 401。

回放模式关闭写操作

演示回放（demo_replay）下知识库写操作与图谱重建明确拒绝，不发起任何外部调用。

B · 知识检索链（智能客服 Agent）
入库格式白名单

仅 txt / md / docx；知识类型封闭集合 FAQ / 产品 / 政策，政策与产品带默认有效期。

命中块回查文档状态

向量臂命中后回查 MySQL 元数据，仅 active 文档的分块可进入候选——已下架 / 处理中的文档即使向量还在也不会返回。

GraphRAG 客户实体只认本人

客户侧提问把 only_customer_id 锁为登录客户：别人姓名解析不出实体，别人的持仓与行业敞口进不了上下文。

图谱工具固定 Cypher

六个查询工具的语句固定、参数是实体标识，Agent 不拼 Cypher；非法标识在发出查询前即 400。

证据分闸门：无依据不作答

向量臂余弦 ≥ 0.57 或关键词臂 BM25 ≥ 13.0 或有图谱段落，三者任一达标才允许生成；否则兜底话术 + 人工热线。重排与融合无权改写这个结论。

受限生成三禁令

只能依据检索片段、不得片段外知识、不得产品推荐或收益预测；每句论断强制 [N] 引用。

引用双向对齐

正文角标为权威：越界 / 悬空角标剔除，模型自报引用只作退化兜底；角标按回答内位次重排。

C · 数据查询链（数据分析 Agent / 客服数据分支）
视图候选集按 Agent 收窄

语义视图分员工 / 客户两域，各 Agent 显式声明自己那一域，两域互不可见；示例问题同样按域收窄。

受限执行账号

wealth_analytics 只对 9 张语义视图有 SELECT，对基础表无任何权限——安全性由结构保证，这是第一道防线。

SQL 校验第二道防线

只允许单条 SELECT：禁注释、禁多语句、禁会话变量（提权面）、禁写类 / DDL / 权限关键词；fail-safe 宁可误伤。

行级权限内建视图，fail closed

员工侧按角色与归属关系（理财顾问 / 风控专员全量，客户经理只见名下客户）；客户域锁死凭证客户本人；身份未设置返回零行。可查字段清单见第四节节点 5。

连接身份的生命周期管理

身份在执行查询的同一连接上设置，归还连接池前重置两域变量；清理失败直接作废连接，防止身份继承。

客户侧解读不交给模型

客户侧文本只给行数 / 截断 / 口径，逐行数据由结构化结果表承载，两者都由结果集直接生成，杜绝模型把口径字段名编造为具体数字；员工侧解读也被喂好计数、禁止重算。
