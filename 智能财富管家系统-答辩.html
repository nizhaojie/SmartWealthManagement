02 · ARCHITECTURE

技术栈之间是怎么联系的

前端只经 REST / SSE 打后端；后端 API 层之下是 Agent 运行时与领域模块；领域模块按职责各取所需地使用四类存储。Milvus 自己再用 etcd 存元数据、MinIO 存对象。

同步调用（REST / 驱动 / SDK） 异步 · 降级 · 镜像 · 内部依赖 核心节点（Agent 运行时）

数据怎么流

  • 写：一切权威数据只写 MySQL；Neo4j 是它的全量重建投影（ADR-0002）；知识文档同时落 MinIO / Milvus / MySQL 分块镜像三处。
  • 读：Agent 的受限查询只走 MySQL 语义视图；检索走 Milvus，超时 2s 降级为 MySQL 关键词检索。
  • 缓存：画像 Cache-Aside 300s；Redis 任何错误都视为未命中并记降级留痕。

请求怎么串

  • TraceIdMiddleware 生成 trace_id，贯穿一次请求及其触发的全部事件。
  • SSE 流式：客服整轮跑完再把定案回答逐字转帧——推流过程不做任何决策。
  • 审核断点：LangGraph interrupt() 暂停在 await_review，理财顾问放行后 resume 续跑。

依赖怎么降级

  • 七类依赖（模型 / 向量库 / 重排 / 图谱 / 缓存 / 事件总线 / 客户数据查询）各有降级行为；前六类有备用路径，客户数据查询没有备路、失败即明说。共同点是降级后仍是成功响应，只是依据更弱。
  • 每次降级写一条 DegradationTrace——回答「系统有多少时间在降级状态工作」。
  • 模型调用链：超时 → 指数退避重试 → 备用配置 → 预设兜底话术。

LangGraph：把 Agent 跑成一张流程图（需要时能停下来等人）

LangGraph 是一个「照着流程图跑程序」的框架。这个项目用它的理由只有两条，都很朴素：

  • 第一，把流程画出来。一次 Agent 处理被拆成若干「步骤」（框架里叫节点）：谁接谁、什么时候分岔，都写在图里。好处是「这段业务怎么走」看得见——不是一长串 if/else，而是一张能拿给人看的图。五个 Agent 各有一张自己的图（第三节逐张画出）。
  • 第二，能停、能续。投顾方案生成完要等理财顾问审核，图就得能跑到一半停下、把当前进度存一份，等人放行或驳回后从停下的那一点接着往下跑。这套「暂停—存档—恢复」很费工；自己写等于自己重写一个状态持久化机制，LangGraph 自带（ADR-0007）。

五处关键写法（不看代码也说得清）

  • ① 画图：声明一张图 → 逐个登记节点（节点就是普通函数）→ 指定从哪一步开始 → 编译。编译出来的对象可以直接调用，调用它等于「照着这张图跑一遍」。backend/app/agent/graph.py
  • ② 分岔：把「下一步该去哪个节点」写成一个函数，函数返回节点名。意图是关键词判的、证据够不够是阈值判的，都是代码；框架只负责按返回值走。所以图上的每条虚线都能指回一段判断逻辑。
  • ③ 停下来等人：在要等的那个节点里调用一次「中断」函数，整张图就在这一点暂停；编译时挂上一个存档点，暂停的进度存在它里面，键是这次运行的标识（thread_id）。advisory/graph.py · advisory/runtime.py
  • ④ 从断点续跑：顾问点放行或驳回时，是另一个请求带着同一个运行标识回来；先确认存档点还在（不在就明确让顾问重新生成，而不是抛一个看不懂的错），再把决定喂回图中——那个节点重跑一遍，中断函数这次直接返回决定，然后继续往下走。advisory/review.py
  • ⑤ 图的寿命：数据库连接、缓存这些「外部工具」是调用时临时带进去的，不放进图的状态里；所以图是每次请求现场建、跑完即弃，不在内存里长期挂着状态。advisory/service.py

项目里怎么用

  • 图里只画流程，不放数据：每个节点就是一个普通函数，要用什么（数据库连接、缓存、图谱驱动）由调用它的人临时传进去。所以图是每次请求现场组装、跑完就结束，不在内存里长期挂着东西。
  • 分岔用「条件边」表达：客服图先按关键词判意图，决定是闲聊、转人工、查数据还是查知识库；检索回来后还要判断「证据够不够」，够就生成回答，不够就走兜底。这些判断全是代码，不是模型。
  • 只有要等人的图才配「存档点」：投顾方案与业务操作两张图在产出原稿后停下等顾问，进度存在一个进程级单例里，键是 thread_id（这个键写在审核记录上）；放行或驳回时用同一个键把图接回来。其余三张图一次跑完，不需要存档。

三条刻意守住的边界

  • 存档不扛进程重启：用的是内存实现，重启后检查点就没了。所以续跑之前先查一眼检查点还在不在，不在就明确告诉顾问「请重新生成」，而不是让框架异常漏成 500。
  • 恢复时不许跑错图：审核记录上带着「内容类型」，按类型查表拿到那张图；类型没登记就报错，绝不复用别的类型的图——跑错图等于把一份决定喂给了另一份内容。
  • 不该用图的地方就不画图：风控监测的主链路是确定性规则引擎（阈值判定不经过模型），本来就不是「会停下来等人的流程」，所以它没有自己的状态图——只有自然语言查预警时才借用数据分析那张图。

一张总览之外，第三节把五个 Agent 各自的执行流程逐张画出：四张是 LangGraph 状态图，风控监测是它自己的确定性流水线。

03 · AGENTS

项目里有哪些 Agent

五个 Agent 是同一套 LangGraph 运行时上的五份配置（提示词、工具集、记忆策略、内容分类默认值），路由按登录身份在入口确定，不存在运行时的意图分发。注册表集中在 backend/app/agent/registry.py。

1智能客服 Agent

面向客户 · 客户域 · POST /api/customer/chat/*
knowledge_search 客户域语义视图查询（数据查询分支） 只产事实性内容
  • 图：关键词意图分类 → 闲聊 / 转人工 / 检索 → GraphRAG 增强 → 证据分判定 → 受限生成 + 强制引用。
  • 工具集内不存在推荐类能力；产品只筛不排序、按产品代码排序，因此仍不构成推荐。
  • 客户可用自然语言查自己的持仓 / 流水 / 余额（复用 NL2SQL 链路，行级锁本人，ADR-0025）。
  • 关键词识别高风险意图 → 只广播一条事件给风控，不产生预警、不改变服务。
检索不到依据 → 不作答，给兜底话术与人工热线。

2数据分析 Agent

面向内部员工 · 内部域 · POST /api/internal/analytics/query
analytics_query_generation analytics_query_execution 事实性内容
  • NL2SQL 五节点链：选视图 → 生成 → 安全校验 → 受限账号只读执行 → 带口径解读。
  • 只能查语义视图（员工侧 5 张），三重保护：受限 DB 账号 + 提示词约束 + 代码校验拒绝写类语句。
  • 行级权限内建在视图定义里：顾问 / 风控全量，客户经理只见名下客户；未设身份返回零行（fail closed）。
行数上限 200、查询超时 5s；成功与拒绝都写审计。

3投顾助手 Agent

面向理财顾问 · 内部域 · POST /api/internal/advisory/customers/{id}/plan
candidate_pool_ranking allocation_suggestion 投顾内容 · 必须审核
  • 图：读画像 → 加载适当性硬过滤后的候选池 → 三因子加权排序 → 生成理由 → 配置建议 → 汇总警示 → 落 AI 原稿 → interrupt 等审核。
  • 排序三因子：收益（池内归一化）/ 风险等级差 / 期限匹配；侧重只改权重不改代码。
  • 风控预警以「风险标记」进入方案（来自事件总线订阅）。
产出 AI 原稿（不可改）→ 顾问定稿是唯一可送达客户的版本。

4业务操作 Agent

客户经理发起 · 理财顾问放行 · POST /api/internal/customers/{id}/operation-advice
candidate_pool_query customer_holdings_and_balance_query operation_advice_generation 投顾内容 · 必须审核
  • 产物是单笔操作建议：一个产品、一个方向、一个金额、一条理由（ADR-0017 / 0021）。
  • 与投顾助手的分工在产物而不在技术；但它不做排序也不选品——产品与金额由发起人选定，图里没有排序节点（ADR-0021）。
  • 三条硬边界：一次一个产品一个方向、金额必填、禁止收益预测与配置比例表述。
  • 它不执行任何操作——接受与否是客户决定，接受才产生交易。
与投顾方案共用同一条审核流水线（ADR-0020）。

5风控监测 Agent

面向风控专员 · 内部域 · POST /api/internal/risk-monitoring/query
risk_alert_query work_order_operation risk_rule_query 事实性内容
  • 主链路是确定性规则引擎，不是 LLM：交易事件先事务性落库 → 再广播 → 规则求值 → 命中生成预警。
  • 封闭算子集（单笔比较 + 窗口聚合）× 封闭字段集（11 个），阈值判断不经过 LLM。
  • 初始 20 条反洗钱规则 R001–R020 共 7 类；规则可在库中增删改（软删、编号永不复用，ADR-0026 / 0027）。
  • 预警分级：单规则 → 轻度，多规则 → 中度，多规则 + 历史 → 重度；处置走工单（理由必填，流程见 5.5）。
自然语言查预警复用数据分析链路，视图收窄为预警统计一张。

∴为什么这样切

设计理由
  • 按身份域与产物切分，不按技术切分：五个 Agent 共享运行时、审核流、留痕与降级设施。
  • 「谁能产投顾内容」由内容分类默认值钉死：客服 / 分析 / 风控默认事实性内容，投顾 / 操作默认投顾内容。
  • 新增 Agent = 新增一份配置 + 一个入口路由，注册表是唯一出处；GET /api/agents 把它只读输出。
  • 路由在入口按登录身份确定——没有运行时意图分发，这是可审计性的前提。

每个 Agent 的执行流程（五张图）

读法很统一：金色实线 = 按顺序往下走；灰色虚线 = 分岔、绕道或中断；金色描边方框 = 要停下来等人。前四张是 LangGraph 状态图，第五张是风控监测自己的确定性流水线。

1 · 智能客服 Agent（8 个节点）

1 个入口分类 → 3 个提前出口（闲聊 / 转人工 / 借分析链路）+ 主线 4 步，最后按「证据够不够」分成两个结局。全程不等人，所以没有中断点。

注 · classify 怎么判意图：一张关键词表 + 固定优先级，不调模型

判定只有「子串包含 + 先命中的先返回」两个动作，顺序即优先级：

顺序 意图 关键词（示例） 判完之后去哪
1转人工 转人工 · 人工客服 · 找人工 · 投诉 · 转接人工 handoff：返回固定话术，连模型都不调
2数据查询 我持有 · 我的持仓 · 我的余额 · 适合我 · 转了多少 data_query：绕到「数据分析」那张图，执行锁本人
3政策解读 政策 · 规定 · 条款 · 法规 · 细则 · 办法 进知识检索：retrieve → graph_augment → generate / fallback
4产品咨询 产品 · 费率 · 净值 · 起投 · 赎回 · 期限 · 收益率 同上（进知识检索）
5闲聊 你好 · 在吗 · 你是谁 · 天气 · 谢谢 · 拜拜 chitchat：寒暄回复这一步才调模型
6FAQ（兜底） 没命中上面任何一张表 进知识检索（默认落点，偏保守）
  • 金融关键词优先于闲聊关键词：避免「你好，请问费率是多少」这类带寒暄前缀的真问题被判成闲聊。
  • 数据查询刻意用第一人称短语（我持有 / 我的持仓），不收「持有」「产品」「转账」这类会与业务咨询重合的词。误判的代价是双向的：产品问题被当成数据查询，客户拿到「查不到」而不是知识库里的说明书；数据问题落进知识检索，客户拿到没有出处的泛泛之谈——后者比前者更坏。
  • 转人工排在最前：「我要转人工投诉」是必须立刻交到人手里的诉求，不该被任何业务关键词截走。
  • 不调模型的是「判断」，不是整条链路：闲聊分支的寒暄回复、检索分支的生成才调模型；转人工分支连模型都不调。
  • 边界：关键词表是穷举，没覆盖的说法会落到默认 FAQ。方向是保守的——后面还有证据分闸门兜底（没依据就不作答、给人工热线）；要加新说法只改这一张常量表，不动流程。

2 · 数据分析 Agent（5 个节点）

五个节点一条直线走到底，每一步都可能提前结束；怎么向人交代由调用方决定（员工侧抛错、客户侧转话术）。同样没有中断点。

注 · ④「受限账号只读执行」与行级权限怎么落地

  • 受限账号：执行这条 SQL 时换用受限账号 wealth_analytics——它只被 GRANT 了语义视图的 SELECT、对基础表零权限，所以写操作和「查视图之外的表」在 MySQL 层直接失败。限制来自授权，不来自提示词。
  • 只读：账号本身无写权限，前面还有 validate_query 只放行单条 SELECT，拒绝注释、多语句、写类关键词与 @ 会话变量——@ 正是行级权限的自我提权面，必须堵死。
  • 视图固定，变的是行：范围条件焊死在视图定义的 WHERE 里，值在查询时从当前连接读会话变量（经 NO SQL 函数 analytics_employee_id() / analytics_employee_role() 中转——MySQL 视图不能直接引用用户变量）。模型改不掉这段条件；改视图要 DDL 权限，而受限账号只有 SELECT。
执行时的身份同一张视图返回
理财顾问 / 风控专员全量客户行
其他角色（客户经理）只见 manager_id 等于本人的客户
未设身份函数返回 NULL → 条件不成立 → 零行（fail closed）
客户（数据查询分支）换客户域 4 张视图，条件为 customer_id = analytics_customer_id()；两域变量互不相通，串不到对方的行

身份写在执行那条连接上，查询结束立即清理，清理失败则作废连接，避免下一个请求继承上一个人的范围。va_product_element 是产品主数据、不含客户数据，因此不做行级过滤。

3 · 投顾助手 Agent（9 个节点 · 含审核中断）

前六步自动跑完 → 落原稿 → 在 ⑧ 停下等顾问（进度送进存档点）→ 放行或驳回后从 ⑧ 接着走到 ⑨ 落定稿或留痕。这是「能停能续」的典型图。

注 · ②「适当性硬过滤」与 ③「三因子排序」分别在做什么

  • 硬过滤发生在检索层：允许范围由最新风险测评算出——Cn 客户只允许 R1–Rn，查候选池时就带上这个范围，越级产品根本不进池，后面的排序与模型都没有机会看到它，因此不由模型裁量。两条额外收紧：测评过期 → 范围置空并返回 403；无收入且总资产不足万元 → 上限压到 R2。
  • 排序只在池内做：输入是候选池减去已持有的产品，每只按三个因子各打一个 0–1 分，加权求和降序排列。全程确定性计算，不调模型；同分按产品代码升序，结果可复现。
因子怎么打分（0–1）权重：均衡 / 收益优先 / 流动性优先
收益池内 min–max 归一化：最低得 0、最高得 1（是池内相对分，不是绝对收益高低）1/3 · 0.6 · 0.2
风险等级差越小越高：C3 买 R3 = 1.0、买 R2 = 0.75、差 4 级 = 01/3 · 0.2 · 0.2
期限匹配不超过客户等级对应的周期即为满分（C1 90 / C2 180 / C3 270 / C4 365 / C5 540 天），超出后按超出比例扣分1/3 · 0.2 · 0.6

每维的原始值、得分、权重、贡献都留在 score_breakdown 里供顾问核对，但不送达客户——送达版本只保留客观产品要素（ADR-0016）。侧重只改上面那张权重表，不改代码。

4 · 业务操作 Agent（7 个节点 · 含审核中断）

形状与投顾方案一样（落原稿 → 停下等审核 → 定稿或留痕），但节点少两个、且没有排序节点：它只负责核验与成文，不负责挑产品。

5 · 风控监测 Agent（不是状态图）

主链路是确定性流水线（阈值判定不经过模型），也不是「会停下等人」的流程，所以它没有自己的状态图；只有问「有哪些预警」时才借用数据分析那张图。

5.5 工单流 · 预警的处置载体

预警只陈述「什么被触发了」；处置过程不由预警自己承载。预警派生出工单，受理人、状态、处置结论与每一次流转的理由都落在工单这条线上——事后能回答「这条预警谁办的、为什么这么办」。

状态是一条单向链，跳步与回头都会被拒绝；每次流转都要说清理由，所以「谁把它推到这个状态」查得清。

  • 一条预警最多派生一张工单：派生入口先查一次、给出明确报错，数据库唯一约束是最后一道——两个并发请求只有一个能落库，另一个被翻译成同一个错误。已处置的预警不再派生，避免同一个事实被处置两次。
  • 每次流转必须说清理由：空白字符不算理由（「留个空格」等于「没填」）。办结还要额外写处置结论；关闭只要求理由——销户、重复建单这类终止本来就没有结论可写。
  • 每个状态都有出处：留痕表只追加，建单时也写一条（from_status 为空），不存在凭空出现的状态。工单与预警的生命周期不合并：工单办结不等于关闭预警。
  • 等级已经算过一次，不让工单再选优先级：重度→特急、中度→紧急、轻度→普通由代码映射；没见过的等级回落「普通」，宁可排在后头，也不因为一个陌生字面量丢单。
  • 谁看得到、谁能办：客户经理只看得到自己名下客户的工单，写操作收紧到风控专员；来源类型里「预警处置」只能由预警派生——人工建单不允许自称预警处置，否则会绕开「一条预警一张工单」。
06 · HIGHLIGHTS

值得一说的细节

答辩时最值得展开讲的十处设计——它们都是「为什么这样做」有明确答案、且答案写在 ADR 里的决定。

1
确定性判断不经过模型 适当性硬过滤、风控阈值、投顾排序、高风险意图识别全部是代码。模型只负责理解、生成与排序阐述；「Cn 客户只能持有 R1–Rn」在适当性候选池这一层硬过滤，越级产品根本不进候选池，因此不由模型裁量。
2
AI 原稿 / 顾问定稿两版本永久留存 原稿只写不改，定稿同样不可改，客户只看送达视图。用途是合规举证：能证明审核是实质性审核（顾问确实改过），而不是点了个按钮。
3
证据分分臂判定，与排序解耦 「有没有依据作答」比的是融合前各臂原始分（余弦 / BM25 量纲不同，各有阈值），图谱查得确定事实直接达标；权重只负责排序。于是一次重排的抖动不会改变「作答还是兜底」这个结论。
4
语义视图 + 行级权限内建 + fail closed NL2SQL 只能查语义视图：受限账号只 GRANT 这组视图的 SELECT，行级过滤写在视图定义里（NO SQL 函数读会话变量），身份未设置时返回零行。员工侧与客户域两套视图互不可见。
5
降级是产品行为，不是错误处理 七类依赖各有降级行为（其中客户数据查询没有备路，失败即明说），降级后仍是成功响应；因为降级不产生错误、只看错误率看不出来，所以单设降级留痕回答「系统有多少时间在降级状态工作」。
6
事件总线：广播是增强，不是数据通道 交易先事务性落库再广播，不依赖广播通道保证不丢；Redis 只是出站镜像，进程内分发放在 finally 里——Redis 抖动不影响 Agent 协作。订阅注册表让新增订阅不改发布方。
7
七条合规护栏不变量 适当性硬过滤、身份域隔离、只许只读查询、产品列表不按收益率排序、未审核内容不可送达、shared 不含业务语义、交易受理校验不可绕过——ADR-0009 定下这七条，每条都落在 CI 里跑的真实测试上（分散在后端与 shared 的多个测试文件中），把合规约束变成可执行的断言。
8
shared 包的构建期边界闸门 check-boundary.mjs 在 build 时词法扫描共享包，命中风控字段、预警分级、审核状态、画像权重等业务语义即中断构建——共享层永远长不出业务逻辑，两个前端因此不会各自漂移。
9
规则引擎的「组合而非表达」 风控专员能配的是在给定字段、算子与值域里挑组合，不能拼逻辑造新算子——否则规则表就变成「存在数据库里的代码」。判定形状即规则身份：改形状只能删除重建，删除是软删、编号永不复用。
10
29 条 ADR + 领域词汇表驱动开发 每个重要决定都有编号的架构决策记录，推翻旧决定必须新增一条说明原因、不许静默偏离；根目录 CONTEXT.md 统一全仓库用词（如「送达」不是「推送」、「客户决定」不是「授权」），spec / issue / 代码共用同一套语言。
一句话总结

这是一个把 LLM 的不确定性关在笼子里的系统：模型只做它擅长的（理解、生成、排序阐述）， 所有合规相关的判断（适当性、风控阈值、审核放行）都是确定性代码； 五个 Agent 共享一套运行时与审核流水线，靠事件总线松散协作， 每一次检索、回答、降级与审核都留有可追溯的痕迹。
